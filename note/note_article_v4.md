# 覚える辞書が、自分の成績を下げていた──「工程表→工程表テスト」と登録した日の記録

会議の録音を文字起こしして、**誰が言ったか**を割り当てるツールを作っています。

文字起こしは固有名詞をよく間違えます。しかも同じ組織の会議なら、同じ人名が毎回同じ形で間違う。なら覚えさせればいい。そう考えて「聞き違いの辞書」を足しました。

動きました。実際の会議データで一周して、想定どおりに動いた。

そのうえで、**辞書が自分の成績を 0% と記録しはじめました。**項目は正しいのに、です。

原因は、私が最初に登録した 1 件でした。

---

## 30秒で分かる前提

作っているのは文字起こしツールではなく、**「この記録のどこを人が耳で確かめたか」が残るエディタ**です。

- **✓ = 音声を聴いて人が確定した**
- **△ = 一括で埋めただけ**

この区別が消えないようにする。それが製品の中身です。転写エンジン自体は差し替えられる部品として扱っています。〔出所: README「このアプリの考え方」/ CLAUDE.md の設計原則〕

今回の話は、その上に足した 2 つの機能で起きました。

1. **語句をまとめて直す画面** — 「田中」を探して、出てきた箇所を一覧にして、**行ごとに ○×** を付けて、○ だけ直す。一括置換ではありません。
2. **聞き違いの辞書** — 直した組（誤り → 正しい語）を貯めておいて、次の音声でも候補として出す。

1 が土台で、2 がその上に載ります。〔出所: 設計書 §2・§3〕

---

## 辞書に「自動で直す」をさせなかった

辞書機能でいちばん時間をかけたのは、**作らなかったもの**の側です。

「田中 → 田仲」を辞書に入れたら、次からは自動で直してほしい。普通そう考えます。私も考えました。

やめました。**「田中 → 田仲」が正しいのは、特定の一人についてだけ**だからです。同じ会議に別の田中さんがいれば、その人は誤って書き換えられます。日本語には語の境界が無いので、部分一致は避けられません。「資格」を直そうとして、本物の資格の話まで巻き込む。

自動適用は、一括置換の危険を消すのではなく、**利用者の目の届かないところに移すだけ**です。

なので辞書がやることは、○× 画面に「この語を探せ」と渡すところまでに限りました。探した結果に ○× を付けるのは人です。**辞書から直した箇所にも ✓（聴いて確定）は付きません。**音声を聴いていないからです。〔出所: 設計書 §3.2〕

この判断は今も正しいと思っています。今日の話は、その先で起きました。

---

## 効果の測り方を、使う前に決めた

前回の測定記事でも書いたことですが、**指標は測る前に固定します。**数字を見てから定義を変えれば、都合のいい値をいくらでも選べてしまうので。

辞書についても、作る前に決めました。

> 適用 ÷（適用 ＋ 却下）＝ 辞書の精度
>
> 〔出所: 設計書 §3.1〕

辞書が「この箇所を直しませんか」と出してきて、人が ○ を付けたら適用、× を付けたら却下。**× の件数も残す**ことを、わざわざ決めて書いています。○ だけ数えたら、外しまくっている辞書でも成績が良く見えるからです。

管理画面に「3/2 (60%)」のように出ます。項目ごとに、その項目がどれだけ当たっているか。

**この仕組みが、今日おかしくなりました。**

---

## そして、「工程表」を登録した

実機で一周する日でした。辞書に候補が出る状態を作るために、実データに出てくる語を 1 件登録しました。

```
工程表 → 工程表テスト
```

テスト用なので、元の語にそのまま「テスト」を足しただけです。深く考えていません。

置換は正しく動きました。本文は「工程表テストを確認します」になった。管理画面にも「由来: 置換」で記録が残った。ここまでは想定どおりです。

**次に辞書を開いたら、まだ候補が出ていました。**

置換したはずの箇所です。直っているのに、候補として出てくる。

理由は一行で説明がつきます。**「工程表テスト」の中には「工程表」が入っている。**部分一致なので、直したあとの本文にもヒットし続けます。

---

## 測ってみた

見立てで書くのは前回やめたので、実物のコードで再現しました。同じ語で、**重なる組と重ならない組を並べます。**

〔出所: 2026-09-06 に `src/dictionary.py` と `src/segments.py` を直接呼んで実行。出力そのまま〕

```
--- 工程表 -> 工程表テスト : 重なる ---
  置換前: 工程表を確認します
  置換後: 工程表テストを確認します
  置換後の候補: 1 件 (項目は候補ありとして数え続ける)
  3 回 x で送った後: 適用 0 / 却下 3 -> 精度 0%

--- 工程表 -> 作業表 : 重ならない ---
  置換前: 工程表を確認します
  置換後: 作業表を確認します
  置換後の候補: 0 件 (項目は候補なし)
  3 回 x で送った後: 適用 0 / 却下 0 -> 精度 (記録なし)
```

下は正常です。直したら候補が消える。項目は役目を終える。

上が問題です。**直しても候補が消えない。**そして、消えないので次の回も出てくる。出てくるので人が × を付ける。× を付けるたびに却下が増える。

**3 回で精度 0%。**

---

## 重いのは、候補が残ることではない

候補が残り続けるだけなら、うるさいだけの不具合です。毎回 × を 1 回押せば済む。

**重いのは、その × が記録されることです。**

「工程表 → 工程表テスト」という項目は、**正しい**項目です。実際に一度は役に立って、本文を直しています。それが 0% と記録される。

つまり、**辞書の効果を測るために入れた仕組みが、正しい項目を「不正確」と記録していく。**

私は辞書の効果を件数で測ると決めました。効果があるかどうか分からなかったからです（同じ人名が録音をまたいで繰り返し出るかどうかに依存し、実会議の音声はまだ 1 件しかありません）。分からないから測ることにした。その測る道具が、**測る前から歪んでいた。**

しかも歪む向きが悪い。**辞書は「効いていない」側に間違えます。**成績の良い辞書を悪く見せるほうに転ぶので、「辞書は効かなかったから外そう」という判断を、間違った数字が後押しすることになります。

割当画面を開くたびに出る「辞書の N 項目に候補があります」という知らせも、この項目を数え続けます。永久にです。

---

## どうやって見つかったか

コードを読んで見つけたのではありません。**使っていて見つかりました。**

しかも、見つけたときは不具合を探していませんでした。テスト用の語を登録して、辞書の画面を一周していただけです。「あれ、直したのにまだ出る」と思った、それだけ。

同じ日に、同じ画面で、別の食い違いも 2 件出ています。

一つは、画面の上下で矛盾する文が同時に出ていたもの。下部の状態行に「辞書の候補はもうありません。」、その下の辞書の行に「辞書の 1 項目に候補があります。」。どちらも**単独では正しい**（前者は「次の項目」の有無、後者は辞書全体の状態）のですが、並べて読むと矛盾します。辞書全体の話が画面の 2 か所に分かれて書かれていたのが原因でした。

もう一つは「残り N 項目に候補」という表示が、**いま開いている項目を数に入れていた**こと。項目が 1 件しかないのに「残り 1 項目」と出て、「次へ」を押すと何も無い。

3 つとも、**動かして目で見るまで分かりませんでした。**テストは全部通っていました。〔出所: 当日の実行。CLAUDE.md 指定の 12 ファイルを個別実行し、1371 項目すべて通過〕

これは自動テストの限界というより、**自動テストが縛れるのは「書いた人が想定した食い違い」だけ**、ということだと思っています。想定できていたら、最初からそう書いています。

## 何が言えて、何が言えないか

**言えないこと**

- **これは私の実装の話です。**「覚える辞書」一般がこうなるとは言えません
- 部分一致が既定なのは日本語向けの判断です。語境界のある言語なら、完全一致で回避できる場面はあります
- 精度指標が歪む度合いは測っていません。**「歪む」ことは示しましたが、「どれだけ歪むか」は分かりません**
- 対策はまだ入れていません。**この記事は直した記録ではなく、見つけた記録です**

**言えること**

- **`correct` が `wrong` を含む項目を登録すると、その項目は候補を出し続けます**（実測）
- **その候補を却下すると、正しい項目の精度が下がります**（実測。3 回で 0%）
- **歪む向きは「効いていない」側です**
- そして、**この種の罠は、テストではなく使うことで見つかりました**

## 結局どうしているか

まだ直していません。今日は記録だけ残しました。〔出所: 設計書 §3 に追記。対応は次回以降〕

案は 2 つあります。

1. 登録するときに `wrong` と `correct` の包含を検出して、人に確認する
2. すでに直っている箇所を候補から外す

どちらを取るにしても、**`reviewed`（✓）と本文には触れない範囲で収める**のが条件です。「もう直っているから候補から外す」は一見きれいですが、**機械が「これは直っている」と判断する**ということでもあります。その判断が外れたとき、利用者からは見えません。今日の話は、まさにその手の見えない判断が測定を歪めた話なので、同じ形の解き方には慎重でいます。

もう一つ、実務的な結論を。

**「覚える機能」を足すときは、覚えたものが自分の成績表を書く経路を先に確かめる。**

自動で直さないことは、最初から決めていました。そこは守れています。守れていなかったのは、**辞書が自分自身をどう評価するか**でした。人の判断を機械が上書きしないようにする設計はできても、**機械が自分の成績を書く経路**までは見ていなかった。

現在のバージョンは v2.2.1 です。〔出所: GitHub Releases。2026-09-03 公開〕検索・置換と辞書は次の版に入ります。**【マージ後に確定】この記事を公開する時点で、辞書は PR がマージされ、v2.3.0 として出ている見込みです。ただし本記事の執筆時点では未マージで、画面の文言 3 つと 1024×768・拡大率 125% での表示が実機未確認のまま残っています。**

未確認のものを「確認した」と書かないために、この段落を残しています。今日つぶしていたのが、まさに**書いてあることと実物が違う**という型の欠陥だったので。
