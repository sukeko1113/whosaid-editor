## 1. 最も重要な発見 — 時刻の正解データは存在しない

`truth/verbatim.*.json` を読んで確認した。

```json
{"project": "01+02edited.speakers.json", "made_by": "human-verbatim"}
{"index": 4, "start": 65.64, "end": 66.86, "asr": "はい、以上です。", "truth": "はい、以上です。"}
```

**人が直したのは `truth`（本文）だけである。** `start` / `end` は `project` が示すとおり、
製品のローカル実行（faster-whisper small）が出した時刻がそのまま入っている。
段階2 の正解作りは「本文を聴いたとおりに直す」作業で、**時刻には触れていない**
（`claude_正解ラベルの作り方_設計書.md` §9）。

> **「最大外れ量」を「正解時刻との差」として定義することはできない。**
> 比べる相手が無い。

**気づかずに進めば、「local の時刻を物差しにして local が最良」という
無意味な結果を出すところだった。**

## 2. 訂正 — `index` は時刻順である（local も artifact だった）

**一度、誤った結論を出した。** 「`.speakers.json` を `index` 順で読めば生成順が得られる。
`premerge`（話者結合前）だから妥当」と**推論で**書いた。**コードを追ったら誤りだった。**

```python
# src/pipeline.py:959   話者分離が有効なとき
all_segments = sorted(all_segments, key=lambda s: (s.start, s.index))
...
# src/pipeline.py:974-975   「通し番号を振り直す」
for n, seg in enumerate(all_segments):
    seg.index = n
```

**開始時刻でソートしてから `index` を振り直している。** したがって
`.speakers.json` の `index` 順 = **時刻順**であって生成順ではない。

**`premerge` でも救われない。** ソート（959）は `merge_same_speaker`（964）より**前**にある。

`src/segments.py:90` にも警告があった。

> **`index` は鍵にしてはいけない**——分割・結合・再実行で振り直る。

**読んでいたのに、自分の主張に引きつけて解釈していた。**

### 失われ方が静かである

気づかなければ「local は破れ 0 件、B は N 件」という表が出て、**数字は全部正しく計算されている。**
違うのは **0 の意味だけ**で、読んだだけでは分からない。
§8 判定1 で議論した「捏造は脱落より重い」のと同じ構造が、**測定側で**起きるところだった。

**教訓: 前提はコードで確認する。「〜だから妥当」は確認ではない。**

## 3. 物差しの選択と、その限界

時刻の正解が無いので、**`src/align.py` の単語時刻を物差しにする。**
音声から直接得られ、評価対象のエンジンとは独立している。

### 3.1 限界1 — local と同じ ASR である（系統的な偏り）

物差しは faster-whisper。**local も faster-whisper。**
したがって **local の外れ量は定義上ほぼ 0 になる。**

```
local(生成順)   測れた 556 / 中央 0.00 / p90 0.00 / 最大 0.20
```

**「local の時刻が正確」なのではない。「local を local 自身で測っている」だけである。**
物差しを align に替えても同じ small 系列なので、**この偏りは残る。**

> **local の外れ量を判定に使わない。**表だけ見た人が local を最良と読む。
> `report_timing.py` は外れ量の表を出すたびに、この注意を直下に印字する
> （`DEVIATION_CAVEAT`）。

### 3.2 限界2 — 物差し自身が誤る（偽マッチ・閾値では防げない）

```
atrain #115  申告  686.2s → 実位置 3879.0s  外れ 3192.8s  被覆 0.62
             本文: 遅刻して申し訳ございません。

物差し[660-720s]   …大事体育館【遅刻して申し上げて】東京くんのはどうですか…
物差し[3865-3895s] …申し訳ありませんでした【また遅れて申し訳ございました】…
```

**正しい位置（686 秒）に発話は存在する。** ただし**物差しがそこを誤って書き起こした**
ため、正しい位置の得票が下がり、literal に近い別の位置が勝った。

**`locate()` の欠陥ではなく物差しの欠陥である。区間の本文をどう検査しても直らない。
情報が物差しに無いためである。**

whisper small は発話を落とし・崩す。6 エンジンの和集合でも 33 件中 14 件は誰も拾えない
（技術方針書 §11.6）。**物差しも同じ ASR なので、同じ穴を持っている。**

**したがって外れ量の最大値は原理的に頑健にならない。**
`p90` を主指標とし、最大値は上限として併記する（指示書 v4.3 §8 判定2）。

### 3.3 門番を足しても救えない

`LOCATE_AMBIGUOUS_SUPPORT = 0.5`（2 位が本文の 5 割以上を説明できるなら棄却）を
足した。**19 件を新たに棄却したが、#115 は捕まえない**（2 位の説明率 0.36）。

**捕まえるまで閾値を下げてはいけない。** 分布に合わせて閾値を選ぶことになり、
しかも原因は曖昧さではないので、**正しく測れるはずの区間を捨てて標本の偏りを増やすだけ**である。

## 4. 判定2 の基準線 — local の破れ 0 件（測定値）

§2 のとおり `.speakers.json` は使えない。代わりに
`.work_<音声>/transcripts/` に残る**チャンクごとのキャッシュ**を読む。
組み立ての前段で、**ソートを一度も通っていない。**

```
生成順（キャッシュ・ソート未通過）  区間 1219  破れ 0  跳躍最大 23.0s  ← 本物
index 順（.speakers.json）        区間 1219  破れ 0  跳躍最大 23.0s  ← artifact
```

**値は一致した。** local にとって `pipeline.py:959` のソートは実質何もしていない
（whisper は時刻順に吐くため）。

> **ただしこれは結果論である。** 一致することは事前には分からなかった。
> **値が正しかったことと、根拠が正しかったことは別である。**

**判定2 はこれで基準線を持てる。** B に破れが出たとき「local では起きないことが
B では起きる」と言える。

### 4.1 チャンク順の検証（推論せず実データで）

キャッシュをファイル名の連番で並べてよいかを、**データで確かめた。**
各チャンクの先頭発話の本文を全長の作業ファイルから探し、累積オフセットと突き合わせた。

```
chunk_0000 期待    0.0s / 実位置    0.0s / 差 0.0s  OK
chunk_0001 期待  420.0s / 実位置  420.0s / 差 0.0s  OK
   …
chunk_0009 期待 3780.0s / 実位置 3780.0s / 差 0.0s  OK

合致 10/10   累積長 4036.9s（音声 4036s）
```

**ファイル名の連番＝時間順**が確定した。`split_audio()` が
`sorted(glob("chunk_*.m4a"))` を返し、`pipeline.py:807` が同じ順で長さを積み上げるのと一致する。

**系列の取り違えに注意。** 同じ音声に 2 系列のキャッシュが残っていた。

```
10 本  local.ca1fb4d464e99c16.c420.small.v1.json              ← .premerge.speakers.json に対応
 3 本  local.ca1fb4d464e99c16.c420.small.int8_float16.p1.v1.json ← 別の実行（部分）
```

## 6. 閾値による棄却率（実測）

```
エンジン                総区間   本文が短くて測れない        測れる候補
local                   1219        618 (50.7%)             601
A_gemini-2.5-flash        87         38 (43.7%)              49
small_cut                117         47 (40.2%)              70
turbo                    114         30 (26.3%)              84
atrain                  2197       1787 (81.3%)             410
notta                    704        138 (19.6%)             566
```

**エンジンによって 19.6%〜81.3% と大きく違う。** 棄却されるかは区間の刻み方で決まるので、
**細かく刻むエンジンほど落ちる。****測れる標本の性質がエンジンごとに違う。**

`LOCATE_MIN_CHARS = 12` は**そのままとする。**
下げると誤マッチが増える方向で、判定2 が捕まえたいのは
まさに「短い本文が遠くの同じ語に当たる」現象である。
**物差し側で同じ誤りを起こしたら測定にならない。**

**判定2 の報告には棄却率を必ず併記する。**
B が細かく刻んで棄却率が高く出るなら、**それ自体が判定材料である。**

## 7. 暫定の測定値（物差し = `local_asr` 由来・要差し替え）

**この節の数字は暫定である。** align の全長実行が終わっていないため、
チャンクキャッシュに残る `local_asr` 由来の単語時刻（11,990 語・被覆 1.000）を
物差しにしている。**align に差し替えて測り直すこと。**

```
エンジン                測れた   測れず    中央   p90(主)   最大(上限)
local(生成順)             556     663    0.00     0.00        0.20   ← 判定に使わない
A_gemini-2.5-flash         25      62    0.68     9.02       30.34
atrain                    295    1902    0.30     1.09     3192.77   ← 最大は偽マッチ
notta                     305     399    0.37     2.25       60.95

棄却の理由:
  local       {'本文が短い': 618, '本文が曖昧': 35, '位置が割れる': 10}
  A           {'本文が短い': 38, '位置が割れる': 19, '被覆率が低い': 5}
  atrain      {'本文が短い': 1787, '位置が割れる': 87, '本文が曖昧': 19, '被覆率が低い': 9}
  notta       {'本文が短い': 138, '位置が割れる': 180, '被覆率が低い': 78}
```

**注意（再掲）**: local の 0.00 は物差しが同じ ASR だからで、判定に使わない。
最大値は上限で、偽マッチを含む。

### 7.1 相関が指標として機能している

```
A_gemini-2.5-flash  0.99   ← 最高
small_cut           0.95
turbo               0.91
local               0.90
atrain              0.86
notta               0.84
```

**A が 0.99 で最高。** A は `redistribute_times()` の文字数按分を通っているので、
文字数と区間長がほぼ完全に比例する。**指標が狙った signature を捉えている。**

### 7.2 帯モードの出力は打ち切りと跳躍を読まない

帯 4 本を繋いだ SRT に全長を分母として当てると、カバー率 0.877 で全部
「打ち切りの疑い」になり、跳躍も帯の間隔 1260 秒がそのまま出る。
**どちらも切れても壊れてもいない。** `report_timing.py --bands` で判定を抑止する。

## 9. 別件で見つけたもの（スパイクとは独立）

**`.gitignore` に `.work_` が無い。**

製品は出力先に `.work_<音声名>/` を作り、音声チャンク・転写キャッシュ・単語時刻・
話者分離の結果を置く。`_tmp/` はあるが `.work_` は拾えない。
**出力先をリポジトリ内に指定した瞬間に、音声も作業ファイルも追跡対象になる。**
`models/`（510MB）を巻き込みかけたのと同じ形で、**実害が出るまで気づかない。**

直すのは 1 行（`.work_*/`）。**スパイクとは独立した 1 コミットで行うこと。**
`HANDOFF.md` にも同じ内容を残す予定（`main` のファイルなので、スパイクが一段落してから）。

今回の実行ではキャッシュ先が `C:\dev\01\test-audio\.work_01+02edited\`（リポジトリ外）
だったため、実害は出ていない。
