## 0. この測定で何を決めるのか

| 比較 | 何が分かるか |
| --- | --- |
| 測定1 対 測定2 | **出力先の差**（Google ドライブ 対 ローカルディスク） |
| 測定2 対 測定3 | **モデルの差**（標準 small 対 高精度 large-v3） |
| 各条件の 3 回 | **揺れの幅**。上の 2 つの差が、揺れを超えているかを判定する |

**揺れの幅が分からないと、差が実在するか判定できません。** 測定1が12分、測定2が17分でも、
同じ条件で3回回して12分〜18分に散らばるなら、その差は揺れの中に埋もれています。

揺れの原因は既知です（設計書 §9.5.7・温度の引き直しによる乱数）。**揺れること自体は
不具合ではありません。** 幅を知るために測ります。

### 1-2. キャッシュ削除のスクリプト（実装済み）

#### 消すもの・退避するもの・残すもの

| | 対象 | なぜ |
| --- | --- | --- |
| **消す** | `transcripts/` | 転写のキャッシュ。**これが本体。**残ると転写が 0 秒になる |
| **消す** | `diarize/` | **話者分離もキャッシュされる**（`diarize.py` の `load_turns`）。残ると話者分離が数秒で終わる |
| **消す** | `inspect/` | 聴く順番。作り直せる派生データ |
| **退避** | `<音声名>.speakers.json` | **消さずに** `.YYYYMMDD-HHMMSS.bak.json` へ改名。残すと前回の割当を引き継いでしまう |
| **残す** | `chunks/` | `split_audio` が**毎回消して分割し直す**。触らないほうが「分割」の所要が正しく測れる |
| **残す** | `timings.jsonl` | **追記なので消さない。**比較したいのはここ |

#### ★ `diarize/` を消す理由

**当初の要件（`transcripts/` だけ）では、この測定の目的が果たせませんでした。**

話者分離の結果は `.work_<名前>/diarize/turns.<指紋>.….json` にキャッシュされ、
2 回目以降は `load_turns` が拾って**数秒で終わります**。

**今回いちばん見たいのは話者分離の揺れ**（前回 8 分対 13 分）です。
`diarize/` を消さないと、2 回目・3 回目の話者分離が測れず、
**揺れの幅を出すという測定の目的そのものが崩れます。**

#### 動作

- 出力先のフォルダを引数で受け取る（**存在しなければエラーで止まる**。打ち間違い対策）
- **何をするかを先に全部出してから、確認を取る**（`--yes` で省ける）
- **消したあとに数え直して**、残っていれば失敗として報告する
- 2 回目に実行すると「消すものがありません」と出る
  → **消し忘れと消しすぎの両方が分かる**

**消し忘れると 2 回目以降がキャッシュから復元され、転写も話者分離もやり直しません。**
処理時間が大幅に短くなり、しかも数字は出るので気づけません。

### 1-3. ログの保存（当初は手作業 → 自動に変更・2026-08-31）

#### 当初の決定（採用しなかった）

7 回ぶんのログ欄を人が全選択・コピーして、`ログ26-08-31\測定1-1.txt` …
のように 1 箇所へ集める、と決めていた。理由は「G ドライブに置くと同期で
クラウドへ上がる」「2 箇所に分かれると集計で取りこぼす」の 2 つ。

#### なぜ変えたか

**7 回のうち 1 回でもコピーを忘れると、その回は捨てて回し直しになる。**
1 回 17〜32 分で、しかも忘れたことに気づくのはアプリを閉じたあと
（画面のログはそこで消えるので、取り返しがつかない）。

**そもそもログは測定のためだけのものではない。** この製品は「誰が確認したか」を
✓ と △ で残しているのに、**機械が何をしたかは残していなかった。**
利用者も、昨日の処理で何が起きたかを後から見られない。

#### 実装（`StageTimer.tee`・pipeline.py）

```
<出力先>\.work_<音声名>\run-YYYYMMDD-HHMMSS.log
```

- 名前の日時は `timings.jsonl` の `started_at` と**同じ値**から作る
- さらに `timings.jsonl` の **`log` の項に、その名前を書く**。
  突き合わせを名前の推測に頼らせない
- 包むのは**1 行目より前**。あとにすると冒頭（作業ファイル・処理経路・音声長）が抜ける
- **書けなくても処理は止めない。**ログが残らないことで転写を捨てるのは割に合わない

#### ログにしか無いもの

| | どこにあるか |
| --- | --- |
| 段階ごとの所要時間 | `timings.jsonl`（機械で読める） |
| 区間の総数・クラスタ・音声指紋 | 作業ファイル |
| **転写の暴走の検出** | **ログだけ**（`local_asr.py` が `on_log` に流すだけ） |
| **チャンクごとの区間数（マージ前）** | **ログだけ**。作業ファイルにあるのはマージ後で別の数字（実測: 1088 対 799） |

#### 当初の懸念はどうなったか

- **「G ドライブに置くと同期される」→ そのとおりになる。**
  ただしこの測定は**作業ファイル（本文すべて）と音声チャンクを元から G1 に置く。**
  ログだけが新たに外へ出るわけではない。測定後に G1 のフォルダごと消す
- **「2 箇所に分かれると取りこぼす」→ 集計が機械で読むので当たらない。**
  人が集めるから取りこぼしたのであって、3 つの出力先を順に読むぶんには落ちない
- **新しい懸念: 同期の最中にファイルが掴まれると、その回のログが途中で切れる。**
  追記に失敗したら諦める作りなので、処理は止まらず**ログだけが短くなる。**
  集計で「合計の行が無い回」として出るので気づける

**この時点では作業を止めます。** 測定の実行は人間が行います。

### 1-4.（測定後）集計と docx 作成

7 回が終わったと聞いてから着手する。**ログは渡されない。**
3 つの出力先の `.work_01+02edited\` から `run-*.log` と `timings.jsonl` を
読む（`timings.jsonl` の `log` の項で 1 対 1 に対応が付く）。出力先:

```
C:\dev\whosaid-editor-testdata\測定結果26-08-31-<終了時刻>.docx
```

まとめる内容:

- **揺れの幅** — 同一条件3回で、所要時間・区間数・声のまとまりの数がどれだけ動くか
- **★ 1回目が「起動後の最初の実行」だったことを明記する** — 下の専用の節を参照
- **★ 実行順に並べた表** — **1回目から7回目まで、測った順に所要時間を並べる。**
  時間とともに遅くなる傾向（機械が温まる・サーマルスロットリング）があるかが
  ここで見える。**交互にした意味は、この表で効く**——傾向があるなら、
  出力先ごとの平均だけを見ても判定を誤る
- **測定1 対 測定2** — 出力先の差。**揺れの幅を超えているかどうかを明記する**
- **測定2 対 測定3** — モデルの差
- **チャンクごとの区間数の表** — 揺れがどのチャンクに出るか（§9.5.7 は「転写が苦しい
  ところだけ揺れる」としている。実測がそれと一致するか）
- **「転写の暴走」の検出** — 何回目のどのチャンクで出たか、直ったか元のままか

#### ★ 1回目は「冷えた回」——しかも必ず G に当たる（2026-08-31・結果を見る前に決めた）

実行順は `G1 → C2 → G1 → C2 → G1 → C2 → C3` なので、**1回目は必ず G。**
交互にしても、**冷えた回が G に当たる偏りは解消しない。**

**まず、何が冷えているのかを切り分ける。**

| | 1回目だけか | どこに乗るか |
| --- | --- | --- |
| faster-whisper のモデルをメモリへ | **いいえ。7回とも起きる** | 転写 |
| cuBLAS の DLL 読み込み | **いいえ。7回とも起きる** | 転写 |
| 話者分離のモデル読み込み | **いいえ。7回とも起きる** | 話者分離 |
| **OS のファイルキャッシュ** | **はい。1回目だけ空** | 転写・話者分離・音声の確認・分割 |

**各回でアプリを起動し直す手順（ステップ2 で起動・ステップ5 で閉じる）なので、
プロセス内の読み込みは 7 回とも起きる。**偏るのは **OS のファイルキャッシュだけ**
——モデルのファイル、cuBLAS の DLL、67 分の音声を、1回目はディスクから、
2回目以降はメモリから読む。

**ただし「冷えていた」と断定はできない。**確かめる手立てが無いうえ、
**12:09 のビルドが `dist\` を 1.1GB 書き直している**ので、書き込み直後のページが
残っていた可能性もある（前夜の 3 回からは 10 時間空いている）。
**「冷えていた可能性がある回」として扱い、断定して書かないこと。**

**偏りの向きを明記すること。冷えた回は遅くなるので、この偏りは G に不利。**

- **G が C より速いという結果が出たら** → 偏りに逆らって出た結果。**そのぶん強い**
- **G が C より遅いという結果が出たら** → **冷えのせいかどうか分けられない。**
  そう書くこと。出力先の差だと書いてはいけない

**見当（前夜の 3 回から。今回の結果を見る前に書いている）:**
1本目 C2 の転写が 3分51秒、3本目 G1 の転写が 3分13秒で、差は 38 秒。
**冷えの効きは分ではなく秒の単位と見込む。**一方、話者分離の揺れは 8分06秒 対
13分14秒 で 5 分。**冷えは、測ろうとしている揺れより小さい可能性が高い。**
この見当が外れたら、それも書くこと。

#### 「突出」の判定基準（結果を見てから決めない）

1回目が突出しているとみなすのは、**次の両方**を満たすとき:

1. 1回目の合計が、他の G 2 本の**両方より大きい**
2. その差が、**他の G 2 本どうしの差（|G2 − G3|）を超える**

あわせて**段階別にも見る。**合計だけで判定しない。冷えが効くのは上の表の
4 段階なので、**そこ以外で突出しているなら、それは起動の冷えではない。**

#### 突出していたときの提案（形も先に決めておく）

**G を 1 本足すことを提案する（8 回目・+約17分）。**
そのとき **1回目は消さない。**「冷 1 本 / 温 3 本」として別に載せ、
G の平均は**温 3 本で出す**。冷の 1 本は参考として併記する。

**突出していなければ足さない。**ただし**「1回目は冷えた回だった」ことは
本文に必ず書く**——足さなかった理由も含めて。書かずに済ませない。

**1回目をやり直した場合、その回はもう冷えていない。**やり直しがあったら
この節の判定は使えないので、そう書くこと。


#### ★ 6回目の前に登録した予測（2026-08-31 17:25・6回目は未実行）

5 回終えた時点の話者分離: **1回目 12分58秒 / 2回目 9分00秒 / 3回目 11分48秒 /
4回目 8分42秒 / 5回目 8分50秒。**

4 回目までは「G が遅い」に見えたが、**5回目（G）が 8分50秒 で C と並んだ。**
G の 3 本の幅は 8分50秒〜12分58秒 で **4分08秒**。出力先をまたぐ差より広い。
**出力先で決まるとは言えなくなった。**

遅い 2 本（1回目・3回目）は、どちらも**長く空けたあとの回**だった
（1回目はビルド直後、3回目は 1時間17分 空けたあと）。速い 3 本は
直前の回から 5〜19 分。**ただしこれはデータを見てから気づいたので、
それ自体は結論ではない。**

**たまたま 5回目のあと約 2 時間空いた。6回目は C2 なので、
「長く空けたあとの C」という、まだ無い組み合わせになる。**
これは 2 つの説明を分ける:

| 6回目の話者分離 | 支持される説明 |
| --- | --- |
| **9 分前後** | 出力先で決まる（空き時間は効かない） |
| **11〜13 分** | 空き時間で決まる（出力先は効かない） |
| どちらでもない | どちらも支持しない。そう書く |

**どちらに出ても、そう書くこと。**外れたほうを落とさない。
**この節は 6回目を実行する前に書いた。**あとから足したものではない。

**差が揺れの中に埋もれている場合は、そう書くこと。** 「G ドライブのほうが速い」と
書けるのは、3回の幅を超えて速い場合だけです。

**実行順に傾向がある場合も、そう書くこと。** 後半ほど遅いなら、出力先の差は
その傾向を差し引いてから判定します。

**回し直しで順序が崩れた回があれば、それも表に書くこと**（何回目をやり直したか）。
交互にしている意味が薄れるので、判定に効きます。

### 2-3. 7回の順序 — **交互にする**

## 3. 測定中に見ておくとよいこと

**話者分離の時間。** 前回、測定1で8分、測定2で13分と5分違いました。転写の差は1分
だけだったので、ここに出力先の影響が出ている可能性があります。3回ずつ交互に回せば、
揺れか・出力先の差か・実行順の差かが分かります。

> **ただし、話者分離は出力先へほとんど書きません。** 音声の変換は OS の一時
> フォルダ（ローカル）で行い、出力先へ書くのは最後の `turns.….json`
> （**42KB を 1 回**）だけです。**5 分の差を 42KB で作ることはできません。**
> 出力先の差だとすると説明がつかないので、**揺れか実行順の差である可能性が
> 高い**と見ています。交互にするのは、そこを切り分けるためでもあります。

**「転写の暴走」の検出。** 前回、同じ設定なのに片方だけ発火しました。乱数で別の道に
入った実行が繰り返しに嵌まったためです。何回目に出るか、直るか元のままかを記録します。

**Google ドライブの同期。** 測定1 の最中に同期が走ります。次の回を始める前に完了を
待ってください。同期中に次を始めると条件が変わります。
