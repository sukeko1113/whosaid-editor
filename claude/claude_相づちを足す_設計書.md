# whosaid-editor — 相づちを足す（実装設計書 v1.0）

2026-08-17。聴きどころ（自動点検設計書 §15）の三歩目を格上げしたもの。
ユーザーの発意:「会話途中の他人の相づちは QDA にとって重要な要素なので、
ぜひ入れられるように」。

## 0. なぜ作るか（根拠はすべて実測）

- **どの ASR も、会話途中の相づちを書けない。**6 系統 11 構成の測定で、
  人が拾った 33 件のうち Whisper 系は 1〜3 件、最良の Gemini でも 13 件
  （技術方針書 §8-10）。重なった声は 1 本の本文に構造的に入らない。
  **エンジンを待っても解決しない**
- 一方、機械は相づちについて**言葉以外のすべて**を既に持っている:
  どこで（pyannote の turn。重なりも出る）、誰が（turn の話者 → `声A`）、
  どの順で聴くべきか（聴きどころ。**上位 10 件中 8 件で裏づけ済み**・§15.5）
- 欠けているのは言葉だけで、それは人の耳だけが知っている

**形: 機械が時刻と声を用意し、人が言葉を入れる。**v2.0.0 の思想
（AI は候補、人が確定）の相づち版である。

**競合との関係**: aTrain は MAXQDA 出力を持ちながら相づちを落とす
（フィラー保持 23.9%・脱落 2/33）。「やりとりの相づちまで、誰の発話として
検証済みで残る」は測った範囲のどの製品も持っていない。差別化「確認履歴」と
地続き（事業計画 v29）。

**QDA における位置づけ（2026-08-17・ユーザーの指摘）**: 相づちは
「相手の感情の入り具合」を、フィラーは「緊張・プレゼンの習熟度」を示す
指標であり、QDA ではそれ自体が分析の素材になる。つまりこれらを拾うことは
記録の完全性の問題であると同時に、**拾えなければ分析が成立しない**という
分析側の要件でもある。競合（ScribeAssist）はフィラーの自動削除を製品特長と
して掲げており、この用途では構造的に競合しない。

なお**同じ話者のフィラーの脱落**は、本 UI の対象外である（既存の本文編集で
書き足せる。区間が既に在るため）。本 UI が埋めるのは「区間ごと無い」
別人の発話だけ。

## 1. 操作の流れ

```
聴きどころの上位区間を聴く
  → 別の人の声が聞こえたら［＋この声を足す］
  → 小窓: 近くの turn の一覧（時刻と 声B などのラベル）から 1 つ選ぶ
  → 言葉を打つ（「はいはい」）
  → 話者を選ぶ（任意。名簿から）
  → ［入れる］ → 一覧に新しい区間が現れる
```

- turn の一覧に該当が無いとき（分離器も逃した声）のために、
  **時刻を手で打つ欄も残す**（既定値はいま聴いている区間の中央）
- 話者を選んだ場合だけ ✓（§3）。選ばなければ未割当のまま

## 2. データ層 — `Project.add_utterance()`

`split_segment` と同族の Project 操作として実装する。

```
add_utterance(start, end, text, cluster) -> Segment
  - 挿入位置は時間順(start, index)。以降の index を +1
  - reviewed=False / speaker_id=None で作る(話者は呼び出し側が通常の
    割当操作で付ける。付けたときの ✓/△ は既存の意味論に従う)
  - text_edited=True(人が打った本文)
  - time_edited=False(時刻は turn 由来の機械値。人が直したら既存の
    時刻編集がいつも通り立てる)
  - orig_start は post_init が start を入れる(既存挙動)
  - edit_log に {"op": "add_utterance", "orig_start", "start", "end",
    "cluster", "at"} を積む ← §4 の鍵
remove_added_utterance(index) -> None
  - edit_log に add_utterance が残っている区間**だけ**消せる
  - 消したら edit_log に {"op": "remove_added_utterance", ...} を積む
```

**スキーマは増やさない。**「人が足した区間」の識別は edit_log で行う
（`edit_log` は既にあり、再実行でも引き継がれる）。区間へのフラグ追加は
v3 一括移行の原則に反するのでやらない。

**区間の重なりを許す。**相づちは主発言と重なるのが本性なので、追加区間が
既存区間と時間的に重なることを禁止しない。既存機構への影響は §7 で確認する。

**削除は人が足した区間に限る。**短い相づちの自動削除をしない原則
（CLAUDE.md）はそのまま。ここで消せるのは「人がいま足したもの」だけで、
ASR 由来の区間には削除の入口を作らない。

## 3. `reviewed` の意味論（最重要・変えない）

| 状態 | 意味 |
| --- | --- |
| 追加直後（話者未選択） | speaker_id=None / reviewed=False。**✓ は立たない** |
| 小窓で話者まで選んだ | speaker_id=あり / **reviewed=True**。人が耳で聴いて誰の声か決めたので ✓ の定義そのもの |
| あとから通常の割当で付けた | 既存の意味論のまま（聴いて確定＝✓、一括適用＝△） |

機械が ✓ を立てる経路は存在しない。小窓の話者選択は「人が音声を聴いた直後に
自分で選ぶ」操作なので、✓ の定義（人が耳で聴いて確定）を満たす。

## 4. 再実行での引き継ぎ（一番危ない箇所）

**何もしないと、人が足した区間は再実行で他人の区間を壊す。**

`_carry_over_assignments` は orig_start ±2.0 秒で旧区間と再生成区間を
突き合わせる。人が足した区間の orig_start は独自の値（例: 主区間の中ほど）
なので、次のどちらかが起きる。

- **近くの無関係な再生成区間に誤って照合される。**time_edited を立てて
  いれば「旧側が正しい」枝に入り、**その区間を置き換えて消す**
  （1 秒の相づちが 8 秒の発言を上書きする）
- **どこにも当たらず、相づちのほうが黙って捨てられる**

**実測（2026-08-17・対策前）で起きたのは後者。**8 秒の区間の中ほど
（104.0 秒）に足した相づちが、100.0 秒の区間と 4 秒離れているため
どの再生成区間にも当たらず、消えた。どちらにせよ人の作業が失われる。

**対策: 人が足した区間は突き合わせから完全に外す。**

```
_carry_over_assignments の先頭で:
  added = edit_log の add_utterance(かつ remove されていない)の orig_start 集合
  旧区間のうち orig_start が added にあるものを退避し、
  ファミリー構築・照合・吸収のどれにも参加させない
最後に:
  退避した区間を時間順の位置へ挿し込み、index を振り直す
```

- 照合しない → 他人の区間を置き換えない
- 吸収範囲（absorb）にも入れない → 相づちの時間幅の内側で始まる再生成区間が
  静かに消える事故を防ぐ
- 音声が別物（`_is_same_audio` 不成立）なら従来どおり全部作り直し。
  人が足した区間も引き継がない（別の録音に別の会議の相づちが乗るため）

## 5. 画面（assign_gui）

### 5.0 実機で作り直した（2026-08-18）— 時刻ではなく本文の位置で入れる

初版は「turn の一覧から時刻を選び、言葉を打つ」形だった。**実機で使えなかった。**

> 「どこで入れたらいいのかがわかりずらい。小窓には、元の文が出ていないので、
> その文に直接挿入（色を変えるなどでわかるように）できるようにできないと、
> 実質挿入は不可能である。」

**前提が間違っていた。**聴いているときの頭の中は「1504.2 秒」ではなく
**「『ながら』と『けれども』の間」**である。時刻は結果であって入力ではない。

作り直した形:

- **小窓に区間の本文を出し、入れたい場所をクリックしてもらう。**
  挿入位置は色（`#FFE082`）と「…ながら【ここ】けれども…」の文字で示す
- 時刻はクリック位置から**文字数按分**で見積もる。`redistribute_times` が
  既に置いている仮定と同じ。**目安であり実測ではない**ので `time_edited` は
  立てない（ユーザー承認済み・2026-08-18）
- 話者分離の候補があれば「声の候補に合わせる」で実測時刻に寄せられる。
  本文の位置を動かしたら候補合わせは自動で外れる
- 本文欄は打鍵を握りつぶして書き換えを防ぐが、**移動キーは通す**
  （通さないとカーソルで位置を選べない）
- **一覧でも足した発話が分かるようにする。**背景色（`#FFF3E0`）に加えて
  本文の頭に「＋」を付ける——色だけだと印刷や色覚の条件で消える

### 5.0.2 3 度目の作り直し — ①②③を積む（2026-08-18・ユーザーの提案）

> 「『入る発話』に窓を作り、複数入れられるようにする。最初に挿入する発話を
> ①とし、それを基の文に入れておけばどこに挿入したらわかると思うし、①の次は
> ②を作成し、同様に基の文に入れる。こうすれば、何回も窓を開かなくても一度で
> 済む」

**指摘は 2 つあり、どちらも設計の穴だった。**

1. **挿入位置が分からなくなる**——入れた後、本文のどこに割り込んだのかが
   画面から消える
2. **複数入れられない**——25:02 の区間には相づちが 3 つあるのに、
   ［入れる］で小窓が閉じるので 3 回開き直すことになる

**採用した形**（ユーザーの提案そのもの）:

- 位置をクリック → 言葉を打つ → ［＋ この位置に足す］で**積む**
- 積んだものは**本文の中に ①②③ として出る。**どこに何を入れたかが一目で分かる
- 一覧に「① 「えー」 山本 25:02.8」と並ぶ。［直す］［消す］も付ける
- 最後に［まとめて入れる（3 件）］で一度に作る
- **印は本文の並び順に振り直す。**あとから前の位置に足しても番号が合う

**印は表示だけのもので、区間の本文には入れない。**言われていない文字を記録に
混ぜないため（逐語の原則）。表示位置と本文の文字位置は `_map` で相互に変換する。

**残る論点（未決）**: Word 出力では、足した発話は時刻順に並ぶので
「長い発言 → 相づち」の順になる。実際は発言の途中に割り込んでいる。
記録として正しく読ませるには **(A) 元の区間を分割して間に挟む**
**(B) 本文に印を残す** のどちらかが要るが、**まだ決めていない。**

### 5.0.3 開き直して直せること（4 度目・2026-08-18）

> 「複数入れ終わったら、左の画面に挿入したものが現れるのはいいんだけれど、
> それを修正しようとすると、最初の画面が出てきても、挿入されたものは
> なくなっています」

一覧で選べば本文や話者は直せるが、**「本文のどの位置か」は小窓でしか
決められない**のに、小窓は空から始まっていた。位置を直す道が無かった。

- 小窓を開くとき、**その区間に足したものを読み込んで①②…として積んでおく**
  （「この区間のもの」＝時刻が区間の範囲に入るもの。位置は時刻から逆算）
- ボタンは［この N 件にする］になる。**押すと、開いたときにあったものを
  いったん全部消してから作り直す。**差分を追うより確実で、edit_log にも
  経緯が残る
- **空にして押せば全部消える**（開いたときに既にあったなら、消したいという
  意思なので通す）。［やめる］なら何も変えない——`applied` で区別する

### 5.0.4 見つかった別の不具合 — 本文欄の書き戻し

上の検査を書いていて、**`_commit_text` が `current` の区間に無条件で
書き戻す**ことが分かった。`current` を直接動かした直後に呼ばれると、
**別の区間へ前の本文を上書きする。**

いまの経路では `goto()` が必ず本文欄を更新するので実害は出ていなかったが、
踏める余地は塞いだ——**本文欄がどの区間のものかを覚え、食い違うときは
書かない**（`_body_index`）。

### 5.0.5 Word の並び — 割るのは出力のときだけ（2026-08-18・§5.0.2 の未決を決着）

実機で Word 出力を見て、未決だった論点が具体的な不具合として現れた。

> 「５つの発言を挿入しましたが、ワードには全部一つになっていて、
> どこに挿入されているのかがわかりません」

```
[00:25:03] 【西村】私からはお願いだけなんですけれども、…（14.5 秒ぶん全部）
[00:25:04] 【山本】あ、はいはいはいええはいはい      ← 5 件がひとまとまり
```

原因は 2 つ重なっていた。

1. 足した発話は元の区間（25:03〜25:17）より後の時刻に並ぶので、
   **長い発言が終わったあとにまとめて出る**
2. `_merge_runs` が**同じ話者の連続区間を 1 段落にまとめる**ので、
   5 件が 1 つの文字列になる

**採った案: 区間は割らない。割るのは Word に出すときだけ。**

- `add_utterance` が `cut`（元の本文のどこに割り込んだか）と
  `parent_orig`（どの区間か）を `edit_log` に残す
- `_merge_runs` が出力を組み立てるとき、その位置で本文を切って間に挟む

**いったん「データ側で区間を割る」実装を作ったが、撤回した。**割ると
§5.0.3 で直したばかりの問題が別の形で再発する——**直そうとして開き直しても、
割れた本文からは元の姿を復元できない。**割り込みは表示の都合であって、
記録の構造ではない、と考えるほうが筋が通る。

副次的な利点として、**元の区間の `reviewed` が保たれる**（割ると断片ごとに
確認状態を持ち直すことになる）。

### 5.0.1 聴く仕掛け（同じ指摘より）

**追記（2026-08-18・2 度目の指摘）**: 初版の小窓は［この辺を聴く］しか無く、
**挿入位置の前後 1.5 秒しか鳴らなかった。**

> 「先ほどは、この区間の音声が全部聞こえたのに、今回は
> 『私からはお願いいただきながらけれども、』で切れてしまいます」

**順序が逆だった。**相づちの場所を見つけるために全体を聴きたいのに、
位置を決めないと聴けない作りになっていた。

- **［▶ 全部聴く］を足した。**区間の頭から終わりまで鳴らす
- **鳴らしながら本文の現在位置を光らせる**（水色。挿入位置の橙とは別の色）。
  聞こえた瞬間にその辺りをクリックできる。位置は経過時間×速度からの推定で、
  ffplay は再生位置を問い合わせられないため。数十ミリ秒の誤差はこの用途では
  問題にならない
- ［▶ この辺だけ］は残す（入れる場所を決めたあとの確認用）
- 一時停止すると追従も止まるが、**印は残す**（どこで止めたか見えるように）


> 「会話音声もスローにする機能とポーズ機能があったほうがいい」

- 小窓に速さの選択を置き、**0.5x / 0.65x を足した**（`DIALOG_SPEEDS`）。
  本体の下限は 0.8x だが、**相づちは短くて速いので足りない**
- **一時停止を作った**（`player.pause()` / `resume()`）。ffplay は外部プロセスで
  再生位置を問い合わせられないので、**開始からの経過時間に速度を掛け戻して
  推定する。**相づちの聴き取りでは、止めた辺りから鳴り直せれば足りる
- 前後にどれだけ余分に鳴らすか（0.8 / 1.5 / 3.0 秒）も選べる



- 右ペインの `row_edit`（分割・結合の並び）に［＋この声を足す］
- 小窓の turn 候補: いまの区間の前後 `WINDOW_SECONDS`（3 秒）に重なる turn。
  各行 =「開始〜終了 ・ 声B」。声の記号は `_speaker_letters`（出現順 A/B/C…）
  で本体と同じ対応にする
- turns の入手: `.work_<名前>/diarize/turns.<指紋>.…json`。
  `num_speakers` は `proj.engine["diarize"]["num_speakers"]` から。
  **turns が無ければ手入力の時刻欄だけの小窓にする**（機能自体は使える）
- 挿入後: `_remap_undo_for_split(index)` と同じ再マップ（挿入位置以降 +1）。
  Ctrl+Z の対象にはしない（分割・結合と同じ扱い。逆操作＝削除ボタンで戻す）
- ［この区間を消す］は edit_log で「人が足した区間」と確認できたときだけ
  活性化する
- **小窓を開く処理は `_ask_utterance()` に分ける。**検査で差し替えるため。
  `wait_window` は本物のウィジェットを要求するので、ダイアログのクラスごと
  差し替える方式では動かない（実際に落ちた）

## 6. 聴きどころとの往復

- 追加された区間には順番（hint）が無い → `match()` で当たらず末尾に並ぶ
  （既存挙動のまま。安全と見せない置き方も既存のまま)
- 将来の「聴いた記録」（あった/なかったボタン）はこの設計の上に足せる:
  ［＋この声を足す］＝「あった」の記録を兼ねる。「なかった」だけ別ボタンが
  要る（本設計の範囲外・次の単位）

## 7. 既存機構への影響（実装時に検査で確かめる）

| 機構 | 想定 | 確認すること |
| --- | --- | --- |
| 再生 | 区間の重なりは元から順不同で鳴らせる | 追加区間を選んで鳴る |
| タイムライン | start 順で描くだけ | 落ちない |
| 時刻点検（inspection） | 追加区間の本文は ASR に無い→照合不能でスキップ | 提案が誤って当たらない |
| 一括適用・候補学習 | cluster が実クラスタなら参加してよい（人が聴いて置いた声ラベルなので汚染ではない） | votes に入ることを確認 |
| Word 出力 | start 順に並ぶ → 相づちが独立した行で出る | 出力に現れる |
| 分割・結合 | 追加区間の分割は不要（短い）。結合は**しない**（重なりを結合すると意味が壊れる）| 追加区間で結合ボタンが出ない/効かない |

## 8. 実装順序（各単位でテストを通し、確認を得てから次へ）

```
1. データ層: add_utterance / remove_added_utterance + edit_log + 検査 ← 完了
2. 引き継ぎ: §4 の退避規則 + 検査(誤照合で他区間が消えないこと) ← 完了
3. 画面: ボタン + 小窓 + 削除 + undo 再マップ + GUI 検査 ← 完了
4. 実データ受け入れ: 3 件目(25:02.8)の相づち 6 個をユーザーが実際に入れ、
   (a) 一覧と Word 出力に現れる (b) 再実行して残る (c) 消して戻せる
```

## 9. 決定済み・要決定

## 10. 次の一手 — 候補の一覧と AI の下書き（2026-08-17・方向を確定）

本書の機能（人が気づいて足す）の次は、**機械が候補を並べ、AI が言葉を下書きし、
人が○×で確定する**形にする。実装前に成立を実測で確かめた。

### 10.1 実測: 隙間だけを切り出して起こすと拾える

区間と区間の隙間（話者分離の turn と重なる＝声のあるところ）を前後 0.35 秒の
余白付きで切り出し、同じエンジン（small）に渡した。

| 帯 | 落ちた発話 | 声のある隙間 | **回収できた** |
|---|---:|---:|---:|
| c-ouchou | 11 | 21 箇所 | 1 |
| d-missitsu | 19 | 21 箇所 | **6** |

**全長のままでは 33 件中 1 件しか出なかったものが、切り出すと拾える。**
「周りの声に埋もれて落ちる」という見立ては正しかった。

### 10.2 同時に判明した制約 — 短いクリップで AI は嘘をつく

```
2420.4-2421.1 (0.7秒)  ご視聴ありがとうございました
2424.6-2425.1 (0.5秒)  ご視聴ありがとうございました
3484.6-3485.9 (1.2秒)  いらっしゃいませ
3474.4-3475.4 (0.9秒)  でーん
```

Whisper が短い・静かな音声に対して作り話をする既知の癖。候補 21 箇所のうち
本物は 6 件で、**適合率は 4 割前後。**

**したがって: AI の出力は下書きに限り、自動では絶対に入れない。**
本書 §3（機械が ✓ を立てる経路は作らない）と同じ線であり、
この実測がその線の必要性を裏づけた。

### 10.3 候補の定義を実測で入れ替えた（2026-08-19）

**作る前に天井を測ったら、①の設計が成り立たないことが分かった。**
`tools/report_candidates.py` で、逐語正解 4 帯の脱落 34 件と、キャッシュ済みの
turn・区間を突き合わせた（再転写も再分離もしていない）。

```
turn に覆われている              34/34   100%
turn はあるが本文の区間が無い      0/34     0%   ← すきまはゼロ
turn にも入らない                 0/34     0%
```

**「声はあるのに本文が無い箇所」は 1 件も無い。**34 件すべてが
**既存の区間の内側**にある。理由は明白で、**脱落は他人の発言の最中に
埋もれている。**25:03 の区間は 14.5 秒あり、相づち 5 件はその中にある。
区間は存在するので「すきま」にならない。

**したがって「turn と区間の差集合」では何も拾えない。**

#### 入れ替えた定義

**候補＝区間の中に、その区間の主たる話者と違う声がある箇所。**
（主たる話者は、区間に最も長く重なる turn の話者。重なり 0.2 秒以上を数える）

| | 元の設計 | 入れ替えた定義 |
|---|---|---|
| 再現 | **0/34** | **31/34（91% ±10 点）** |
| 適合 | — | **35/51（69% ±13 点）** |
| 作業量 | — | 4 帯 8 分で候補 **51 個** |

既存の「聴きどころ」（`listen_order`）は高スコア 96 区間で **9/34** しか
指せない。**同じデータで明確に上回る。**

適合率 69% は、§10.2 で測った AI の下書きの 4 割前後を大きく上回る。
空振り 16 個を捨てる手間で 31 件を拾えるなら見合う。

#### 効かなかった絞り込み

「その声が別の区間として本文になっているなら脱落ではない」——筋は通ると
思って試したが、**候補 33 個・適合 64%・再現 20/34** となり、
**適合率が下がって再現率が 31→20 に落ちた。**外した 18 個に本物が多く
混ざっていた。**採らない。**素の 51 個のほうが優れている。

#### 数字の扱い（誇張しない）

- **±13 点・±10 点**ある。音声 1 本・34 件ぶん。確定値として書かない
- 空振り 16 個のうち **12 個は理由を説明できていない**
- 外れた 3 件のうち 1 件は `overlap: true` で**原理的に取れない**
- **閾値は一度もいじっていない。**重なり 0.2 秒・窓 3 秒とも既定のまま、
  一度で出た数字（正解は音声 1 本しかないので、合わせこむとこの音声に
  当てるだけの数字になる）

### 10.3.1 作る順序

| # | 機能 | 根拠 | 実装の重さ |
|---|---|---|---|
| ① | **候補の一覧**（区間の中の、別の声の位置を並べる） | §10.3。再現 31/34・適合 35/51 | 軽い（turn と区間の重なり） |
| ② | **AI の下書き**（候補ごとに切り出して起こす） | §10.1。回収 6/19 | 中（クリップ生成＋転写） |
| ③ | 話者の推定 | turn の声ラベル → 既存の候補学習（suggest.py）を繋ぐ | 軽い |
| ④ | ○×の記録で並べ替えを学習 | ①②の使用記録が溜まってから | 後回し |

①は「相づちを足す」小窓の入口になる。候補を選ぶと、その位置が `cut` として
そのまま渡せる（§5.0.5 で位置を記録する形にしてあるため）。

### 10.3.2 画面 — 行も幅も増やさない（2026-08-19）

右ペインは §5.0 の作り直しで 4 行に詰め、**高さも幅も余裕が無い。**

- 行を増やす → 下の［保存］が隠れる（実機の指摘・2026-08-18）
- 幅は **要 571 / 幅 592 で余裕 21px**。何かを足すと右端が切れる

そこで**既存の「＋この声を足す」の行に相乗りし、説明文と候補を排他にした。**
同時には出さないので、この行の幅は「どちらか広いほう」で決まる。

```
候補が無いとき  [＋この声を足す...] [この区間を消す] （本文に無い発話を、位置を指して足します）
候補があるとき  [＋この声を足す...] [この区間を消す] 別の声: [25:04 声B ▾] [ここから] [×] 空振りあり
```

**幅は実測で詰めた**（右ペイン 520px に対し 説明 420 / 候補 502）。
途中で 809 → 562 → 532 → 502 と削っている。削ったもの:

- 元の説明文は **360px** あり、**そもそも収まっていなかった**（225px に短縮）
- 「N 件・空振りあり」→「空振りあり」。**件数は選択肢の一覧で分かるが、
  「空振りあり」は落とさない**——3 割は外れるので、書かないと
  「候補＝脱落」と読まれる

**実機で 1 つ切れていた。**選択肢が `00:00:29 声!` と途切れた（幅を 502px に
収めるため 10 文字まで削っていた）。幅を広げずに、**時刻の書き方を短くした**
——`00:00:29` → `0:29`、1 時間を超えたら `1:05:30`。先頭の `00:` は 1 時間の
録音では常に同じで情報が無く、［時刻へ飛ぶ］が受け付ける書き方とも揃う。
最長は `1:05:30 声B` の 11 文字で、行は 508px に収まる。

絞り込みに「候補のみ(別の声)」を足した。**言い切らない**——
「別の声がある区間 N/710 を出しました(候補 M 箇所)。3 割ほどは空振りです。
候補の無い区間にも取りこぼしはあります。」話者分離を通していない作業
ファイルでは「使えません」と言う（黙って 0 件にしない）。

**× は sidecar に残る。**空振りが 3 割あるので、捨てた判断が残らないと
毎回出てきて使えない。

### 10.3.3 もう足した位置と、候補から小窓を開くこと（2026-08-19）

#### 「済」は隠さずに印を付ける

実機で 25:03 の区間を見たら、**もう足した 5 件の位置に候補が残っていて
煩わしかった。**ただし**隠さない**——隠すと「候補が無い＝やることが無い」
と読まれ、この道具の性格（印が無い＝安全ではない）と食い違う。

- 選択肢に **「済」** を付け、**後ろに回す**（`済25:04 声B`）
- 注記を `残N・空振りあり` にする
- **待ち行列（絞り込み「候補のみ」）からは、全部済んだ区間だけ外す。**
  候補そのものは残っており、すべて表示にすれば「済」付きで見える

時間の余裕は **1.0 秒**。足した発話の時刻は小窓の文字数按分から決まるので
turn の開始とはずれる。**実データで 0.69〜1.07 秒**ずれていた。
広げると別の相づちまで「済」にしてしまうので、黙って変えないよう検査を置いた。

実データでの効き: 候補 319 のうち **6 件が「済」**、待ち行列は
**234 → 231 区間**。25:03 の区間は 4 件すべてが「済」になって外れた。

#### ［ここから］は位置だけ渡す。**話者は渡さない**

候補が持っているのは turn の**声**（声B）であって、名簿の誰かではない。
機械が選んだ話者のまま［＋この位置に足す］が押されると、
**`reviewed=True`（✓）が機械の判断で立つ。**
✓ は「人が聴いて決めた」という意味なので、そこは譲れない（CLAUDE.md）。

- カーソルは候補の時刻から**文字数按分の逆算**で立てる。**目安であって実測
  ではない**ので、案内文にもそう書く（「位置は目安なので、聴いて直してください」）
- どの声だったかは案内文で伝えるだけ（「候補: 25:04 に声Bが聞こえます」）
- 話者の欄は「（決めない）」のまま

#### 名前の衝突に注意

`assign_gui` には既に**話者の候補**（`suggest.py` の `self._candidates` /
`_rebuild_candidates`）がある。声の候補はすべて `_voice_` を付けて分けた。
**一括置換で話者側を壊しかけた**ので、触るときは必ず区別すること。

#### 検査

幅の検査は**見えている部品だけ**を数える（`winfo_ismapped`）。排他にした
2 つを両方足すと実際より広く見積もり、通らなくなる。**候補を出した状態でも
収まること**を別に確かめている。

### 10.4 到達点の見込み（誇張しない）

- 隙間の切り出しで回収できるのは、密な帯で **19 件中 6 件**
- **重なった声は切り出しても取り出せない**（33 件中 1 件がそれ）
- それでも「人が 2 分を聴き直して探す」より速い。**候補 21 箇所を○×で流す**形になる

### 10.5 競合が提供できない理由（事業計画へ）

1. **3 つの独立した情報源が 1 つのデータの上に要る**——音声認識（何と言ったか）・
   話者分離（いつ誰が）・確認履歴（どこを人が確かめたか）。転写サービスは
   1 番目だけを売っており、2 番目を足しても 3 番目の器が無い
2. **「確認済み」の概念が製品に無い**——人が足した相づちと AI の出力が混ざったとき、
   どちらがどちらか区別できない記録になる
3. **逐語性を捨てる設計を選んでいる**——ScribeAssist はフィラーの自動削除を
   製品特長として掲げており、そこから逐語へ戻る道が無い

## 11. 出力の表記法 — 標準を調べて 2 通りから選べるようにする（2026-08-18）

§5.0.5 で「割るのは Word に出すときだけ」と決めたが、**割った結果をどう書くか**
には触れていなかった。ユーザーの問い「標準的な反訳の表記法で、挿入の記載方法などが
あるのですか」を受けて調べたところ、**規定が存在した。**しかも我々の判断と同じ形
だった。以下は調査の結果と、そこから決めたことである。

### 11.1 調べて分かったこと

**(1) BTSJ（基本的な文字化の原則・宇佐美まゆみ・2019 年改訂版）**

日本語会話研究の事実上の標準。**この問題そのものを開発動機に挙げている。**

> 相手の発話に重なる、短く、特別な意味を持たないあいづちは、相手の発話中の
> 最も近い部分に、( ) にくくって入れる（3.2.3 周辺言語情報 (1)）

```
例49  A  わたしは、あの、小学部中学部にいたん(ふうん)ですけれども。
例13  A  えーと生まれたのが文京区で(はいはい)、でー幼稚園の(うん)年長の(うん)ときに,,
```

BTSJ は**行内に埋め込む形と、行を分ける形を使い分けている。**

| 入ったもの | 書き方 |
|---|---|
| 短く特別な意味を持たないあいづち・重なった笑い | 行内に `( )`（改行しない）。笑いは `(<笑い>)` |
| 1 発話文と認定されるもの（返答・意味のある発話） | 行を分ける |

行を分けたときは、**元の発話がまだ終わっていないことを行末の `,,` で示し**、
同じ発話文番号に `-1` `-2` を振って、後から一続きだったと分かるようにする。

```
1     A  もう、もろ駅前商店街。
2-1   B  北浦とか、もっと、それよりもっと,,
3     A  そうそうそうそう。
2-2   B  駅前。
```

他に、割り込みで発話が終わった場合は `【【 】】`、同時発話は双方を `< >` で囲み
重ねられた側に `{<}`・重ねた側に `{>}`。BTSJ は**「重ねられた記号のあとに、
重なっていない内容を続けて書く」ことを誤りとして明示している**（例 47）。
理由は「時間的整合性を欠く」から。**本書 §11.3 の時刻の扱いは、この指摘と同じ線。**

**(2) 会話分析（Jefferson 式）**

国際標準。重なりは `[` `]` で、**必ず行を分け、開始位置を縦に揃える。**
切れ目ない接続は `=`、間は `(0.5)`。日本語版は『文と発話』の共通転記記号。
BTSJ が「読みやすさ」を取って行内埋め込みを許すのに対し、Jefferson 式は
**位置の正確さ**を取る。

**(3) 商用の反訳実務**

**一般の反訳（裁判提出用を含む）に、挿入の統一規格は無い。**相づちは「ケバ取り」で
消されるのが普通で、残すなら「ケバ付き（素起こし）」を指定する。
ただし会話分析用として明示的に売っている業者はあり、東京反訳は 4 段階に分けている。

- 【A】相づち挿入型 — `Ｑ：7年目ですね。(Ａ：ええ)では、このお仕事について…`
- 【D】統合型 — 相づち＋沈黙秒数＋重なり。重なり始めに `[`

**【A】が話者名を `( )` の中に入れている**点は採用する。BTSJ は 1 対 1 の会話を
想定して話者名を省くが、**本製品が扱うのは多人数の会議で、名前が無いと誰の相づちか
分からない**（誰が言ったかの記録が製品価値そのものである以上、ここは譲れない）。

### 11.2 決めたこと — 2 通りを出力時に選ぶ

データは 1 つのまま、**出し方だけを選ぶ**（§5.0.5 の「割るのは出力のときだけ」の延長）。
同じ作業ファイルから (ア) で反訳書を、(イ) で QDA 用を、続けて出せる。

**(ア) 行を分ける（既定）**

```
[00:25:03] 【西村】私からはお願いだけなんですけれども、,,
[00:25:04] 【山本】あ、はいはいはい
           【西村】十分私立のことなんで、,,
[00:25:08] 【山本】はい
           【西村】あのー何も言わずにお願いして、
```

**(イ) 行に埋め込む**

```
[00:25:03] 【西村】私からはお願いだけなんですけれども、(山本：あ、はいはいはい)
                  十分私立のことなんで、(山本：はい)あのー何も言わずにお願いして、
```

**既定を (ア) にした理由**: 反訳書として第三者が読むのはこちらで、(イ) は本文が
読点だらけになり長い発言では追えなくなる。また (ア) は話者一覧の見え方が
今までと変わらない。

**継続の印に `,,` を使う理由**: 独自記号を作ると外部の研究者に説明できない。
BTSJ にそのままの規定がある以上、それに従う。

### 11.3 分断された後半に時刻を書かない

今の実装では、割られた前半と後半が**どちらも元の区間の開始時刻を持つ。**
そのまま出すと時刻が戻って見える。

```
[00:25:03] 【西村】私からはお願いだけなんですけれども、,,
[00:25:04] 【山本】あ、はいはいはい
[00:25:03] 【西村】十分私立のことなんで、     ← 戻っている
```

**後半の本当の開始時刻は測っていないので、書かない。**測っていないものを
書けば記録として嘘になる。§5.0.5 で相づちの時刻を「目安」と決めたのと同じ理由
であり、BTSJ 例 47 が「時間的整合性を欠く」として退けた書き方とも同じ線である。

### 11.4 凡例を出す（使われたときだけ）

`,,` も `( )` も、**説明が無ければ受け取った人が読めない。**BTSJ は読み手が
研究者であることを前提にできるが、反訳書の読み手はそうではない。

差し込みが 1 件でもあるときに限り、冒頭（出席者一覧の下）に 1 行入れる。

- (ア): `表記について: 発言の末尾の「,,」は、その発言が下の行に続いていることを示します（BTSJ 2.3.2 に準拠）。間の行は、そこに重なって入った別の人の発言です。`
- (イ): `表記について: 本文中の「(氏名：…)」は、その位置に重なって入った別の人の発言です（BTSJ 3.2.3 に準拠）。`

差し込みが無いときは出さない（無関係な説明は記録を汚す）。

**見出しを「凡例」にしない。**検証要約にすでに「凡例」という項目があり
（聴いて確定／まとめて適用の説明）、1 つの文書に同じ見出しが 2 つ並ぶ。
検査を書いていて気付いた。「表記について:」を使う。

### 11.5 採らなかったもの

- **Jefferson 式の桁揃え** — 等幅前提であり Word で崩れる。QDA ソフトが
  読むのも BTSJ 系が主。必要になったら別出力として足す
- **`【【 】】`（割り込みで終わった発話）・`< >{<}`（同時発話）** — これらは
  「どこで重なったか」を人が耳で判定して初めて書ける。本製品はまだ
  その入力手段を持たない（相づちは「どこに入れるか」だけを人が決める形）。
  §10 の候補一覧が入ってから再検討する
- **`(<笑い>)`** — 笑いを区別して入れる手段が小窓に無い。人が `<笑い>` と
  打てば結果的に同じ形にはなる。専用の欄を作るかは実際に困ってから

### 11.7 埋め込みの氏名を短くする（2026-08-18・実データで判明）

実データで (イ) を出したところ、**使いものにならなかった。**

```
私からはお願いだけ(山本学　文科省　高等教育局私学部参事官付　企画官（命）
学校法人経営指導室長：あ、はいはい)なんですけれども、…
```

**6 字の相づちが 40 字の肩書に埋もれる。**5 回入るので、この段落は肩書だけで
200 字になった。

**採った案: 埋め込みのときだけ、最初の空白までを使う。**
「山本学　文科省 高等教育局…」→「山本学」。

- **短くした形が他の人とかぶるなら、その人は短くしない。**取り違えは
  「誰が言ったかの記録」そのものを壊すので、読みやすさより優先する
- 他人の**全名**とぶつかる場合も戻す（「山本」と「山本学」が並ぶ等）
- 空白の無い名前（「吉沢忠一加茂暁星高校同窓会長」）は切りようが無いのでそのまま
- **記録は書き換えない。**【 】のラベルと出席者一覧は全名のまま
- 読み方の説明に「氏名は冒頭の出席者一覧の略記です」を足す

根拠として、東京反訳の会話分析用【A】も `(Ａ：ええ)` と 1 文字にしている。
全名は冒頭の出席者一覧にある。

**同じ問題が (ア) にもある（未解決）。**【 】のラベルも 40 字で、同じ話者の
発言が 60 箇所以上ある。原因は名簿で、`Speaker` は `name` と `note`（役職）を
分けて持てるのに、全部が `name` に入っている。名簿の行に区切り記号が無く、
しかも `企画官（命）` の括弧が途中にあるため `_ROSTER_LINE` が分けられない。

**ここは直さずに残した。**`plan_roster_text`（assign_gui.py）は**名前の一致**で
既存の話者 ID を引き継ぐので、「山本学　文科省…室長」を「山本学」に縮めると
**別人が入って古い方が消えたと判断され、確定済みの割当が外れる。**
名前を変えても ID を保てるようにする（名前一致ではなく行の対応で引き継ぐ）
のが本筋で、確定済みの割当に触れる変更なので独立した単位にする。

### 11.8 名前と企業・役職に分ける（2026-08-18・ユーザーの提案）

§11.7 で「(ア) の【 】も 40 字」を宿題に残した。私は「表示名」という
項目を足す案を出したが、**ユーザーがより良い案を出した。**

> 出席者を、名前、企業・役職なの2つに分けて入力してもらって、
> 表示は名前のみ、または役職も付けるかどうかせんたくしてもらうのはどうですか。

**こちらを採る。**理由は 2 つ。

1. **新しい項目が要らない。**`Speaker` はすでに `name` と `note`(役職)を持ち、
   `display` は `名前(役職)` を返す。**器はもうあり、名簿の中身が全部
   `name` に入っていただけだった。**CLAUDE.md のスキーマの決まりにも触れない
2. **表示名だと同じ情報が 2 か所になる。**片方だけ直したとき食い違う。
   名前と役職に分けておけば、表示は組み立てるだけで済む

| | 中身 |
|---|---|
| 入力 | 左＝**名前**、右＝**企業・役職** |
| 出席者一覧 | **常に 名前＋役職**（記録として全名を残す） |
| 本文の【 】 | **名前のみ / 役職も付ける を選択**（出力設定で） |
| 埋め込みの `( )` | **常に 名前のみ**（本文の中なので長いと意味がない） |

#### 自動での分割は「提案」であって確定ではない

外部には送らない。**名簿は実名の一覧**であり、CLAUDE.md の
「機微情報は明示した Gemini 呼び出し以外に外部送信しない」に照らせば
名簿も同じ扱いにすべきで、既定がローカル転写で API キーも要らないのに
名簿のためだけにキーが要るのは筋が通らない。端末内の規則で提案する。

規則は 3 つ（`suggest_split()`）。

1. 空白があればそこで切る
2. 役職・所属の語が出てきたら、その手前まで。**2 文字以上の語だけを使う**
   ——「市」「村」「部」を入れると「田村」さんが「田」になる
3. **他の人の行にも出てくる 3 字の並びは、個人名ではなく所属**
   ——「加茂暁星」が梅田さんの行にも出るなら、吉沢さんの名前ではない

実データ（9 人）で **8 人が当たる**。外れるのは 1 件。

```
山口京子蓮田 ｜市長      ← 正しくは 山口京子 ／ 蓮田市長
```

**当てにいかない。**「蓮田」は地名だが、規則で取ろうとすると本物の姓を削る
事故が出る（「山田町長」の「山田」が姓なのか地名なのかは字面では決まらない）。
**提案であって確定ではない**ので、外れたぶんは人が直す。

#### 見つけて直した不具合 — 入れ子の括弧

`_ROSTER_LINE` の役職部分が `[^)）]*` だったため、

```
山本学(文科省 高等教育局私学部参事官付 企画官（命）学校法人経営指導室長)
```

は**内側の（命）で切れて行全体が名前になっていた。**分けて入力しても
今のままでは通らない。最初の開き括弧から最後の閉じ括弧までを取るようにした。

#### ID は行が持ち回る（§11.7 の宿題を解消）

`plan_roster_text` は**名前の一致**で既存の話者 ID を引き継いでいた。
「山本学　文科省…室長」を「山本学」に直すと、**別人が入って古い方が消えたと
判断され、確定済みの割当が外れる。**

`plan_roster_rows(proj, [(話者ID, 名前, 役職), …])` を足した。表の各行が
元の ID を覚えているので、名前を直しても並べ替えても保たれる。新しい行は
ID を空にし、渡されなかった ID は削除とみなす。

**名前一致だと壊れることを検査で示してある**（`plan_roster_text` に同じ
入力を与えて `removed` に入ることを確かめる）。その道を選び直したら落ちる。

#### 画面 — 2 列の表（`RosterDialog`）

```
  名前            企業・役職
  [三ツ林      ] [衆議院議員                      ] [×]
  [山本学      ] [文科省　高等教育局私学部参事官付…] [×]

  [行を足す] [名前と役職に自動で分ける]        [OK] [キャンセル]
```

- **［名前と役職に自動で分ける］は、すでに役職が入っている行に触らない。**
  人が入れたものを推測で上書きしない
- 行が話者 ID を持つ。新しい行は ID が空。窓は画面より大きくしない
- **ホイールは表の上にいるときだけ拾う。**`bind_all` を出しっぱなしにすると
  他の窓のホイールまで食う（主画面が同じ轍を踏んでいて、そこの書き方に合わせた）

#### 文字起こし画面も同じ表（`RosterTable`）

小窓と主画面で同じ部品を使う。主画面はそれ自体がスクロールするので、表は
内側にスクロールを持たない（`RosterDialog` 側だけが canvas で包む）。

- ［一覧をまとめて貼り付け...］ — 1 行 1 人で読み、名前と役職に分ける。
  **一覧をメールから貼る使い方を残すため**（表だけにすると貼り込めない）
- 設定と転写経路に渡す形は従来どおり「名前(役職)」1 行 1 人のテキスト。
  **保存の形を変えていない**ので、古い設定もそのまま読める（分かれていない
  行だけ読み込み時に分ける）

**名簿は転写経路に渡すが、外部に出るとは限らない。**`build_prompt` は
`cluster_only=True`（＝「区間ごとに聴いて割り当てる(推奨)」）のとき
**名簿をプロンプトに入れずに返す**（transcribe.py の早期 return）。
名簿が Gemini に渡るのは「AI にすべて任せる(従来方式)」だけで、
ローカル経路では一切外に出ない。自動分割も端末内の規則。

#### 実機で出た事故 — 同じ人が 2 つの ID になる（2026-08-18）

文字起こし画面で名簿を分けてから走らせたところ、**話者が 9 人から 17 人に
増えた。**分けた 9 人が追加され、元の 8 人が残っていた。

原因は `_merge_speakers`（pipeline.py）。

1. **名前だけで照合**していたので「三ツ林衆議院議員」と「三ツ林」は別人
2. さらに「名簿から消えた人も、割当が残っているかもしれないので保持する」
   規則があるため、**古い方も残る**

私が直したのは割当画面側（`plan_roster_rows`）だけで、
**文字起こし画面からの経路は手つかずだった。**

**割当そのものは 1 件も失われていない**（区間は古い ID を指したまま）。
ただし副作用が 1 つあり、`short_labels` が「山本学」に縮めようとすると
**新しく増えた `山本学` とぶつかる**ため、取り違え防止が働いて全名のまま
出た。埋め込みが短くならなかったのはこれ。**規則は正しく働いている。**

**直したこと。**`_merge_speakers` は、名前で見つからないときに
**「名前＋役職をつないで空白を除いた形」でも照合する**。
名前だけの照合を先に試すので、ほかの場合の動きは変わらない。

**すでにそうなったファイルは** `tools/merge_duplicate_speakers.py` で直す。
同一人物の判定は上と同じ「空白を除いた形の一致」だけで、推測はしない。
判定できない組は触らずに報告する。既定は下見で、`--apply` で書き換え、
元のファイルは `.bak` に残す。**`reviewed` は付け替えるだけで触らない。**

#### 出力

`speaker_label(proj, sid, with_role)` に一本化した。出力設定の
「本文の【 】に企業・役職も入れる」で切り替える（既定は名前だけ）。

- **出席者一覧は常に 名前＋役職**。名前だけにしても、誰なのかは冒頭から辿れる
- **埋め込みの `( )` は with_role によらず常に名前だけ。**本文の中なので
  長いと意味がない（§11.7 の実測）
