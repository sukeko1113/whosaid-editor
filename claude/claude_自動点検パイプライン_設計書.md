## 0. 目的と原則

手動修正の 3 工程「**発見 → 操作 → 検証**」のうち、発見と操作案の生成を機械に移し、
**「聴いて確定」だけを人に残す**。

- 点検は**提案のみ**を出す。自動で本体データを書き換えない。
- 提案の適用（承認）は人の操作。適用結果は `reviewed` の意味論（✓=聴いた / △=埋めただけ）を壊さない。
- v1.3→v2.0 の方針転換（AI は候補、人が確定）のタイムライン版・分割版であり、思想は同一。

**経緯（v1.1 追記）**: §9 の「補正を周辺に反映」に相当する線形補間が
`feature/time-interpolation`（93ccee0）として試作されたが、帯ごとにアンカーを 2 点
手動で作る前提の割に埋まる区間が少なく、線形推定の妥当性も実測で揺れたため
**不採用と決定（2026-08-13）**。時刻修正の自動化は本パイプラインに一本化する。
同ブランチはマージ・削除せずアーカイブとして残し、§2.5 の部品のみ移植する。

## 1. 技術選定（決定）

**faster-whisper の `word_timestamps=True` ＋ 自前の文字アンカー照合**を採用する。

| 候補 | 判定 | 理由 |
| --- | --- | --- |
| faster-whisper 単語時刻 + 自前照合 | **採用** | torch 不要（CTranslate2）。CPU int8 で動く。**Day 30 のローカル転写エンジン導入と依存が完全に同一**（新規ランタイム依存ゼロ）。音声デコードは PyAV 内蔵で追加のシステム依存なし |
| stable-ts | 不採用 | GitHub リポジトリが Public archive（開発終了）。torch を外した派生版（whisperless）でも torch/torchaudio 依存が残る |
| WhisperX（wav2vec2 CTC） | 差し替え候補として温存 | 文字レベルで最も高精度だが torch + transformers + 日本語 wav2vec2 モデル（1GB超）を要する。精度不足が実測で判明した場合の交換部品 |

差し替え可能性を保つため、アライナは「音声 → `[{word, start, end}]` のリスト」を返す
**薄いアダプタ**（§2 の `align.py`）に隔離する。`features.extract` を差し替え可能にした v2.0.0 と同じ流儀。

## 2. 全体構成

```
音声 ──┬─→ (既存) Gemini 転写 → 区間列（テキスト・話者記号・推定時刻）
       │
       └─→ align.py: faster-whisper 逐語転写（単語時刻付き）→ words キャッシュ
                 │
                 ▼
        anchor.py: Gemini テキスト × whisper テキストの文字アンカー照合
                 │            （両者は同じ音声の逐語 → 大部分が一致する）
                 ▼
        inspect.py: 提案の生成
           1-3a 時刻提案（実測時刻との差分）
           1-3b 分割候補（区間内の長ポーズ）
           1-3c 結合候補（異記号間・第二段階）
                 │
                 ▼
        sidecar（.work_<名前>/inspect/…）に保存 → GUI の提案一覧 → 人が承認/却下
```

新規モジュール:

| ファイル | 役割 | テスト性 |
| --- | --- | --- |
| `src/align.py` | faster-whisper 呼び出し・モデル管理・words キャッシュ | 統合テストのみ（CI 対象外） |
| `src/anchor.py` | 正規化・アンカー照合・時刻転写・境界再推定 | **純粋関数。テキストとフィクスチャだけで全ユニットテスト可能（モデル不要）** |
| `src/inspect.py` | 点検オーケストレーション・提案生成・sidecar 入出力 | フィクスチャ注入でユニットテスト可能 |

既存への変更は GUI（点検ボタンと提案一覧、§10）と、承認適用時の書き込みのみ。
`transcribe.py` の `redistribute_times()` / `merge_consecutive()` には**手を入れない**
（点検はその出力に対する後段の差分提案。Day 30 のバックエンド層移動とも干渉しない）。

## 3. Step 1-3a — 時刻照合

### 3.1 正規化と照合（v1.2 改訂: 全文照合 → 区間ごとの時間窓）

1. 両テキストを NFKC 正規化し、空白・句読点・記号（、。？！・…等）を除去。
   除去時に「正規化後位置 ⇄ 元テキスト位置」の写像表を保持する。
   正規化は 1 文字ずつ行う（全体を NFKC に掛けると位置の対応が崩れるため）。
2. **照合は区間ごとに、その区間の時刻の前後 `WINDOW` 秒の範囲だけを見て行う。**
   その範囲の実測文字列と区間本文を `difflib.SequenceMatcher(autojunk=False)` に掛け、
   matching blocks をアンカー集合とする。
   - **近い順に探す**: まず `NEAR_WINDOW` 秒で探し、被覆率が `GOOD_ENOUGH` に届かなければ
     `WINDOW` まで広げる。会議では同じ言い回しが何度も出る（「そうですね」
     「はい、わかりました」）。difflib は窓の中で**最も手前の**一致を選ぶので、
     いきなり広く探すと 20〜30 秒前の同じ言葉に当たり、
     ずれていない区間にずれた提案を出してしまう。
   - 最小ブロック長: **3 文字**（初期値。日本語は 1〜2 文字一致が偶然でも頻発するため）。
   - whisper 側単語列の時刻から、アンカー各文字に時刻を割り付ける
     （単語内は文字数按分。逐語の粒度ではこれで十分。実測では 45 語中 35 語が 1 文字）。
   - **単調掃引**: 次の区間は、直前の区間が一致した位置より後ろから探す
     （`SWEEP_SLACK` 秒だけ戻ることは許す）。言い直し・繰り返し表現で前へ戻って
     当たるのを防ぐ。当初案の「アンカー列を時刻昇順で走査して逆行を棄却する
     フィルタ」と同じ役目を、窓を切る側でまとめて果たす。
   - 1 度目で一致しなかった区間だけ、`WIDE_WINDOW` 秒の広い窓でもう一度探す。
     数が少ないので広げても安く、ドリフトの大きい帯を取りこぼさずに済む。
3. どの窓でも一致しなかった区間は「照合不能」として返し、**時刻は作らない**。
   フィラー（えー、あのー）の有無や誤認識で一致が減った区間は、
   被覆率が下がった状態で返る（§3.2 の `MIN_COVERAGE` で弾く）。
   前後アンカー間の補間で推定時刻を作る案もあったが、作っても §3.2 の被覆率で
   同じく弾かれる先が同じなので採らない。

**なぜ全文照合をやめたか（2026-08-13 実測）**: `difflib` は O(n²) で、
2,000 字 0.02 秒 / 10,000 字 1.50 秒 / 20,000 字 9.62 秒 / **40,000 字 65.72 秒**。
52 分会議が約 4 万字なので、全文どうしでは 66 秒かかり、2 時間の録音では 5 分を超える。
区間ごとに窓を切ると n が千字弱に落ち、520 区間で**合計 0.16 秒**（1 区間あたり 0.3ms）。
速さ以上に効くのは誤マッチが構造的に起きなくなること。全文照合では「はい」が
3 分先の「はい」に当たり得るが、窓を切ればそもそも届かない。
Gemini 側にも実測側にも時刻があるのだから、その情報を使う。
（代案として「両方に 1 回だけ出る n-gram を杭にして帯に切る」も試したが、
繰り返しの多いテキストでは杭が取れず全文照合に退化するため不採用。）

渡す時刻は**実音声の時刻**（再生位置）であること。作業ファイルの保存値には
ずれ補正が乗っていない区間があるので、呼び出し側で補正を足してから渡す。

### 3.2 区間境界の再推定

**v1.3 改訂（2026-08-13・聴き取り 2 回目の結果を反映）**:

- anchor.py は**測ったままの生の値**を返す（余白なし）。余白と補正は提案を
  作る側（inspection.py）の方針。実測と混ぜると較正で切り分けられなくなる。
- 提案 start = 最初のアンカー文字の開始時刻 − **頭の欠け補正** − `START_PAD`
  - 頭の欠け補正 = 頭の欠け文字数 ÷ その区間の実測発話速度（字/秒）。
    本文の頭が whisper に聞き取られていないと、開始はその分だけ遅く出る。
    聴取実測: 換算 5.1 秒の区間を人は「約 5 秒切れている」と判定（ほぼ一致）。
    補正後の提案は真の位置と 0.2 秒差まで戻った。
  - `START_PAD` が厚いのは whisper が発話の立ち上がりを遅く取る癖のため
    （頭の欠けゼロでも「わずかに遅い」と判定された）。
- 提案 end = 最後のアンカー文字の終了時刻 ＋ `END_PAD`。
  ただし末尾の欠けが `TAIL_GAP_LIMIT` 以上なら終了は信用せず、いまの長さを保つ。
- **被覆率** = 区間内文字のうちアンカーに乗った割合。

提案を出す条件（すべて初期値。§12 のキャリブレーション対象）:

| パラメータ | 初期値 | 意味 | 置き場所 |
| --- | --- | --- | --- |
| `MIN_COVERAGE` | 0.60 | これ未満は提案せず「照合不能」マークのみ | inspection.py |
| `MIN_MATCHED` | 8 文字 | 一致がこれ未満なら提案しない（短文の被覆率 100% は偶然でも出る） | inspection.py |
| `TIME_DELTA` | 0.75 秒 | **開始の** \|Δ\| がこれ超で提案（終了のずれでは提案しない） | inspection.py |
| `TAIL_GAP_LIMIT` | 3 文字 | 末尾の欠けがこれ以上なら終了は動かさず長さを保つ | inspection.py |
| `CONFLICT_OVERLAP` | 0.5 | 実測範囲がこの割合を超えて重なる提案どうしは全部引っ込める | inspection.py |
| `START_PAD` | 0.30 秒 | 開始側の余白（whisper は立ち上がりを遅く取る） | inspection.py |
| `END_PAD` | 0.20 秒 | 終了側の余白（実測できたときだけ足す） | inspection.py |
| `MIN_DENSITY` | 1.5 字/秒 | 一致密度がこれ未満は散らばった偶然（正常な発話は 4〜11） | inspection.py |
| `HEAD_COMP_MAX` | 6.0 秒 | 頭の欠け換算がこれ超なら開始を測れていないので提案しない | inspection.py |
| `MIN_BLOCK` | 3 文字 | これ未満の一致はアンカーにしない | anchor.py |
| `NEAR_WINDOW` | 5 秒 | まずここだけ探す（同じ言い回しの取り違え対策） | anchor.py |
| `GOOD_ENOUGH` | 0.80 | 狭い窓でこれだけ乗ったら広げない | anchor.py |
| `WINDOW` | 30 秒 | 区間の時刻の前後、どこまで探すか（実測のドリフトは +6.8 秒） | anchor.py |
| `WIDE_WINDOW` | 120 秒 | 1 度目で見つからなかった区間を探し直す幅 | anchor.py |
| `SWEEP_SLACK` | 1.0 秒 | 単調掃引で、直前の一致から戻ることを許す幅 | anchor.py |
| `SWEEP_MIN_COVERAGE` | 0.50 | これ未満の一致では掃引位置を進めない | anchor.py |

**既知の弱点（実データで確認すること）**: 隣り合う区間の本文がほぼ同じ場合、
1 区間ぶんずれて一致することがある（実際の会議録では起きにくいが、
定型的な点呼・読み上げでは起こりうる）。被覆率は高いまま出るので、
被覆率では弾けない。`NEAR_WINDOW` を先に見ることで大半は防げるが、
完全ではない。§12 のキャリブレーションで実データでの発生率を測ること。

隣接区間と重なる提案は、適用時に接点でクリップする（同時適用しても重ならない）。

### 3.3 `time_offset` との整合（設計判断）

現行の再生規約は「再生位置 = 保存時刻 + `Project.time_offset`」（`time_edited` 区間は適用外）。
アライメントが測るのは**実音声の時刻 T** なので、承認適用時は **保存値 = T** をそのまま書き、
`time_edited=True` にする（Step 1-1 の意味論どおり、以後 offset は掛からない）。
部分適用状態でも規約は壊れない。

### 3.4 スキップ規則（v1.1 で精密化）

- **`time_reviewed=True`（人が耳で確定した時刻）の区間は提案を出さない。**
  人の確定を機械が上書き提案しない。差分はログにのみ記録。
- `time_edited=True` でも `time_reviewed=False` の区間（過去の推定適用のまま未確認）は
  **提案対象**。より新しい実測で上書き提案してよい。
- `reviewed=True`（話者確定）はスキップ理由にしない。時刻提案の適用は `reviewed` を
  変更しない（話者は変わっていないため）。

## 4. Step 1-3b — 分割候補

二段階で入れる。

**第一段階（本設計の範囲）: 単語間ギャップ検出。** アライメントの副産物で追加コストゼロ。
- 区間内の隣接単語間ギャップ > **1.2 秒**(初期値)で、かつギャップの両側にそれぞれ
  一定文字数（初期値 5 文字）以上のテキストがあるとき、分割候補とする。
- 分割点はアンカー写像でテキスト位置に決定的に写す（音声側の切れ目 → 本文の切れ目）。
- 提案適用は Step 1-2 の分割ダイアログに初期値を渡す形（family / `orig_start` の規則は 1-2 設計書に従う）。

**第二段階（本設計の範囲外・明記のみ）: 声質乖離。**
現行 `main` に声質特徴量モジュールは**存在しない**（`features.py` は
`feature/manual-speaker-labeling` ブランチ側の資産で、本線には未採用）。
前半/後半の声質乖離による検出は、同モジュールの移植または新規実装が前提。
1-3c と併せて別途設計する。

**オプション（1-3d・最後）: Gemini クリップ質問。**
疑い区間 ±2 秒を ffmpeg で切り出し（`find_ffmpeg()` 基盤を流用。切り出しヘルパは小規模な新設）、
音声＋本文を Gemini に渡して交代地点を JSON で返させる。対象は候補区間のみでコストは数円級。
第一段階の見逃し率を実測してから要否を判断。

## 5. Step 1-3c — 結合候補（第二段階・概要のみ）

同一記号の連続は `merge_consecutive()` で処理済み。残るのは「別記号だが実は同一人物」で、
根拠は声質類似しかないため 3 種の提案中もっとも信頼度が低い。声質モジュール導入後に別途設計。

## 6. 提案の保存と適用

### 6.1 sidecar 方式（スキーマを増やさない）

提案は**派生データ**（再点検すれば再生成できる）なので、本体 JSON には入れず
作業ディレクトリに置く:

```
.work_<名前>/inspect/proposals.<指紋>.a<ALIGN_VER>.json
```

- 内容: `[{id, type: time|split, target_orig_start, payload, evidence, confidence, status: pending|accepted|rejected}]`
- `target` は v3 の安定キー `orig_start` で区間を指す（index は分割で振り直るため使わない）。
- `rejected` は記録し、同一根拠の提案は再点検でも再提示しない。
- スキーマへの追加は §2.5 の `time_reviewed` のみ。適用の痕跡は Day 30 で入る
  `edit_log`（v5）に記録する。

### 6.2 承認の意味論（v1.1 で確定）— 話者の ✓/△ と同型にする

| 操作 | time_edited | time_reviewed | 一覧表示 |
| --- | --- | --- | --- |
| 提案を**個別に**承認（その区間を再生してから承認） | True | **True** | ✎ |
| 提案を**まとめて適用**（聴かずに一括） | True | **False** | ✎△ |
| ✎△ の区間をあとで聴いて「この時刻で確認」 | True | True | ✎ |
| 却下 | 変更なし | 変更なし | — |

- 「まとめて適用 → 聴いて確認したものから ✎ に昇格」は、話者割当の
  「一括適用（△）→ 聴いて確定（✓）」と完全に同じ動線。利用者は新しい概念を学ばない。
- 適用は Step 1-1 の時刻編集の適用経路（検証・再描画・`_dirty`）を通す。
  **点検専用の書き込み経路は作らない**。
- `edit_log`（Day 30/v5）導入時は `by: "user"|"inspect"` と `evidence` を持たせる（変更なし）。

## 7. キャッシュ

既存のキー規律（指紋 + 設定。欠けると使い回し事故）に合わせる:

```
.work_<名前>/align/words.<指紋>.<モデル名>.a<ALIGN_VER>.json
```

- `ALIGN_VER` はアンカー照合実装のバージョン定数。照合ロジック変更時に上げて再計算させる。
- whisper 転写（重い）はキャッシュし、照合〜提案生成（軽い）は毎回計算し直す。
  `redistribute_times` を毎回再計算する既存の運用思想と同じ。

## 8. `audio_fingerprint` 調査結果と `source_sha256` の設計（Day 30 へ反映）

`src/audio.py` の実測: **全量ハッシュ**である。ファイル全体を 4MB ブロックで読み、
サイズをシードに **BLAKE2b（digest_size=8 = 64bit、16 hex 桁）**を計算。取得失敗時は空文字で
継続時間比較にフォールバック。

含意:

1. **変更検知としては現状で完全**（1 バイト違えば別指紋）。キャッシュキーは変更しない。
   アルゴリズムを変えると既存キャッシュ全滅＋旧作業ファイルとの `_is_same_audio` 比較が壊れる。
2. **証跡としては 64bit は短い**（対外的な同一性証明には不足。第三者検証の標準は SHA-256:
   `Get-FileHash` / `certutil` / `sha256sum` でそのまま照合できる）。
   よって Day 30 の `source_sha256` は**別フィールドとして追加が正当**。役割が違う
   （キャッシュ同一性 vs 証拠完全性）。
3. 実装メモ: どちらも全読みなので、**同一の読みループで両ハッシュを同時計算**する
   （1GB を二度読まない）。`audio_fingerprint` に追加ハッシャを渡せる形に拡張するのが最小。

## 9. モデル配布【要決定 — 推奨 A で着手可】

| 案 | インストーラ | 初回 | 備考 |
| --- | --- | --- | --- |
| A: 同梱なし・初回 DL（**推奨**） | 現状サイズ維持 | small(int8) を HF から取得 | 点検はオプトイン機能なので未使用者に負担ゼロ |
| B: base(int8) 同梱 | +100MB 弱 | オフラインで即動く | 精度は small に劣る |

推奨は A ＋ **手動配置経路の用意**（モデルフォルダを指定できるようにする）。
ローカル完結が必須の利用者（研究倫理審査・機密案件）はオンライン DL 自体が難しい場合があるため、
「別 PC で取得したモデルフォルダを置けば動く」を仕様として明記する。
既定モデルは small、設定で base/medium を選択可。

## 11. 性能・プライバシー

- 完全ローカル処理。音声は外部送信しない（1-3d の Gemini クリップ質問のみ例外で、
  実行前に明示の確認を挟む）。
- CPU int8 / small の処理時間は**実測してから確定**（52 分音声で目安 10〜25 分を想定。
  1 音声につき 1 回でキャッシュされる）。実測値を本書に追記する。
  - 2026-08-13: 14 秒の合成音声で 52 秒（モデルの初回取得を含む）。
  - **2026-08-13 実測: 67 分の実会議（WAV 370MB）で転写 24.4 分（音声の 0.36 倍）、
    11,426 語。照合〜提案生成は 0.3 秒。** 想定（10〜25 分）の範囲内。
    高速化の余地（VAD・beam_size=1・base モデル）は精度への影響が未測定のため
    未着手。キャッシュにより 2 回目以降は数秒。
- 照合（anchor.py）は 520 区間で 0.16 秒。提案生成を含めても体感は無視できる。
  重いのは whisper 転写だけなので、キャッシュするのもそこだけでよい（§7 のとおり）。

## 12. テスト計画

- **ユニット（CI 対象・モデル不要）**: `anchor.py` は正規化・照合・単調性・被覆率・境界再推定を
  テキストと単語時刻フィクスチャだけで検証できる。フィラー差異・誤認識・言い直しの合成ケースを含める。
  `inspect.py` は偽の words リスト注入で提案生成を検証。
- **`time_reviewed` の意味論**: §6.2 の表の 4 操作すべて＋旧ファイル読込
  （`time_edited=True` → `time_reviewed=True` 扱い）＋スキップ規則（§3.4）。
- **統合（ローカルのみ・CI 対象外）**: Windows SAPI の日本語 TTS で既知テキストの音声を合成し、
  実 whisper を通して境界誤差 < 0.3 秒を確認。
- **キャリブレーション**: 52 分実会議（00:43 台の +6 秒帯を含む）で提案の当たり率を測り、
  §3.2 / §4 の閾値（`WINDOW` / `WIDE_WINDOW` を含む）を確定。
  雑音・マイク距離での劣化もここで見る。
  - 2026-08-13 時点: 合成音声での被覆率は 0.85 / 0.96 / 0.95。
    表記ゆれ（第一号→第1号、いただき→頂き）を含んでもこの水準。
    実会議は雑音とマイク距離で落ちるはずなので、`MIN_COVERAGE` 0.60 の妥当性は
    実データで確認すること。
  - **2026-08-13 実会議で第 1 回キャリブレーション実施**（67 分・520 区間・
    信頼度層別 15 件の聴き取り）。結果と対策:
    - 当たり 8 / 部分外れ 5 / 完全な外れ 2（53%）。**被覆率ベースの信頼度は
      当たり率と連動しなかった**（「高」が最下位）。
    - 完全な外れ 2 件はどちらも一致 3 文字。短文は被覆率 100% が偶然でも出る
      → `MIN_MATCHED` 8 文字を導入。
    - 終了×は末尾の欠け 3 字以上と完全に一致（2 字以下は全部終了○）
      → `TAIL_GAP_LIMIT` 導入。開始のずれだけで提案し、末尾が欠けた区間は
      長さを保って開始だけ動かす。
    - 挨拶の応酬で 3 区間が全く同じ実測位置に当たる「取り合い」を確認
      → 実測範囲が重なる提案は全部引っ込める（`drop_conflicts`）。
      取り合いは、一致範囲が単調掃引の戻り幅（`SWEEP_SLACK` 1 秒）より
      短いときに、次の走査が同じ場所を取り直せることで起きる。
    - 新規則適用後: 提案 141 → 66 件。判定済み 15 件のうち生き残ったのは
      当たりの 3 件のみ（外れ・部分外れは全滅）。
  - **2026-08-13 第 2 回聴き取り**（生き残りのずれ上位 10 件）。
    当たり 2 / 開始× 6 / 終了だけ× 1 / 内容違い 2（重複あり）。
    完全な誤マッチはゼロで、**大ずれ提案も正しい発言の近傍を指していた**。
    外れ方は端の精度の問題で、機構が特定でき、すべて対策済み:
    - 開始が遅い（5 秒級）＝頭の欠け。欠け字数 × 実測発話速度の換算が
      人の観察とほぼ一致（29 字 → 5.1 秒 vs 観察「約 5 秒」）→ 補正を導入。
      補正後は真の位置と 0.2 秒差。換算 6 秒超は提案しない（`HEAD_COMP_MAX`）
    - 開始がわずかに遅い（頭の欠けゼロ）＝ whisper の立ち上がりの癖
      → `START_PAD` 0.3 秒
    - 本文が発話と食い違う区間は一致密度が 0.8 字/秒に落ちる
      （正常 4〜11）→ `MIN_DENSITY` で機械的に検出・棄却。
      局所的な内容違い（数語だけ）は検出できない。耳が捉える設計どおり
    - 第 2 回反映後: 提案 57 件。判定済みで残った提案は真の位置に収束
      （127: 残差 0.2 秒 / 151: 残差 1.7 秒）
    - 照合不能 200 件の 9 割は本文 10 字未満の相づち。whisper が重なった
      短い発話を文字に起こさないため、**文字照合の原理的な限界**。
      短い区間のずれはこの方式では測れない（1-3d や声質側の課題として残る）。
  - 隣接して本文がほぼ同一の区間（Gemini の重複転写）が **20 組**見つかった。
    時刻照合を乱すほか、それ自体が Step 1-3c の**結合候補の入力**になる
    （声質なしでも「本文同一＋音声位置が重なる」を根拠にできる）。
- 既存の罠への注意: `pytest tests/` は命名規約で拾われないテストがある。
  新設テストも `python tests\test_xxx.py` 単体実行で全チェックが走る構成にする。
