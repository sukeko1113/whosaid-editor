**この順である理由**

1 は終わった。当初の前提（「DPAPI 復号失敗が握りつぶされている」）は誤りで、実際にあったのは「旧版の設定を引き継ぐと API キーが平文のまま残る」構造だった。何を直したかは §1。

2 を 3 の前に置くのは、**期限が外から決まる唯一の項目**だからである。既定のクラウドモデル（`pipeline.py` の `DEFAULT_CLOUD_MODEL`）が止まると、クラウド経路を選んだ人の転写が全部失敗する。変更そのものは小さい（既定モデル名、画面の選択肢 `MODELS`、README の記述）。ただし**モデル名はキャッシュキーに入っている**ので、既定を変えるとクラウド利用者は同じ音声を取り直すことになる。設計書の順序に入れておかないと、3・4 の途中で割り込みになる。

**2 の位置は暫定である。**停止日が確かめられるまで、単独で出すか v2.3.0 に同梱するかは決めない。日付が分からないまま「間に合わない可能性」を理由に出荷の形を決めると、未確認の情報が順序を決めることになる（初版がそうだった）。確かなのは方向だけ（2.0 系は 2026-06-01 に停止済みで、2.5 系も退役の側にある）。分からないのは期限。

**停止日について、記録と一次情報が食い違っている（2026-09-03 に確認）。** 会話記録の「10 月 16 日停止」は、検索結果の抜粋 2 件（Google のフォーラム投稿と第三者のまとめ）が一致していたのを確定と扱ったもので、一次情報ではなかった。Google のフォーラムでは、7 月 2 日時点の Google の廃止予定ページに 10 月 16 日と書かれていた、7 月 9 日に一時 404 が返った、という報告がある。一方、**9 月 3 日に見た同じ廃止予定ページには `gemini-2.5-flash` の停止日の記載が無く**、変更履歴にも 2026 年の廃止告知は無い。第三者のまとめサイトは 10 月 16 日と書いているが、「早くてもその日」という書き方をしているものもある。**着手前に、Google の廃止予定ページを開いて自分の目で確かめること。**あわせて、二号機で実際に `gemini-2.5-flash` を呼べるかを試す。記録・二次情報・要約のどれも実物ではない。

3 は 4 の土台になる。辞書は「置換候補のリストを事前に用意するもの」であり、適用の仕組みは 3 が提供する（詳細は §3）。順序を逆にすると辞書側に独自の適用エンジンを作ることになり、二重実装になる。

5 は**入れない可能性がある**。測定して効果が出なければ実装しない。順番に並べると 3・4 が待たされるので、二号機が空いている時間に並行して測定を回す。

## 2. 一件ずつの検索・置換（v2.3.0）

本節は 2026-09-03 に実物に合わせて書き直した。初版は「現在は一括置換しかない」「`edit_log` は未実装」「既存の Undo で置換も戻せる」を前提にしていたが、いずれも実物と違った（§2.1）。UI は Word 式の「置換／スキップ」ボタンではなく、**既存の○×方式に寄せる**（§6 の決定）。

### 2.1 目的と、実物にあるもの

**なぜ必要か**: 一括置換は誤りを一括で広げる。「田中」を「田仲」に一括置換すると、別人の田中さんまで巻き込む。日本語には語境界がないため部分一致が避けられず、この危険は構造的に残る。

**実物にあるもの（v2.2.1 時点）**

- `AssignWindow.replace_words()` → `ReplaceWordsDialog`（assign_gui.py）。語句を探して**前後の文脈つきで全件を並べ、行ごとに○×を付け、「この N 箇所を直す」で適用する**画面。既定は全部○。設計書（話者分離）§16.3 に基づく
- `Project.find_text(term)`（segments.py）。**出現 1 回につき 1 件**の `TextHit` を返し、区間の鍵と「その区間で何番目か」を持つ。同じ区間に 2 回出ても別々に扱える
- `Project.replace_text(before, after, targets)`。(区間の鍵, 何番目) で指した箇所だけ置き換える。**記録は `edit_log` に 1 件**（`replace_text_bulk`）。`reviewed` は触らず、`text_edited` を立てる
- 本文の変更（手直しも置換も）に **Undo は無い**。既存の Undo は話者と✓の写しを戻すだけ

つまり「一件ずつ判断して置換する」「区間内の複数ヒットを個別に数える」「`reviewed` を触らない」「`edit_log` に残す」は、データ層で既に満たされている。

**このアプリ固有の利点で、実物に無いもの**: 該当区間にジャンプして、**その場で音声を聴く**こと。人名が本当にそう発音されているかを耳で確かめてから○×を決められる。Word にはできない。§2 で足すのはここが本丸。

### 2.2 UI（○×方式に寄せる）

既存の `ReplaceWordsDialog` を拡張する。別の画面は作らない（二重実装になる）。

- 検索語／置換語の入力欄と「探す」（既存）
- ヒットの一覧。行ごとに○×（既存）
- **行を選ぶと、本体の一覧がその区間に飛ぶ**（`AssignWindow.goto_key()`。区間の鍵で指す。絞り込みで隠れていれば「すべて表示」に戻す）。**「▶ 聴く」**でその区間を再生する（`play_current`。自動再生が切れていても押せば鳴る）。行を移ったときに自動で再生するかは、本体の「移動したら自動再生」の設定に従う
- **位置表示**「n / N」と、次へ・前へのキー（↓↑ は Treeview 標準、Enter は次の行）。探した直後は 1 件目を選ぶ
- 一致の条件を切り替えると探し直しになり、**○×は「付け直し」ではなく全部○（直す）に戻る**（`search()` が `marks = [True] * len(hits)` を張り直すため）。危険な側に倒れる既定値なので、**×が 1 つでも付いていれば確認のダイアログを出す**。文面に×の件数を入れ、「いいえ」ならチェックを直前に探した条件へ戻して探し直さない。×が無ければ失うものが無いので聞かない。その旨を画面にも書く
- 「全部に○」「全部に×」（既存）が、Word の「すべて置換」に相当する
- 適用は「この N 箇所を直す」1 回。**`edit_log` の記録も Undo も 1 件**になる

「置換」「スキップ」ボタン方式にしない理由: 一件ずつ判断するのは同じで、○×なら判断を全部見てから 1 回で適用できる。判断の途中で本文が変わらないので、置換語が検索語を含む場合の無限ループ（初版 §2.3）も構造的に起きない。

オプション:

- **完全一致 / 部分一致の切り替え**。既定は部分一致（日本語では語境界が無いため）。完全一致は「語句の前後が半角英数字でない」と定義する（`um` が `summary` に当たらないため）。**日本語には効かない**ことを画面に書く
- **英大文字小文字の区別**。既定は区別する（実物の `str.find` と同じ）。外すと `Um` も `um` に当たる。英語ディベート音声で効く

### 2.3 一致の扱い

- 検索は**その区間の本文に対して**行う。話者名は対象外（話者名の変更は `replace_speaker` という別機構がある）
- 同一区間内に複数ヒットがある場合、**各ヒットを個別に数える**（実物どおり）
- **探すときと直すときで同じ照合関数を使う。**オプションが片方にしか効かないと、「探して○を付けた箇所」と「直した箇所」がずれる。`find_text` と `replace_text` は同じ関数で位置を列挙し、オプションも同じ引数で受ける
- 大文字小文字を区別しないとき、一覧に出す語句は**本文に実際にある綴り**（検索語ではなく）

### 2.4 `reviewed` は変更しないこと（決定済み）

**置換によって `reviewed` を True にしてはならない**（実物どおり）。`reviewed` は「話者を自分の耳で聴いて確認した」の意味であって、本文の文字を直したことではない。

既に `reviewed = True` の区間の本文を置換したとき、フラグは**戻さない**（§6 の 1、2026-09-03 に決定）。確認したのは話者であり、本文の誤変換修正はそれを無効にしない。

置換の記録は `edit_log` に `replace_text_bulk` として 1 件（実装済み）。オプション（完全一致・大文字小文字）を使ったときは、その記録に載せる。

### 2.5 Undo（今回の範囲に入れる）

本文の変更には Undo が無いので、**置換だけを 1 段戻せる仕組み**を足す。時刻の一括適用にある `undo_bulk_times` と同じ形:

- 適用の直前に、対象区間の**直す前の本文**を区間の鍵（`segment_key`）で覚える。`index` は分割・結合で振り直るので鍵に使わない
- 「直した語句を戻す」で、その区間の本文を戻す。本文が適用後にさらに手で変えられていた区間は戻さず、その旨を知らせる
- 戻したことを `edit_log` に 1 件記録する（`replace_text_undo`）。記録を消さない——「直して、戻した」も人の判断の履歴
- 1 段だけ。次の置換をすると前の分は戻せなくなる。ボタンの有効／無効で分かるようにする
- 適用のあとに分割・結合した区間も戻さない。鍵は同じでも本文が変わっている（分割で前半は短く、結合ではつながる）ので、「手で直した区間」と同じ判定で守られる。意図して作った判定ではないので、テストで縛ってある（実装: `Project.restore_texts()`、画面: 「直した語句を戻す」）

### 2.6 テスト

- 大文字小文字を区別しないとき `Um` と `um` の両方に当たり、一覧の語句が本文の綴りであること

## 3. 辞書機能（v2.3.0）

### 3.1 目的

固有名詞（人名・団体名）の定型的な誤変換を蓄積し、次回以降の修正コストを下げる。

**前提として、効果の程度は不明である。** 同じ人名が録音をまたいで繰り返し出るかどうかに依存し、現時点で実会議の音声は1件しかない。**効果を測るなら、辞書適用前後で修正件数を数える指標を、実装前に決めておくこと。**

### 3.2 設計の要点 — 辞書は「検索語のリスト」である

**辞書に独自の適用エンジンを作らない。** 辞書がやることは、§2 で作った一件ずつ置換の**検索キューを事前に埋めること**だけ。

- 転写完了後、辞書の各エントリで本文を検索し、「辞書に基づく候補 N件」として提示する
- ユーザーは §2 の UI で一件ずつ確認して置換する
- **自動適用しない**

自動適用しない理由は §2.1 と同じ。「田中」→「田仲」が正しいのは特定の人物についてだけで、別の田中さんには誤り。自動適用は一括置換の問題を、ユーザーの目の届かないところに移すだけになる。「元データは壊さない」に反する。

### 3.3 データ

保存先: ユーザーの設定ディレクトリ（プロジェクト単位ではなくグローバル）。固有名詞は組織をまたいで繰り返すより、同じ組織の会議で繰り返すため、グローバルに持つほうが効く。プロジェクト単位で無効化できるようにする。

エントリの項目:

| 項目 | 内容 |
| --- | --- |
| `wrong` | 誤変換の文字列 |
| `correct` | 正しい文字列 |
| `enabled` | 有効/無効 |
| `added_at` | 追加日時 |
| `origin` | `manual`（手入力）/ `replace_history`（置換から登録） |
| `note` | 任意のメモ（「○○課の田仲さん」など、同名別人の区別用） |

`note` は同名別人を区別するために要る。辞書だけでは判断できないケースがあることを、UI 上でも隠さないこと。

### 3.4 置換履歴からの登録

§2 で置換を行ったとき、「この置換を辞書に登録しますか」を出す。**黙って追加しないこと。** 一度きりの修正まで辞書に溜まると、辞書自体がノイズになる。

### 3.5 個人情報の扱い

辞書には人名が入る。ローカル保存だが、以下に注意:

- ログに辞書の内容を出さないこと
- 不具合報告用のエクスポートやフィードバックフォームに、辞書が紛れ込まないこと

（書き出し・読み込み機能は将来の検討事項。テープ起こし業者での利用を想定すると有用だが、今回の範囲外）

### 3.6 テスト

- エントリの追加・無効化・削除と永続化
- 辞書からの候補生成が §2 の検索と同じ結果を返すこと
- **自動適用されないこと**（本文が辞書適用だけで変化しないことを明示的に検証する）
- 辞書が空のときに正常動作すること
- 無効化したエントリが候補に出ないこと

## 4. 並列処理の実験（実装するかは測定次第）

### 4.1 仮説

**CPU のみの環境で、チャンクを複数同時に転写し、ワーカーあたりの `cpu_threads` を下げると、逐次実行より実時間が短くなる。**

根拠: faster-whisper の CPU 実行は複数コアを使うが、1本のチャンクだけではコアを使い切れないことがある。

### 4.2 効かないと予想される条件

**GPU 環境（一号機）では効果はほぼ無いと予想する。** GPU は1枚しかなく、同時に流しても順番待ちが GPU 内部に移るだけ。加えてワーカーごとにモデルを読むと VRAM を二重に消費し、large-v3 では載り切らない可能性がある。

この予想が外れる可能性もあるので、**GPU 側でも測定して、効かないことを確認する**こと。予想どおりでも記録に残す。

### 4.3 測定計画

**実験用スクリプトを `tools/` に置く。本体（`pipeline.py`）には手を入れない。** 効果が確認できてから初めて本体に入れる。

**測定機**: 二号機（CPU）が主。一号機（GPU）でも実施し、効かないことを確認する。

**固定するもの**

- 同一の音声ファイル（毎回同じもの）
- チャンク長
- モデル（標準モデルで実施。large-v3 は別途）
- 各実行前にキャッシュを消す（`tools/clear_run_cache.py`）

**振るもの**

- ワーカー数: 1 / 2 / 4
- ワーカーあたり `cpu_threads`: フル / 半分 / 1/4

**測定する指標（測定開始前に固定すること）**

1. 実時間の合計（主指標）
2. ピーク RAM
3. ピーク VRAM（GPU 実行時）
4. **出力の一致**: 並列実行の結果が逐次実行と同一の本文になるか

4 は必須。**速くなっても本文が変われば意味がない。** 一致しない場合は、速度の数値を採用しない。

**交絡要因**

- **ノート PC の発熱**。長時間の連続実行で周波数が落ちる。実行順を入れ替えて複数回測る。室温と実行順を記録する
- **モデルの読み込み時間**。ワーカーごとに固定費がかかる。チャンク数が少ないとここが支配的になる。モデル読み込み時間を別に計測すること

### 4.4 成功条件

**測定を始める前に、以下を埋めること。結果を見てから決めると事後選択になる。**

- 並列2本が逐次比で __________ % 以上短縮
- かつ 出力が逐次と一致
- かつ ピーク RAM が __________ GB 以内

3つすべてを満たしたときに限り、本体への実装に進む。1つでも欠ければ実装しない。

### 4.5 Gemini バックエンドの並列化（別件）

Gemini は待ち時間がネットワークとサーバー側なので、並列化は効く。ローカルとは事情が異なる。ただし:

- **レート制限が実質の上限を決める。** 実装前に現在の制限値を確認すること
- **たまたま通った本数を設計の根拠にしないこと。** 上限を超えて成功した実測があっても、文書化された上限に従う（既存方針）

これは日本語側の要件ではなく、`ai-debate-analyzer` 側の速度要件（試合直後にジャッジへ転写を渡す）から来ている。本書の 1〜4 とは別に扱う。

## 6. 実装前に確定が必要な事項

1. **`reviewed` の扱い**（§2.4）— 既に `reviewed = True` の区間の本文を置換したとき、フラグを戻すか戻さないか。推奨は「戻さない」
   → **決定（2026-09-03）: 戻さない。** `reviewed` は「話者を耳で聴いて確認した」の印であり、本文の誤変換を直したことはそれを無効にしない。置換は `reviewed` を True にも False にもしない
   → **あわせて決定（2026-09-03）:** §2 の UI は Word 式の「置換／スキップ」ボタンではなく、**既存の○×方式（`ReplaceWordsDialog`）に寄せる**。一件ずつ判断するのは同じで、判断を全部見てから 1 回で適用でき、記録も Undo も 1 件で済む。別画面を作ると二重実装になる。**置換の Undo（§2.5）は今回の範囲に入れる**（本文の変更に Undo が無いため、置換だけ 1 段戻せる形）
2. **辞書の効果指標**（§3.1）— 何をもって「効いた」とするか。修正件数か、修正にかかった時間か
   → **決定（2026-09-03）: 件数で測る。** 辞書の候補から適用した件数を `edit_log` の記録（`origin: dictionary`）から数える。**○だけでなく×の件数も残す**（記録に `rejected`）。適用 ÷（適用 ＋ 却下）が辞書の精度になる。時間は測れない
   → **あわせて決定（2026-09-03）:** プロジェクト単位の無効化は、作業ファイルのスキーマを変えず**辞書ファイル側に音声指紋（`audio_fingerprint`）で持つ**（CLAUDE.md「スキーマ変更は一括で」）。辞書の候補は**一度に 1 項目ずつ**○×画面で回す（行ごとに置換語が違う一覧は作らない）。項目を終えたら**次の項目へ進むボタン**を置く。辞書の置換に使った条件（完全一致・大文字小文字）は項目に持たせ、探すときと直すときで同じ値を使う（§2.3）。自動適用はしない
3. **並列化の成功条件**（§4.4）— 短縮率と RAM 上限の数値
4. **v2.2.1 を単独で出すか**（§0）— DPAPI 修正のみを先行リリースするか、v2.3.0 にまとめるか
5. **条件を切り替えたときの○×**（§2.2）— 確認を挟むか、注記だけで黙って探し直すか
   → **決定（2026-09-06）: ×が付いているときだけ確認ダイアログを出す。** 初版は注記だけで黙って探し直していた。実物は marks を全部 True に張り直すので、○×が中立に戻るのではなく**全部○（直す）に倒れる**。区間へ飛んで耳で聴いて付けた×が「直す」に反転し、ボタンの件数表示が変わるだけで警告が無かった。`reviewed` の✓は立たないので製品価値の核は汚れないが、**倒れる方向が「適用」側で、本文の書き換えを戻す手段は §2.5 の 1 段しか無い**（適用後に手で直した区間は戻らない）。よって確認を挟む
   → **あわせて決定:** ×が 1 つも無いときは聞かない（既定のまま条件を試す手を止めない）。文面には**×の件数を入れる**——「付け直しになる」という曖昧な言い方が実物と食い違った原因なので、失うものの大きさを数で見せる。「いいえ」ではチェックを直前に探した条件（`self.options`）へ戻す。**この画面の変数に `trace` は付けない**——`Checkbutton` の `command` は `var.set()` では発火しないため戻す操作が再帰しない。`trace` を付けるなら二重発火のガードが要る
