## 4. 前提となる事実

### 4-1. B: Gemini 3.5 Transcribe（確認済み・2026-08-26 公開）

出典: `https://ai.google.dev/gemini-api/docs/transcribe`、同 `docs/pricing`

| 項目 | 内容 |
| --- | --- |
| モデル名 | `gemini-3.5-transcribe`（録音済み用）。`-live` はストリーミング用で**対象外** |
| API | **Interactions API**（`client.interactions.create`）。`generateContent` ではない |
| 提供段階 | Public preview |
| `mode` | `verbatim`（既定）と `smart`。verbatim はフィラー・繰り返し・言い直し・ポーズを保持。**必ず verbatim を使う** |
| `smart` | フィラー除去・自動整形。**使わない。** timestamp / diarization と併用不可 |
| 話者分離 | `mode.diarization_mode: "speaker"` → `spk_1`, `spk_2` … 最大8話者。**3話者以上は experimental** |
| 単語時刻 | `mode.timestamp_granularities: ["word"]` |
| 精度注記 | 単語時刻を有効にすると**全体の転写精度が劣化しうる**と公式が明記 |
| **音声長上限** | **diarization か単語時刻を有効にすると30分**（両方無効なら1時間） |
| 言語 | `language_codes: ["ja-JP"]` |
| 語彙 | `custom_vocabulary` 最大1,000語（推奨100語程度） |
| 出力 | `interaction.output_text` に全文。注釈は `interaction.steps[].content[].annotations[]` の `type == "word_info"`（`text` / `speaker` / `start_offset` / `end_offset`） |
| 料金 | 音声入力 $0.003/分、テキスト出力 $0.002/分（実効約 $0.30/時）。**無料枠は入力が製品改善に使われるため使わない** |

```python
interaction = client.interactions.create(
    model="gemini-3.5-transcribe",
    input=[{"type": "audio", "uri": audio_file.uri, "mime_type": audio_file.mime_type}],
    generation_config={
        "transcription_config": {
            "language_codes": ["ja-JP"],
            "mode": {
                "type": "verbatim",
                "diarization_mode": "speaker",
                "timestamp_granularities": ["word"],
            },
        }
    },
)
```

### 4-2. C: Cloud Speech-to-Text V2 / Chirp 3

出典: `https://docs.cloud.google.com/speech-to-text/docs/models/chirp-3`、同 `docs/release-notes`

**確認済み:**
- Chirp 3: Transcription は **GA**（B・D と違い preview ではない）。モデル識別子 `chirp_3`。
- **Speech-to-Text API V2 専用。** v1 では使えない。
- 話者分離・自動言語判定に対応。speech adaptation によるカスタム語彙、ノイズ除去あり。
- StreamingRecognize / Recognize / BatchRecognize に対応。ただし**文字起こしと話者分離は Recognize と BatchRecognize のみ**、かつ**対応言語が限定される**と明記。
- 単語時刻は Chirp 2 で導入。`RecognitionFeatures(enable_word_time_offsets=True)`。
- 対応ロケールと機能の最新一覧は **locations API** で取得できると公式が案内。
- 既存 GCP プロジェクト `solar-melody-419821` が使える（kitei-search で使用中、`iron.duckie@gmail.com` 紐付け）。Cloud Storage も使用実績あり。

**要確認:**
1. **`ja-JP` が `chirp_3` の diarization 対応言語一覧に入っているか。**（× なら C を落とす）
2. `ja-JP` で単語時刻と話者分離を**同時に**有効化できるか。
3. `Recognize`（同期）の音声長上限。1分程度という記述があり、事実なら `BatchRecognize` + GCS ステージングが必須。
4. `BatchRecognize` の音声長上限。
5. リージョン（`us` / `us-central1` / `asia-northeast1` 等）での `ja-JP` 可用性。
6. **話者分離の追加課金の有無。** 公開料金ページに明示されていないという第三者指摘がある。
7. `SpeakerDiarizationConfig` の話者数 min/max 指定方法と上限。

### 4-3. D: Voxtral Mini Transcribe V2（Mistral・2026-02-04 公開）

出典: `https://docs.mistral.ai/studio/audio/speech_to_text`、`https://mistral.ai/news/voxtral-transcribe-2/`

**確認済み:**

| 項目 | 内容 |

| **音声長上限** | **1リクエストで最大3時間** |
| 料金 | **$0.003/分**（約 $0.18/時）。B より安い |
| ノイズ耐性 | 工場・コールセンター・フィールド録音などの環境で精度維持を謳う |

**重要な設計上の含意:** 3時間まで1リクエストで処理できるため、**このバックエンドではチャンク分割が不要になる**。すなわち `cluster = f"{chunk}:{label}"`（チャンクをまたいだ `spk_1` が同一人物とは限らない）という前提が消える。B（30分）や C とは構造が違う。**この差はフェーズ2で必ず評価すること。**

**要確認:**

2. 話者数の上限、および話者数のヒント指定の可否。
3. **オンプレ / セルフホストの可否。** Apache 2.0 のオープンウェイトとして公開されているのは **Voxtral Realtime**（`mistralai/Voxtral-Mini-4B-Realtime-2602`）であり、**話者分離を持つのは Transcribe V2 のほう**。「ローカルで話者分離まで」が成立するかは要確認。**成立しない前提で考えること。**

5. 出力 JSON の構造（単語時刻と話者ラベルの入れ子）。
6. 日本語の WER に関する公表値の有無（FLEURS 等）。ただし**読み上げベンチであり会議音声の指標ではない**ことを前提に扱う。

## 8. フェーズ 2 — 実測結果の分析

人間が既存の52分音源で実行し、`raw_*.json` と `words.tsv` を渡す。A（2.5-flash）の同一区間の出力も渡す。**B と C はチャンク1本、D は全長**という条件差が生じるため、比較時は必ず同一時間帯で切り出して並べること。

`claude/claude_stt_バックエンド評価結果.md` を作成する。判定は次の4点。**各項目に ◯ / △ / × と、根拠となる数字を必ず添えること。数字のない所感は書かない。**

**判定1: フィラー・相づちの保持**
「えー」「あの」「はい」等の出現件数を A / B / C / D で並べる。逐語録として使えるかの一次判定。**D は逐語モードの明示指定が見当たらないため、ここが最大の関門になる。**

**判定2: 時刻の精度** ← **`redistribute_times()` の要否を決める判定**
- 隣接区間の重なり件数
- 1秒未満の極端に短い区間の件数（A では「37文字が1秒」という機械的な割り振りが起きていた）
- 文字数と区間長の相関（機械的に均等割りされていないか）
- 音声全体の長さと最終単語の終了時刻のずれ（進行性ドリフトの有無）

**判定3: 話者ラベル**
- 話者記号の異なり数と実際の話者数の一致
- ラベルが入れ替わっている箇所の件数
- 3話者以上での崩れ方

**判定4: チャンク分割の要否がもたらす差**（D 固有）

レポート末尾に、採用した場合に「消える既存の作り込み」と「残る既存の作り込み」を列挙すること。

## 9. フェーズ 3 — 判断と設計への反映（着手前に必ず確認を取る）

コードは書かない。設計書のみ。

- **判定2 が ◯ のバックエンドがある場合**: そのバックエンドでは `redistribute_times()` が不要になる。「Gemini 固有の欠陥修正をバックエンド層に移す」という現行の抽象化方針が変わるため、見直し案を書く。
- **判定4 が ◯ の場合**: チャンク分割を前提としない処理経路が必要になる。既存のチャンク基盤を残したまま「分割しない」を選べる構造にする案を書く。
- **どれも × の場合**: A を維持。`spike/stt-backends` は記録として残し、評価結果だけ `claude/` に置いて終了。

**結果にかかわらず共通で必要な提案:**

1. **キャッシュキーにバックエンド識別子とモデル識別子を追加する。** 現行キーは音声指紋 + チャンク長 + 逐語フラグでモデルが入っていない。A の結果を B の結果として再利用する事故が起きる。**加えて、D のようにチャンク分割しない経路ができるとチャンク長がキーとして意味を失う。** 計画中の per-segment `engine` フィールドと合わせ、`source_sha256` / `doc_version` / `edit_log` を含む schema 拡張の一括パスで扱う形を提案する。
2. **取り込み経路（インポータ）の優先度を評価する。** §3 の通り、競合調査の結論は「バックエンドを増やす」ではなく「入出力をフォーマット非依存にする」だった。RTTM / SRT / VTT / WhisperX JSON の取り込みを1本作れば全候補を一度にカバーできる。**バックエンド追加とインポータ追加の工数と効果を比較し、どちらを先にすべきかの見解を書くこと。**
3. **`reviewed`（✓/△）の位置づけを冒頭に明記する。** どのエンジンを使ったかに関係なく「人が耳で確認した」という記録が成果物の価値であり、エンジンの入れ替えはその主張を弱めない。むしろバックエンドが増えるほど価値は上がる。
4. **E（faster-whisper / ローカル完結）はこの評価の影響を受けない。** 結論に「ローカル路線を見直す」を含めないこと。
