## ログは自動で残ります（手でコピーする作業はありません）

**v3 からの変更（2026-08-31）。** ログは実行のたびに、その回の出力先の下へ
書かれます。

```
<その回の出力先>\.work_01+02edited\run-20260831-140312.log
```

名前の日時は `timings.jsonl` の `started_at` と一致します。所要時間の記録と
1 対 1 で突き合わせられます（`timings.jsonl` の `log` の項にも、同じ名前が
入ります）。

**7 本は 3 箇所に分かれます**（G1・C2・C3 のそれぞれの出力先）。手で集めなくて
構いません。集計のときに 3 箇所から読みます。

> **知っておいてください: G1 の 3 本は Google ドライブへ同期されます。**
> ログには本文が含まれます。ただしこの測定では**作業ファイル（本文すべて）と
> 音声チャンクを、元から G1 に置いています。**ログだけが新たに外へ出るわけでは
> ありません。測定が終わったら G1 のフォルダごと消してください。
>
> 同期の最中にファイルが掴まれると、**その回のログは途中で切れることが
> あります。**集計で「合計の行が無い回」として出るので、気づけます。

## 0. なぜ順序を交互にするのか

v1 は G1 を3回続けてから C2 を3回でした。**この順だと、出力先の差と実行順の差が
混ざります。**

2時間近く連続で GPU を回すので、後半ほど機械が温まります。サーマルスロットリングが
あれば、あとに回した C2 が遅く出るのは当然です。**そうなると「G ドライブのほうが速い」
という結論が、実は「先に測ったほうが速い」だっただけ、ということになります。**

交互にすれば、順序の影響が両方に均等にかかります。

```
G1 → C2 → G1 → C2 → G1 → C2 → C3
```

出力先を毎回切り替えるので手順は面倒ですが、**結論の正しさのほうが重要です。**

# 途中で止まったとき

**キャッシュを消し忘れた回**は、そのログを捨てて、消してから回し直してください。

**出力先やモデルを間違えた回**も同じです。捨てて回し直します。

**中断した回**も捨てます。ただし**ログのファイルは自動でできてしまう**ので、
手で消すことはせず、**「何回目を捨てたか」を Claude Code に伝えてください。**
中途半端なログを混ぜると集計が読めなくなります。

**回し直したときは、順序が崩れることも伝えてください。**
交互にしている意味が薄れるので、集計のときに考慮が要ります。

# 測定の結果にかかわらず

**作業ファイルを Google ドライブなどの同期フォルダに置くと、音声も本文もクラウドに
アップロードされます。** ローカル完結を売りにしているアプリで、倫理審査や守秘義務が
理由で使う利用者がいる以上、**速さでは推奨を決められません。**
