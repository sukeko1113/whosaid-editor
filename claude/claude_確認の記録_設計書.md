## 第1部　なぜ変えるか

### 1.1 `reviewed` はひとつの真偽値で二つの主張を運んでいる

今の `Segment.reviewed` は、次の二つを同時に表している。

- **人が判断した** — 利用者がその区間の話者を 1 区間ずつ選んだ
- **音声を確認した** — その区間を聴いたうえで決めた

一括適用は前者を満たし、後者を満たさない。ひとつの真偽値では、どちらかが必ず嘘になる。2026-09-15 の文言修正（PR #23）は、Word 出力・画面・README が後者を主張していたのを、前者だけに弱めたものである。**挙動は変えていない。`✓` は今も再生を確かめずに付く。**

外部評価で指摘された「一括入力だけで確認済み 100% と出る」も、根はここにある。

### 1.2 記録に残らない経路が三つある

`reviewed` が保存値であるために、人の判断を経ずに値が動く経路がある。いずれも編集履歴に残らない。

| 経路 | 何が起きるか | 場所 |
|---|---|---|
| 転写し直しの引き継ぎ | 旧区間の `reviewed` が新区間へ写る。区間の切れ目や本文が変わっていても写る | `pipeline.py:783` |
| 分割 | 前半は話者を残して `reviewed=False`、後半は話者なし | 履歴に記録なし |
| 結合 | 両側の話者が違えば未確定、`reviewed=False` | 履歴に記録なし |

分割・結合で `✓` を落とすこと自体は正しい（範囲が変わったのだから聴き直す対象になる）。問題は、落としたことが追えないことである。引き継ぎは逆に、人が `✓` を付けたのは旧区間なのに、新区間が `✓` を名乗る。

### 1.3 AI エージェントが操作する前提

画面を操作できる AI エージェントは既に実在する。アプリから見ると、エージェントの操作と人の操作は区別がつかない。Tk のイベント水準で見分ける方法はない。

そして **AI は音声を聴けない。** 再生ボタンを押して波形を進めることはできても、そこで鳴っている声を聴き分けることはしない（現行の主要なモデルは音声入力を持たないか、持っていても話者の聴き分けを担えない）。区別しないまま運用すると、「再生した」という記録だけが、誰も聴かないまま積み上がる。

逐語反訳を証拠として出すとき、問われるのは「この記録は正しいか」ではなく「誰がそれを保証するのか」である。ここには人の名前が要る。**AI は証人になれない。** 精度が上がっても、この構造は動かない。

### 1.4 作業ファイルの性質

`.speakers.json` は人に渡すことがある。その前提で、何を入れないかを決めておく。

- **既に本文そのものが入っている。** `edit_text` の前後の文、`remove_segment` で消した本文、`replace_text_bulk` の語句。会議の発言内容である
- したがって「個人名を入れなければ渡しやすくなる」は成り立たない。作業ファイルは本質的に機微な情報を含む
- そのうえで、**新たに個人を識別する情報を足さない。** 操作者の軸が区別するのは「人 / AI / 不明」であって、どの人かではない

### 1.5 旧版互換の制約

- 版を上げると、v2.2.0〜v2.3.0 ではそのファイルが**読み取り専用**になる（`NewerSchemaError`）。v2.1 以前にはこの守りが無い
- 旧版で保存すると、区間の新しい項目は消える。`edit_log` はリストごと運ばれるので残る
- **版上げは一度にまとめる。** 三軸のためにもう一度、重なりのためにもう一度、では同じ痛みを二度与える

## 第2部　三軸

### 2.1 定義

`reviewed` を廃し、三つの独立した軸に分ける。

**第一軸 — 割当の出どころ（`assign_origin`）**

その区間の話者が、どうやって決まったか。

| 値 | 意味 | 今の経路 |
|---|---|---|
| `individual` | 利用者がその区間だけを選んで決めた | `assign()` の単一選択、発話追加時の話者選択 |
| `bulk` | 声のまとまり全体・複数選択・話者置換でまとめて当てた | `assign_bulk`、`_assign_many`、`replace_speaker_bulk` |
| `carried` | 転写し直しで旧区間から写した | `pipeline.py` の引き継ぎ |
| `unset` | 未割当 | `speaker_id is None` |

**第二軸 — 再生の記録（`playback`）**

その区間の音声が、実際にどれだけ再生されたか。人の申告ではなく、アプリが観測した事実。

- 保存するのは**生の再生記録**（後述 2.3）であり、「聴いたか」の真偽値ではない
- 閾値による判定は表示時に導出する。閾値を後から変えても、聴き直しは発生しない

**第三軸 — 操作者（`actor`）**

その記録を作ったのが誰か。

| 値 | 意味 |
|---|---|
| `human` | 人が操作した |
| `agent` | AI エージェントが操作した |
| `unknown` | 不明（既存データ、判別できない経路） |

`actor` は `edit_log` に既にあるが、`"user"` 固定である。この語を `human` に改め、三値を取れるようにする。

### 2.2 `✓` は保存しない

**`✓` は三軸から導出する表示値とする。** 保存フィールドとしての `reviewed` は持たない。

今 `reviewed` が保存値であることが、人の判断を経ずに値が動く余地（1.2）を作っている。導出値にすれば、`✓` が付く条件はコード上の一箇所に集まり、後から塗り替えることができない。

導出規則は第3部に置く。

### 2.3 再生記録の構造

区間ごとに、再生された範囲の集合を持つ。

```
"playback": [
  {"from": 12.30, "to": 15.80, "actor": "human", "at": "2026-09-15T14:17:59+00:00"},
  {"from": 15.80, "to": 18.20, "actor": "human", "at": "2026-09-15T14:18:04+00:00"}
]
```

- `from` / `to` は**区間そのものの時刻**に対する値（秒・小数2桁）。再生範囲は区間より広い（先読み最大 0.4 秒、後ろ 0.3 秒、短い区間は `preview_length` まで延ばす）ので、区間の外側は切り落として記録する
- 重なる範囲は結合する。同じ所を何度聴いても被覆は増えない
- 件数が増えすぎないよう、結合後の範囲だけを保つ
- `time_offset` を戻した値で記録する（時刻を直した区間には補正を足していないため）

**被覆率** = 記録された範囲の合計 ÷ 区間の長さ。これは導出値で、保存しない。

### 2.4 重なり（複数人が同時）

今の `__multi__` は「複数人が同時に話している」という事実だけを持ち、誰かは持てない。正解ラベル 300 件のうち 37 件（12%）が複数人同時であり、この比率は無視できない。

`speaker_id` はそのまま残し、`__multi__` のときだけ意味を持つフィールドを足す。

```
"speaker_id": "__multi__",
"speakers_multi": {
  "ids": ["sp01", "sp03"],
  "primary": "sp01"
}
```

- `primary` は主に話している人。判断できなければ `null`
- 旧版で開いても `speaker_id` は `__multi__` のままなので、表示は壊れない
- 旧版で保存すれば `speakers_multi` は消える。版上げの既知の代償

**表現しないもの:** 誰がいつ何秒話したかという重なり具合。逐語反訳の粒度を超える。

## 第3部　`✓` の導出規則と、値が動く経路

### 3.1 導出規則

| 表示 | 条件 |
|---|---|
| `✓` | `assign_origin == individual` かつ 被覆率 ≥ 閾値 かつ `actor == human` |
| `◐` | `assign_origin == individual` だが被覆が閾値未満（第7部・未決2） |
| `△` | `assign_origin == bulk` または `carried` |
| （なし） | `assign_origin == unset` |

`actor == agent` の場合は `✓` にしない。AI は証人になれない（1.3）。表示は第7部で決める。

`actor == unknown` も `✓` にしない。既存データはすべてここに落ちる（第5部）。

### 3.2 時刻側（`✎`）も同じ扱い

`time_reviewed` も再生を確かめずに付く（`confirm_time`、点検の［聴いて承認］）。話者側だけ再定義すると、また非対称になる。

`time_reviewed` を廃し、`time_origin`（`individual` / `bulk` / `unset`）と、話者側と共有する `playback`・`actor` から導出する。

`time_edited`（時刻を直したか）は事実の記録なので残す。

### 3.3 分割・結合

**履歴に残す。** 今は記録がないまま `reviewed` が落ちる。

- 分割: `split` を `edit_log` に追加。`segment`（元の区間）、`at_time`（分割位置）、`origin_before`（元の `assign_origin`）を記録
- 結合: `merge` を追加。`segments`（元の二つ）、`origin_before`（両方の値）を記録

分割・結合でできた区間は `assign_origin` を `unset` に落とす（話者が残る場合も `individual` は名乗らせない）。`playback` は**引き継がない**。範囲が変わった以上、元の再生記録が新しい範囲を覆う保証がない。

### 3.4 転写し直しの引き継ぎ

写すのは `speaker_id` までとし、`assign_origin` は `carried` に落とす。`playback` は引き継がない（3.3 と同じ理由）。

`carry_speakers` として既に `edit_log` に記録される経路があるが、`pipeline.py:783` の引き継ぎは履歴に残らない。**ここも記録する。**

README と CLAUDE.md の「自動処理が `✓` を立てることは（決して）ない」は、この引き継ぎを勘定に入れていない。三軸では `carried` が `△` になるので、この記述が初めて正確になる。

## 第4部　再生記録の実装

### 4.1 取り方

ffplay を `-loglevel info` で起動すると、約 30 ミリ秒ごとに音声内の絶対時刻を標準エラーに書く。現在は `-loglevel error` で起動し、標準エラーを捨てている。

実験（無音・音量 0・`SDL_AUDIODRIVER=dummy`）では、2.000 秒から 2 秒間を指定したとき 1.95 → 3.93 と進み、先読みと後ろの余白の仕様と整合した。

**実装上の注意:** 1 秒に約 30 行出るので、読み続けないと出力の受け皿が詰まって ffplay が止まる。読むための専用スレッドが要る。

### 4.2 確かめていない条件

実験は限られた条件でしか行っていない。実装前に確かめる。

| 条件 | なぜ要るか |
|---|---|
| 実際の音声装置で同じ間隔で出るか | dummy ドライバでしか見ていない |
| 再生速度を変えたとき（`atempo`）の時刻の出方 | 速度変更は実際に使われる機能 |
| m4a など圧縮形式での頭出しの正確さ | 実データは m4a を含む |
| **途中で止めたとき、最後の時刻が残るか** | **被覆の記録が成立するかを左右する。最優先** |

最後の項目が成立しない場合、途中で止めた再生の被覆が記録できない。その場合は「最後に受け取った時刻まで」を採る案になるが、止めた瞬間より前の値になる可能性がある。実測してから決める。

### 4.3 取れないもの

アプリが言えるのは「**この区間の音声を、この割合だけ鳴らした**」までである。

- 音が実際に耳に届いたか（消音・音量・装置の状態）は分からない
- 人が聴いていたか（席を外していた、他のことをしていた）は分からない
- ffplay が無い環境の代替再生（winsound）では位置が取れない。この経路では `playback` を記録しない

**成果物の文言は、この限界に合わせる。** 「聴いた」ではなく「再生した記録がある」と書く。

### 4.4 再生の入口

割当画面の `SegmentPlayer` は 1 つで、すべての再生がここを通る。ただし、プレイヤーには時刻しか渡らず、どの区間の再生かは渡っていない。区間を渡すようにする必要がある。

分割の窓・発話追加の窓・語句の窓も同じプレイヤーを使う。これらの再生を記録するかは、区間が特定できるかによる。特定できない再生は記録しない。

## 第5部　移行

### 5.1 既存データはすべて「不明」に倒す

`reviewed=true` の区間を `assign_origin=individual` として読むことはしない。`actor` も `unknown` とする。結果として、**既存の `✓` はすべて `✓` ではなくなる。**

理由は、`true` を `false` にするのが逆向きの嘘になるのと同様、`true` を `individual` と読むのも根拠のない断定だからである。実際に個別に決めた区間も、一括適用の区間も、引き継ぎで写った区間も、同じ `true` になっている。区別する情報がない。

**v3→v4 の前例とは向きが逆である。** あのとき、古い `time_edited` を「確認済み」として読んだ。今回そうしない理由は上記のとおりで、設計書に残しておく（後から迷わないため）。

本体ファイルでは、`✓` 76 件・`✎` 11 件がすべて不明に落ちる。

### 5.2 旧版を使う利用者への知らせ

版を上げた時点で、v2.2.0〜v2.3.0 の利用者は新しいファイルを読むだけになる。

- リリースノートに明記する
- 保存を拒むときのメッセージ（`NewerSchemaError`）は既にあるので、文面を確認する
- 旧版で保存すると `speakers_multi`・`assign_origin`・`playback` が消えることも書く

### 5.3 Word 出力の文言

再生記録が入ると、2026-09-15 に直した文言がまた変わる。

- 「音声を再生して確かめたかどうかは記録していません」は、記録するようになれば削る
- 代わりに「再生した記録のある区間 N」を出す。「聴いた」とは書かない（4.3）
- 今日足した検査（`test_output_does_not_claim_the_audio_was_heard`）は「聴い」を禁じている。**意図して書き換える**形にし、何と書いてよいかを設計で決める

## 第6部　表示

### 6.1 進捗の二段表示

今: `確定 524/810 (65%)  個別に確定 76 / まとめて適用 448`

新: `割当済み 524/810 (65%)　個別 76 / 一括 448　再生記録 N (n%)`

「確認済み 100%」という単一の数字をやめる。外部評価の指摘は、この一点でほぼ解消する。

### 6.2 一覧の印

三軸を二文字に畳むので、記号が増える。第7部・未決2 で決める。

### 6.3 色に頼らない

「括弧が主、色は従」の原則を守る。印刷や色覚の条件で色は消える。三つ目の状態も記号で区別する。

## 第7部　未決事項

### 未決1 — 被覆の閾値

区間の再生範囲をどれだけ覆えば「再生した」とするか。

| 案 | 内容 | 難点 |
|---|---|---|
| A | 100% | 途中で止める・次へ送るたびに記録が付かず、実用に耐えない |
| **B（推奨）** | **80%** | 根拠は経験則。実測の裏付けはない |
| C | 一度でも再生されれば | 意味をなさない |

**生の記録を保存するので、閾値は後から変えられる。**まず 80% で始め、実運用の分布を見て調整する。定数にコメントで「実測の裏付けなし」と明記する。

### 未決2 — 三つ目の状態の見せ方

`individual` だが被覆が閾値未満の区間をどう見せるか。

| 案 | 表示 | 難点 |
|---|---|---|
| A | `◐` を足す | 記号が三つになり、一覧が読みにくくなる |
| B | `✓` と `✓△` で分ける | `✎` / `✎△` と揃うが、二文字ぶん幅が要る |
| **C（推奨）** | **`✓` と `◐`**（`△` はそのまま） | 一文字で済み、既存の幅に収まる |

`agent` が操作した記録の表示も、ここで決める。案は `✓` を付けず `◐` と同じ扱いにし、区間の詳細でのみ `agent` と示す形。

### 未決3 — `speakers_multi` の入力方法

複数の話者 ID を選ぶ UI が要る。今は［複数人が同時］ボタンを押すだけ。

- 候補リストから複数選択する形か、専用の小窓か
- `primary` を指定する操作をどう置くか
- 1024×768@125% で収まるか（右ペインは既に窮屈）

**実装規模はここが一番大きい。** 設計を詰めてから着手する。
