# whosaid-editor — 編集履歴（実装設計書 v0.1）

## 0. なぜ作るか

事業計画 v29 で、**差別化は一点に絞られた。**

> 「どこまで人が原音で確認したかを成果物に残せるか」

v29 §4・6.5 は次を差別化から**外している**——「ローカルで文字起こしできる」
「音声を聴きながら訂正できる」「逐語書式で出せる」「提出用の Word テンプレートを
出せる」。**いずれも無料または同価格帯の競合が同等以上を持つ。**

その一点を支えるのが `edit_log` だが、2026-08-19 時点の実装はこうだった。

| | 状態 |
|---|---|
| 器（スキーマ v5 の項目） | ある。再実行でも引き継ぐ（pipeline.py） |
| 記録している操作 | 相づちの追加・削除の 2 つだけ |
| 記録していない操作 | 話者の割当・一括適用・本文の修正・時刻の修正・分割・結合 |
| 成果物への出力 | 無し（検証要約は件数の集計だけ） |

**差別化の中核が 2 割しか入っていない。**

## 1. 決めたこと

### 1.1 記録するのは「人がした判断」であって「区間の書き換え」ではない

一括適用は 50 区間を変えても、**人の判断は 1 回**。記録も 1 件にして対象を
列挙する。

区間ごとに 1 件ずつ残すと、

- 実データ（710 区間・684 割当）で **95KB**。作業ファイルが 1.35 倍
- しかも**「何回判断したか」が読み取れなくなる**——検証履歴として一番大事な
  情報が、件数の山に埋もれる

1 操作 1 記録にすると **52 件・10KB**、ファイルは **1.04 倍**（実測 2026-08-19）。

### 1.2 `before` を残す

**「機械が何と言い、人が何に直したか」が無ければ検証履歴の意味がない。**

本文を丸ごと持っても、実データで作業ファイルは 1.35 倍（280KB→379KB）、
起こりうる最大（全区間に 3 種類とも）でも 2.4 倍で収まる。
「長さだけ」に削っても 400KB→297KB しか減らず、**得られるものに見合わない。**

### 1.3 書き換えの経路をデータ層に集める

画面が `seg.speaker_id = ...` と直接書き換えると**記録を素通りする。**
経路が増えるたびに記録し忘れるので、`Project` のメソッドを必ず通す。
相づちの追加（`add_utterance`）が既にこの形なので、それに揃えた。

```python
Project.assign_speaker(index, speaker_id, reviewed=True)
Project.apply_speaker_to(indexes, speaker_id, heard_index)   # 一括
Project.restore_assignments(snapshot)                        # 取り消し
Project.edit_text(index, new_text)
Project.edit_time(index, start, end, reviewed)
```

### 1.4 取り消しも記録に残す

消してしまうと「一度は当てたが戻した」経緯が読めなくなる。
**検証履歴は結果ではなく経緯の記録**なので、打ち消しも残す（`undo_assign`）。

### 1.5 変わらないものは記録しない

同じ話者を当て直す・同じ本文で確定する、では記録しない。
**履歴が水増しされると読めなくなる。**

（`_base_for_insert()` が 1 区間を割当済みにしているため、検査を書いていて
この規則を実際に踏んだ。規則そのものを検査に残してある。）

### 1.6 鍵は `orig_start`

`index` は分割・結合・再実行で振り直るので鍵にしてはいけない
（自動点検設計書 §6.1・`listen_order`・`candidates` と同じ）。

## 2. 記録の形

```json
{"op": "assign", "at": "2026-08-19T05:03:40+00:00", "actor": "user",
 "orig_start": 1502.8, "before": null, "after": "sp12", "reviewed": true}

{"op": "assign_bulk", "at": "…", "actor": "user", "after": "sp12",
 "heard": [1502.8], "bulk": [1520.1, 1533.4, …], "count": 20}

{"op": "undo_assign", "at": "…", "actor": "user", "targets": [...], "count": 3}

{"op": "edit_text", "at": "…", "actor": "user", "orig_start": 1502.8,
 "before": "機械が出した本文", "after": "人が直した本文"}

{"op": "edit_time", "at": "…", "actor": "user", "orig_start": 1502.8,
 "before": [1502.8, 1517.3], "after": [1503.1, 1517.3], "reviewed": true}
```

**`assign_bulk` の `heard` と `bulk` を分けている。**聴いた 1 区間だけが ✓ で、
残りは △（機械の結果をまとめて当てただけ）。**この区別が製品価値そのもの**
（CLAUDE.md）なので、記録の側でも区別できる形にする。

**時刻は値が同じでも記録する。**✎△ → ✎ は「確認した」という変化で、
それ自体が履歴の中身。

## 3. 出力（Day 45 簡易版）

検証要約に 1 行足した。

```
編集の履歴: 全 7 件（相づちを足した 1 / 時刻(まとめて) 1 / 話者 1 /
            話者(まとめて) 1 / 本文 1 / 時刻 1 / 話者の取り消し 1）
            最終 2026-08-19 14:12
```

- **時刻は UTC で持ち、表示は手元の時刻に直す**（読む人は現地時刻で読む）
- **知らない `op` は畳まず、op 名のまま出す。**黙って「その他」にまとめると、
  新しい操作を足したときに履歴から消えたように見える
- 履歴が無い（古い作業ファイル）ときは **「記録なし」**。空欄にしない

**1 件ずつの明細は Day 75（完全版）。**今回は「何件あるか・いつまで触ったか」まで。

## 4. 画面の付け替え（単位 2）

`assign_gui` から**直接の書き換えを全部なくした。**

| 経路 | 通すメソッド |
|---|---|
| 話者を当てる／まとめて適用 | `apply_speaker_to` |
| Ctrl+Z | `restore_assignments` |
| まとまりを未確定に戻す | `apply_speaker_to(..., None)` |
| 本文 | `edit_text` |
| 時刻（1 件・提案 1 件） | `edit_time` |
| 時刻（まとめて適用） | `apply_times_to` — **1 件の記録** |
| 時刻を元に戻す | `revert_time` |
| 時刻の一括を戻す | `restore_times` |
| 名簿から人を消して割当が外れる | `clear_speakers` |
| 足した発話に話者を入れる | `set_added_speaker` |

**検査で固定した。**`assign_gui.py` に
`\w+\.(speaker_id|reviewed|text_edited|time_edited|time_reviewed) =`
が 1 つでもあれば落ちる。**わざと 1 行足して、実際に落ちることを確かめてある。**

## 6. 未決

- **`actor` は今すべて `"user"`。**機械が触る経路（自動点検の一括適用など）を
  記録に混ぜるなら、そこで `"auto"` を入れる。**混ぜたら ✓ の意味が壊れるので、
  混ぜる前にここで決めること。**
- **明細の出力形式**（Day 75）。Word の付録か、別ファイル（CSV/JSON）か。
  第三者が検算できる形であること。
- **履歴の改ざん耐性**。いまは作業ファイルの中の素の JSON で、書き換えられる。
  「検証済み」を売るなら、いずれ署名やハッシュ連鎖を検討する必要がある。
  **ただし過剰設計になりやすいので、必要になってから。**
