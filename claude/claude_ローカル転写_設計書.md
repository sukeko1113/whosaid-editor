## 0. 目的と原則

音声から**本文を作る主体**を、Gemini から端末内の ASR へ移す。録音も本文も外へ出さずに
反訳を完成できる状態にする。

原則（既存の設計原則を上書きしない）:

- `reviewed` / `time_reviewed` の意味論を変えない。**ローカル ASR の出力は「機械の推定」であり、
  時刻を実測しても `time_reviewed=True` にはしない。** ✓ を立てるのは人だけ。
- 短い相づちの自動削除・自動重複除去はしない（エンジンが変わっても同じ）。
- `audio_fingerprint` のアルゴリズムは変更しない。
- 既存のクラウド経路は残す。ローカルを**既定**にするが、選べる状態は維持する
  （事業計画 4.3「クラウド高速処理は利用者が明示的に選んだ場合のみ」）。
- **エンジンを替えても、製品の主張は「AI の出力を完成品として扱わない」ことである。**
  したがって本書は「精度が上がる」ことを目的に置かない。目的は**外に出さずに同じ作業ができる**こと。

## 3. 全体構成

```
                      ┌─ mode="cloud" ─→ transcribe.py（Gemini）
                      │                    → "[MM:SS] 【A】 本文" テキスト
音声 → 分割 → 各チャンク ┤                    → parse_segments()
                      │
                      └─ mode="local" ─→ local_asr.py（faster-whisper）★新規
                                           → Utterance[]（実測時刻・本文）
                                           → to_segment_dicts()
                                                      │
                        （どちらの経路も）             ▼
                                            共通の後段: 通し番号・チャンク接続
                                                      │
                        全長 1 回 ─→ diarize.py（話者分離）★新規・§6
                                    → SpeakerTurn[] → cluster 記号を付ける
                                                      │
                                                      ▼
                                            Project（schema 5）→ .speakers.json
```

新規モジュール:

| ファイル | 役割 | テスト性 |
| --- | --- | --- |
| `src/local_asr.py` | faster-whisper で**本文＋時刻**を取る。モデル解決・キャッシュは `align.py` の部品を共用 | 統合テスト（実モデル）＋契約テスト（フェイク） |
| `src/diarize.py` | 話者分離。`(start, end, label)` の列を返す薄いアダプタ | 同上。§6.2 |

`align.py` は残す（自動点検の物差し）。**モデル解決 `resolve_model()`・`WhisperModel` 生成・
キャンセル・進捗の部品は `local_asr.py` と共用し、二重実装しない**
（自動点検設計書 §13 の「同一ランタイムなので共用設計にする」を履行）。

## 4. 差し替え点（アダプタ）

### 4.1 どこで分けるか【決定】

| 案 | 分岐点 | 判定 |
| --- | --- | --- |
| 最小 | `pipeline.py:505` の `transcribe_audio()` だけ差し替え、`[MM:SS] 【A】 本文` テキストを返す | **不採用**。§4.2 の理由（時刻を捨てることになる） |
| **中** | チャンク → **区間リスト**を返すアダプタを立て、`pipeline.py:505-541` を経路で分ける | **採用** |
| 大 | `run_segment_pipeline` ごと `run_local_segment_pipeline` に分岐 | 不採用。カットオーバー後に 2 本を保守することになる |

**最小案を採らない理由**: whisper は単語単位の実測時刻を持っている。これを `[MM:SS]` の
テキストへ落とすと秒精度に丸められ、さらに `parse_segments()` の中で
`redistribute_times()`（`transcribe.py:512`）が**文字数按分で時刻を作り直す**。
按分は Gemini のタイムスタンプがドリフトする既知バグへの対策であり、
実測時刻に適用すると測ったものをわざわざ推定値に戻すことになる。

### 4.2 アダプタの契約

両経路が返す共通の形（`transcribe.py:687` の中間 dict と同じ語彙に揃える）:

```python
@dataclass(frozen=True)
class Utterance:
    rel_start: float   # チャンク先頭からの相対秒
    rel_end: float
    text: str
    cluster: str       # "A"/"B"/… または "?"（判別不能）/"*"（複数人同時）
```

- クラウド経路: `parse_segments()` の内部で作られている中間表現を、そのまま `Utterance` に置き換える。
  **`redistribute_times()` / `merge_consecutive()` の中身は変更しない**（CLAUDE.md の注意点）。
- ローカル経路: whisper の発話区間から直接組む（§5）。**按分は通さない**。
- 共通の後段（オフセット加算・`chunk` の付与・`index` の通し番号）は 1 か所に集約する。

### 4.3 呼び出し側の変更

```python
def run_segment_pipeline(
    audio_path, output_dir,
    engine: EngineSpec,          # ★ api_key / model を包む。mode="cloud"|"local"
    chunk_minutes, on_log, on_progress, is_cancelled,
    verbatim=False, roster="", force_retranscribe=False,
) -> Optional[Project]:
```

- `api_key: str` / `model: str` を `EngineSpec` に畳む。**ローカルでは API キーを要求しない**
  （現状 `gui.py:427-429` がキー未入力を無条件で弾く。ここも経路で分ける）。
- `pipeline.py:475` の `_make_client()` は `mode == "cloud"` のときだけ呼ぶ。
- **既存テストへの影響**: `tests/test_pipeline_integration.py:88-95` は
  `pipeline.transcribe_audio` / `pipeline.genai` をモジュール属性ごと差し替えてフェイクを注入している。
  この差し込み口は**壊さない**（`transcribe_audio` の名前を `pipeline` 名前空間から消さない）。
  ローカル経路のフェイクも同じ流儀で `pipeline.local_transcribe` を差し替える。

### 4.4 `engine` の記録【必ず触る】

`pipeline.py:605-610` は `"mode": "cloud"` をハードコードしている。ここを実際の経路で埋める。
`segments.py:305-307` が慣例キー（`mode` / `model` / `app_version` / `at`）を定義済み。
表示側 `segments.py:593` `build_verification()` は既に `{"cloud": "クラウド", "local": "ローカル"}` を持つ。

ローカルでは Model BOM 相当を足す（第三者がどのモデルで作られた記録かを検算できるようにする）:

```jsonc
"engine": {
  "mode": "local", "model": "faster-whisper/small", "compute_type": "int8",
  "model_sha": "…",        // モデルフォルダの同一性（要検討・§9）
  "diarize": "sherpa-onnx/pyannote-3.0+titanet",   // 話者分離を使った場合
  "app_version": "…", "at": "…"
}
```

## 5. 区間の作り方

### 5.1 whisper の発話区間をそのまま使う【決定】

| 案 | 内容 | 判定 |
| --- | --- | --- |
| **A: whisper の segment をそのまま 1 区間** | `faster_whisper` が返す segment 単位 | **採用** |
| B: 単語時刻の無音ギャップで切り直す | 閾値を決めて再分割 | 不採用 |

B を採らない理由: 自動点検で**単語間ギャップは話者交代の手がかりにならない**と実測済み
（当たり率 13%。8.7 秒の沈黙でも同一人物。自動点検設計書 §4.1）。区間の切り方は話者交代とは
別の問題だが、**新しい閾値を 1 つ増やして、それを較正する正解データが無い**という事情は同じ。
whisper の segment は句点区切りに近く、追加の閾値をゼロで始められる。

補足: `merge_consecutive()`（`transcribe.py:603`）は**同一クラスタの連結**であり、
話者分離が無い間は擬似クラスタ判定（`transcribe.py:624-628`）で常に素通りする。
ローカル経路では**話者分離の結果が付いてから**通す（順序が逆だと何も連結されない）。

### 5.2 時刻の意味が変わる

| | クラウド経路 | ローカル経路 |
| --- | --- | --- |
| 時刻の出どころ | Gemini の申告（ドリフトあり） | **whisper の実測** |
| `redistribute_times()` | 通す（ドリフト補正） | **通さない** |
| 自動点検（1-3a 時刻照合） | 有効。実測 39 件を訂正 | **ほぼ自明になる**（本文と時刻が同じ 1 回の転写から出るため） |
| `time_reviewed` | False で開始 | **False で開始（変えない）** |

最後の行が重要。時刻が実測でも、**人が聴いて確かめていない以上 ✎ は立てない**。
「測れたから確認済み」にはしない（`reviewed` の意味論と同型）。

### 5.3 単語時刻を捨てない

`word_timestamps=True` のまま転写すれば、**本文と単語時刻が 1 回の転写で同時に得られる**。
これを `align.py` の words キャッシュ（`align.py:98` `words_cache_path()`）へ書けば、
自動点検が転写をやり直さずに済む（現状は自動点検が別途 24 分かける）。

- チャンクごとの単語時刻に**チャンク開始オフセットを足して**全長の列に合成してから保存する。
- キーは `align.py` の既存規則（指紋＋モデル＋`model_dir` 短ハッシュ＋`ALIGN_VER`）をそのまま使う。
- **要注意**: 合成した words は「チャンク境界で切った転写」の産物であり、
  `align.py` が全長 1 本で転写した words とは境界付近で一致しない。
  同じキーに書くなら、**チャンク長もキーに含める**（§7）。

### 5.4 `verbatim`（逐語モード）の扱い

`verbatim` は Gemini へのプロンプト指示（`transcribe.py:116` で `_RULES_VERBATIM` を選ぶ）であり、
**whisper には対応する指示が無い**。ローカルで逐語トグルを出すと、
v28 4.4 が「過大表示」として撤回したのと同じことをもう一度やることになる。

- ローカル選択時は逐語トグルを**無効化し、理由を画面に出す**
  （例:「ローカルは書式を指定できません。相づち・言い淀みは脱落することがあります」）。
- 代わりに §10 の脱落候補の検出へ動線をつなぐ。
- 実験項目（未検証・決定ではない）: `initial_prompt` にフィラーを含む例文を与えると
  逐語寄りになるという報告がある。Gate A の測定項目に入れるだけにして、v1 では使わない。

**したがって縮小経路は Day 45 の合格経路ではなく、遅延を宣言するための退避路である。**

### 6.2 話者分離の受け口

本書は転写を対象とするが、**受け口だけは同時に決める**（後から足すと §4 の共通後段を作り直すことになる）:

```python
@dataclass(frozen=True)
class SpeakerTurn:
    start: float      # 全長での絶対秒
    end: float
    label: str        # "A" / "B" / … （名簿の実名は入れない）
```

- 話者分離は**全長 1 本**で走らせる（チャンク単位ではない）。区間への割当は
  「区間の時間範囲と最も重なる turn」の多数決。重なりが閾値未満なら `?` にする。
- **名簿の人数を `num_clusters` として渡せる**のは本製品の強み（方針書 §3.4）。
  sherpa-onnx のクラスタリングが 2 話者を潰す既知報告（issue #1708）を相当緩和できる見込み。

### 6.3 クラスタ記号の名前空間【決定: 話者分離の設計書へ送る】

現状のクラスタは**チャンク内で閉じている**（`transcribe.py:731` `f"{chunk_index}:{tail}"`）。
Gemini はチャンクをまたいで同一人物を同定できないためで、表示は `C1-A`（`segments.py:239-245`）。

**全長で話者分離するなら、この制約が消える。**「C1-A と C2-B が同じ人」を人が対応づける作業
（52 分・4 チャンクで実際に発生していた）が不要になり、一括適用の対象が会議全体に広がる。
これは製品の作業動線に効く改善だが、`cluster_label` の表示規則とスキーマの互換に触れる。

**本書では決めない**（2026-08-14）。ローカル v1 は話者分離を持たないため全区間が `?` になり、
記号の形式は現行のまま `f"{chunk}:?"` を出す。この時点では
`is_pseudo_cluster`（`segments.py:230-236`）が常に真になるだけで、何も壊れず、何も塞がない。
全長へ移すときに触るのは `segments.py` の `cluster_label` と `suggest.py` の集計キーに限られる。

## 7. キャッシュ

CLAUDE.md の原則（音声指紋＋チャンク長＋逐語フラグ）に、ローカルでは**モデル**を足す。

| 経路 | 現状のキー | ローカルで足すもの |
| --- | --- | --- |
| クラウド | `.cluster.<指紋>.c<秒>[.vb].txt`（`pipeline.py:482-485`） | — |
| **ローカル** | — | `.local.<指紋>.c<秒>.<モデル名>[.d<model_dir短ハッシュ>].json` |

- **`.vb` は付けない**（ローカルに逐語モードは無い。§5.4）。付けると同じ転写が 2 つできる。
- 形式は**テキストではなく JSON**（時刻を秒精度に丸めないため）。クラウド側の `.txt` は現状維持。
- `model_dir` の短ハッシュは `align.py:117-121` と同じ規則を使う（PR #10 で導入済み）。
- **words キャッシュを兼ねる場合**（§5.3）は `ALIGN_VER` を 1 → 2 に上げ、
  キーに**チャンク長**を含める。全長 1 本の words とチャンク分割の words が同じキーを
  共有すると、境界付近の異なる転写が混ざる。

## 8. スキーマとデータ互換

**スキーマは上げない（v5 のまま）。** 追加が要るのは `engine` の中身だけで、
`engine` は自由キーの辞書として v5 で定義済み（`segments.py:305-307`）。
スキーマ変更は一括で行うという原則（CLAUDE.md）に沿い、
編集履歴（`edit_log` の記録実装・Day 45）で本当に必要になったときにまとめて判断する。

### 8.1 経路が変わったときの再実行【決定: 引き継がず作り直す】

`_carry_over_assignments()`（`pipeline.py:296`）は **`orig_start` が 2.0 秒以内で最も近い旧区間**を
対応づけ（`pipeline.py:224` `MATCH_TOLERANCE_SECONDS = 2.0`）、`speaker_id` と一緒に
**`reviewed` をそのまま移す**（`pipeline.py:369-372`）。同じエンジン・同じキャッシュなら
`orig_start` は完全一致するので正しく動く（docstring のとおり）。

**経路が変わるとこの前提が崩れる。** クラウドとローカルでは区間の切れ目も本文も別物になるが、
時刻が 2 秒以内なら対応づいてしまう。結果として、**人が聴いて確定した ✓ が、その人が一度も
見ていない別の区間に移る**。これは「自動処理が ✓ を立てることは決してない」という原則
（CLAUDE.md）に正面から反する。加えて `engine` はプロジェクト単位に 1 つしか持てないため
（`segments.py:305-307`）、本文の一部がクラウド由来のまま残ると Word の検証要約に出る
「処理経路」が実態と食い違う。

したがって**経路が変わった再実行は「音声の中身が変わった」場合と同じ扱いにする**:

- `_is_same_audio()` の判定に**経路の一致**を足す（`old.engine.get("mode")` と今回の `mode`）。
- 不一致なら `_backup_stale_project()` で退避し、`_merge_speakers()` で**名簿だけ引き継ぐ**。
  区間の割当・本文修正・時刻修正は引き継がない。
- 退避したことと理由をログに出す（「区間の切れ目が変わるため、前回の割当は引き継ぎません」）。

1274）と「建て替え」が 1 回落ちること。**許容した**——前者は意味を壊さず、
後者は［語句をまとめて直す...］で直せる。

### 9.5.5 実装

### 9.5.6 転写の暴走（2026-08-20・実機の指摘）

> 00:49:16から同じ発言が10個以上続いています

large-v3 が同じ 1 文を **20 区間**繰り返し、**4 分ぶんの会話が丸ごと
失われていた**。small では同じ区間が正しく起きている（45 区間・1,347 字）。

#### 測定の穴（3 つ重なった）

1. **逐語正解は 8 分しかない。**事故が起きた 4 分はそこに入っていなかった。
   「large-v3 のほうが良い」の根拠は、この 8 分の数字だった。
2. **繰り返しの数え方が間違っていた。**本文を 1 本に繋いだ文字列に正規表現を
   かけていたので、**区間をまたいだ繰り返しを拾えない。**「0 件」と報告して
   いたのは方法の欠陥。→ `max_repeat_run()` は**区間ごとに数える**。
3. **WAV に切り出すと再現しない。**製品が渡しているのは m4a（非可逆）で、
   音がわずかに違う。**実物のチャンクで初めて再現した。**
   以後、暴走の再現は `chunks/chunk_NNNN.m4a` で行うこと。

#### 直したこと

```
転写のあと、同じ本文が 3 区間以上続いていないか調べる
  → あれば condition_on_previous_text=False でそのチャンクだけ起こし直す
  → 直れば差し替え、直らなければ**利用者に知らせる**（黙って進めない）
```

実測: chunk_0007.m4a で 20 区間 → 1 区間、本文 **1,288 字 → 1,723 字**。

閾値 3 の根拠: 同じ音声に「はい。」3 連、「吉沢さん。」4 連があり、**どちらも
実際にそう言っている**。ここは検出であって削除ではないので、拾いすぎても
起こし直すだけで済む（起こし直して同じなら元を採る）。

**全体で引き継ぎを切ることはしない。**§8.3 の実測（small）では、切ると
CER 28.6% → 35.0%、短発話再現 57.3% → 46.4% と悪化する。暴走した
チャンクだけに留める。

#### 引き継ぎを切るのは、壊れたチャンクだけ（2026-08-21・実測）

**large-v3 でも測った。**§8.3 は small の数字だったので、確かめた。

| 条件 | CER | 誤字 | 脱落 | 回収 |
| --- | ---: | ---: | ---: | ---: |
| 引き継ぎ有り（既定） | 28.1% | 8.2% | **10.4%** | **18/34** |
| 引き継ぎ切り | 27.4% | **6.2%** | 16.6% | 10/34 |

**誤字は 2 点減るが、脱落が 6.2 点増え、落とした発言の回収が半減する。**
§8.4 の基準（区間ごと落ちるほうが手数が要る）では不採用。small と同じ向き。

ただし**長いチャンクでは逆転する。**

| | 区間 | 文字 | 繰り返し | 2 回目と同じか |
| --- | ---: | ---: | ---: | --- |
| chunk_0001 引き継ぎ有り | 128 | 1,758 | 3 | 違う |
| chunk_0001 引き継ぎ切り | 97 | 1,669 | 2 | **同じ** |
| chunk_0007 引き継ぎ有り | 42 | 1,288 | **20** | 違う |
| chunk_0007 引き継ぎ切り | 57 | **1,723** | 1 | **同じ** |

**切ると結果が安定する**（温度の引き直しが減るため。§9.5.7）。
**壊れている場面では、切ったほうが本文も多い。**

#### 検出の線を引き直した（2026-08-21・実機で誤発動だらけ）

> 30分近くかかりました

**5 チャンク中 4 つで誤発動した。**起こし直しはチャンク 1 本を丸ごと
転写し直すので、時間がほぼ倍（15 分 → 30 分）になった。

原因は閾値の当て方。「3 区間以上」は**7 分チャンクで決めた**もので、
15 分チャンクは 1 本に 260 区間あり、**本物の相づちが 3〜4 回続くのは普通**。

同じ音声の 8 件を人が見分けて線を引き直した。

| 時刻 | 回 | 中央値 字/秒 | 実際 | 本文 |
| --- | ---: | ---: | --- | --- |
| 00:11:31 | 8 | 5 | 暴走 | nick |
| 00:12:33 | 4 | 13 | 暴走 | はい ← **取りこぼす** |
| 00:34:19 | 6 | 44 | 暴走 | はい。 |
| 00:42:11 | 4 | 5 | 本物 | 吉澤さん |
| 00:58:48 | 3 | 14 | 本物 | もちろん。 |
| 01:04:06 | 4 | 8 | 本物 | はい。 |
| 01:05:49 | 3 | 13 | 本物 | 失礼いたします。 |
| 01:05:53 | 8 | 23 | 暴走 | ありがとうございます。 |

**回数か、話速か**（`find_runaway`）。本物の繰り返しは 4 回までで暴走は
6 回以上。また **0.1 秒の区間に「ありがとうございます」(11 字)は入らない**
——日本語は速くても毎秒 12 字程度なので、3 割の余裕を見て 15 で切る。
本物は 13〜14、暴走は 23〜44 で、間に線が引ける。

**7/8 を正しく分け、誤発動は 0。**取りこぼす「はい」4 回は本文が 2 文字で
聴けばすぐ直る。**誤発動が 0 になることのほうが大事**——1 回につき
チャンク 1 本ぶんの時間が無駄になる。

検査の見本も**実データそのもの**に置き換えた。作り物（「同じ」×8）では
この誤発動を捕まえられなかった。

#### 拾えない壊れ方（2026-08-21）

**話速が正常なのに内容が違う**ものは、機械では判定できない。

```
01:04:05  はい、登りました。      0.92 秒 / 10 字/秒   ← 実際は「はい、もう一回ちょっと」
01:04:13  何か、 leader 聞いて。  1.04 秒 / 14 字/秒   ← 実際は「愚痴を聞いていただきまして」
```

重なった声の帯では small も large-v3 も崩れる（逐語正解でも d-missitsu だけ
脱落が 3 倍）。**聴いて直すしかない。**この製品はそのための道具である。

#### 「直った」の判定を厳しくした

**繰り返しが減っただけでは採らない。本文が減っていないことも見る。**

chunk_0001 は閾値ちょうど（3 区間）で発動しうるが、起こし直すと繰り返しは
3 → 2 に減る一方で**本文が 1,758 → 1,669 字に減る**。本当に壊れていた
chunk_0007 は 1,288 → 1,723 字と**増える**。**増えたときだけ採る**なら
両方とも正しく分かれる。

減ったときは元を採り、その旨をログに出す（「起こし直すと本文が減るので、
元のままにします。本物の相づちかもしれません」）。

### 9.5.7 同じ音声でも、毎回同じ本文にはならない（2026-08-20・実測）

**キャッシュを消して再実行すると、別の転写になる。**§7 は「同じ鍵なら
同じ結果」を暗に前提にしていたが、**その前提は成り立たない。**

#### 原因は温度の引き直し（乱数）

faster-whisper には「その 30 秒がうまく起こせていない」と判断したら
（圧縮率・確からしさが閾値を割ったら）**温度を上げて引き直す**仕組みが
ある。温度を上げた復号は**乱数を使う**ので毎回違う。

| 条件 | 結果 |
| --- | --- |
| large-v3 / GPU / 2 分の帯を 3 回 | **3 回とも 1 文字も違わない** |
| large-v3 / GPU / 7 分のチャンクを 2 回 | 1,793 字 / 1,708 字 → **違う** |
| 同上・`temperature=[0.0]`（引き直しを止める） | 1,912 字 / 1,912 字 → **完全に同一** |
| small / CPU / 2 分の帯を 2 回 | **6.0% の文字が違う** |

**GPU でも int8 でもない。**当初そう見立てたが誤りだった。
CPU の small のほうがよほど揺れる（苦しい窓が多く、引き直しが頻発するため）。

**揺れるのは「転写が苦しいところ」だけ。**うまく起きている箇所は再現する。

#### 引き直しは止めない

**§9.5.6 の暴走から抜けるための仕組みそのもの**である。同じ文を繰り返し
始めたら温度を上げて別の道を探す。止めると暴走が固定される。
`temperature=[0.0]` のほうが文字数は多いが、それは「苦しい窓をそのまま
出している」ということでもあり、中身が良い保証はない。

#### 記録として、どう扱うか

- **キャッシュには「結果を固定する」役目もある。**設定違いの使い回しを
  防ぐだけではない。**消すと本文が変わる。**
- **検証要約は「再現できる」と読まれてはいけない。**記録しているのは
  「この音声から、この日時に、この経路で作った」という事実であって、
  第三者が同じ手順で同じ本文を得られるという意味ではない。
  音声の SHA-256 が「どの音声から作ったか」を担保する。
- **§9.5.1 の測定（誤字 11.9% → 7.0% 等）は 2 分の帯で行っており、
  そこでは 3 回とも完全に再現した。**ばらつきの影響を受けていない。

#### 未決

- 検証要約の文面を直すか（いまは「処理経路」としか書いていないので、
  誤読の余地は小さい。優先度は低い）
- 種を固定できるか。faster-whisper は seed を受け取らない。
  CTranslate2 側の対応が要る

### 9.5.8 配布 —— 案イで実装（2026-08-21）

無料公開を前提に決めた。**案イ（small だけ同梱、large-v3 は初回取得）。**

| --- | ---: | --- | --- |
| ア. 全部同梱 | 4GB 級 | GPU 機でも初回から動く | **GitHub Releases は 1 ファイル 2GB が上限。載らない** |

| ウ. 版を分ける | 1.1GB / 4GB 級 | どちらも動く | 「どっちを落とすの」が必ず質問になる。無料配布は個別対応ができない |

#### GPU の部品（cuBLAS）は同梱しない

`nvidia-cublas-cu12` は `LicenseRef-NVIDIA-Proprietary`。本体は MIT なので、
**MIT の配布物に proprietary を混ぜると受け取った人が「自由に再配布できる」と
誤解する。**利用者の PC が配布元（NVIDIA が PyPI に上げた wheel）から直接
取る形にした。こちらが配るのは仕組みだけで、再配布にあたらない。

**要るのは 2 ファイルだけ**（実測）。nvidia パッケージ一式は 2.0GB だが、
`cublas64_12.dll` + `cublasLt64_12.dll`（735MB）で large-v3 の転写が完走した。
**cuDNN（1.0GB）も nvrtc（178MB）も不要。**

#### 実ビルドで確かめたこと（2026-08-21）

- ビルドが通る（警告は `tzdata` の 1 件。無害）
- 凍結後も `_internal/models/asr/small` を正しく解決する
- **通信を遮断した状態で 1.0 秒で読み込み、推論も通る**
- `dist` 1.1GB（LGPL 版 ffmpeg/ffplay 込み）

#### 同梱する ffmpeg は LGPL 版（2026-08-21・実測して発覚）

**GPL 版が入っていた。**`CREDITS.txt` は「LGPL 構成のビルドです」と表示し、
CI のコメントにも「どちらも LGPL 版」と書いてあったが、優先していた
gyan.dev の `release-essentials` は `--enable-gpl` でビルドされたもの。
**誰も確かめていなかった。**

本体は MIT。GPL の FFmpeg を同梱すると「同梱物全体を GPL にせよ」と
衝突する。別プロセスで起動する使い方なので、LGPL なら MIT のまま配れる。

配布元を BtbN の `ffmpeg-master-latest-win64-lgpl.zip` だけにし、
**取得直後に構成を検査する**（`--enable-gpl` / `--enable-nonfree` があれば
ビルドを止める）。手元でも同じことを見る検査を置いた
（`test_bundled_ffmpeg_is_lgpl` / `test_bundled_ffplay_is_present`）。

**コメントに書くだけでは足りない。**配布元が差し替わっても気づけない。

#### DLL はフルパスで読み込む（2026-08-22・配布版で発覚）

配布版で `Library cublas64_12.dll is not found` が出て CPU に落ちた。

**`os.environ["PATH"]` も `os.add_dll_directory()` も、凍結した exe では
CTranslate2 の DLL 読み込みに効かない。**開発環境で動いていたのは
**シェルの PATH に入れて試していたため**で、仕組みが効いていたのではない。
**自分で通した PATH で動いているのを、実装が動いていると読み違えた。**

`ctypes.WinDLL(フルパス)` で先に読み込む。一度プロセスに読み込ませれば、
あとから名前で LoadLibrary されたときに既読のものが使われる。
**依存の順に読む**（cublas は cublasLt を必要とする）。

検査は「PATH からも `nvidia` パッケージからも切り離した状態」で行う——
これが配布版と同じ条件。手元の環境の助けを消さないと、同じ見落としをする。

- インストーラ（Inno Setup）の実サイズ

### 11.1 処理時間の見積りと、10 分デモの成立条件【決定】

実測（1号機・CPU・small/int8・`beam_size` 既定 5・`vad_filter=False`）:
**67 分の実会議で転写 24.4 分（音声の 0.36 倍）**。

この比率のまま外挿すると:

| 音声 | 現行設定 | 高速化した場合（未実測・推定） |
| --- | --- | --- |
| 10 分の抜粋 | **約 3.6 分** | — |
| 60 分（標準検証音声 1 本目） | 約 22 分 | 約 5〜7 分 |
| **120 分（Day 45 デモの音声・標準検証音声 2 本目）** | **約 44 分** | 約 8〜14 分 |

**v28 第 5 章のデモは「同一の 2 時間音声について ①〜⑥ を通信遮断のまま 10 分で見せる」と定めている。
2 時間音声のライブ転写は 10 分に収まらない。** 音声を 60 分に替えても 22 分かかるので、
**設定を変えずにライブ転写を収めるには抜粋を使うしかない**。高速化（base モデル・`beam_size=1`・
VAD 有効）は 3〜5 倍を見込めるが、精度への影響が未測定で、しかも VAD は相づちを落とさないために
意図的に切っている（`align.py:220-222`）。

**決定（2026-08-14）: デモの起点を分ける。**②のライブ転写は 10 分の抜粋（約 3.6 分）で見せ、
③〜⑥は事前に転写済みの 2 時間ファイルで見せる。**通信遮断は全工程で維持できるので、
デモの主張（外に出さずに全部できる）は崩れない。**事業計画の記述は変更しない
（デモ台本の運用で吸収する）。

デモ台本（10 分）の目安:

| 時刻 | 内容 | デモ項目 |
| --- | --- | --- |
| 0:00 | 通信遮断を見せる ＋ 元音声の SHA-256 を表示 | ① |
| 1:00 | 10 分抜粋をローカル転写（約 3.6 分。進捗を見せながら説明） | ② |
| 5:00 | 2 時間ファイルで確認状態の三値と編集区間の一覧 | ③④ |
| 8:00 | Word 出力（版番号・処理経路）→ 元音声と照合 | ⑤⑥ |

## 14. 決定事項

**設計として決めたこと**: アダプタ境界は「チャンク → `Utterance[]`」（§4.1）／
按分（`redistribute_times`）はローカルでは通さない（§4.1・§5.2）／
区間は whisper の segment をそのまま使う（§5.1）／
実測時刻でも `time_reviewed` は立てない（§5.2）／
ローカルでは逐語トグルを無効化する（§5.4）／
スキーマは v5 のまま上げない（§8）／
実装は「アダプタ境界の導入」と「ローカル投入」を分ける（§13）。

| --- | --- | --- |
| 1 | 話者分離を本書に含めるか | **別設計書に分ける。**本書は §6.2 の受け口だけ固定し、`claude_話者分離_設計書.md` は PoC の実測後に書く。実装順は「転写を完成 → PoC → 設計書 → 実装」 |

**未決（実測待ち）**: Gate A の全数値、話者分離の的中率、
int8 変換後のモデル実サイズ、チャンク長をローカルで変える利得（境界の欠けと
中断再開のしやすさの釣り合い）、非力な機械での RTF（`base` を後から同梱するかの判断材料）。

**未決（2026-08-15 追加）— GPU 対応**: 開発機に GTX 1660 SUPER（6GB）があると
判明した（技術方針書 §3.6）。`align.py` は `DEVICE = "cpu"` を固定しており使っていない。
同じ機械で aTrain は GPU により転写 RTF 0.106（large-v3-turbo）・話者分離 RTF 0.045 を
出しており、**本製品の CPU 実測の 3.4 倍**。決めるべきは次の 3 点:

1. `EngineSpec` に device を足すか（`auto` / `cpu` / `cuda`）。既定は `cpu` のまま
   （中核層が GPU を持つ前提は置けない）
2. CUDA の依存（cuBLAS・cuDNN）を同梱するか、あるときだけ使うか。
   同梱すると配布が数百 MB 増える。**同梱しない場合、GPU があっても
   利用者の環境では動かない**ことがある
3. `engine` の記録に device を残すか（検証要約の「処理経路」に出すか）。
   **同じ音声・同じモデルでも device で結果が変わりうる**なら残すべき

**実務上の利得は大きい。**Gate A のモデル比較（small / turbo / distil）や
Day 45 の横並び実測は、GPU があれば試行錯誤が現実的な速さになる。
Day 45 の 10 分デモ（§11.1）の成立条件にも効く可能性がある。

**実測で片づいたもの**: 配布サイズ（§9。`dist` 365.4MB・モデル抜き。2026-08-14）／
本文と単語時刻が 1 回の転写から同時に取れること（§5.3。SAPI 合成音声で
`local_asr` の単語時刻が `align.py` の実測と完全一致。`tests/test_align_integration.py`）。
