# Whosaid 反訳エディタ

日本語の会議音声から、**誰が言ったかを人が確かめた記録**を作る
Windows デスクトップアプリです。文字起こしから話者の確定までを 1 つの画面で行い、
Word ファイル(.docx)にまとめます。

無料・MIT ライセンス。ソースコードはすべてこのリポジトリにあります。

**このアプリが他と違うのは 3 点です。**

1. **AI は「発言者A」までしか言いません。** 実名は人が音声を聴いて確定します
2. **`✓` と `△` を分けます。** 自分の耳で聴いたのか、一括で埋めただけなのか
3. **録音がこの PC から出ません。** 既定では通信を遮断したままでも動きます

---

## 1 · AI は「発言者A」までしか言いません

多くの文字起こしツールは、出席者名簿を渡すと AI が「この発言は佐藤さん」まで
当てようとします。**この方式は、日本語の会議音声では原理的に成立しません。**

話者分離の精度は DER(話者ダイアライゼーション誤り率)で測ります。

| 条件 | DER |
| --- | --- |
| 全員がヘッドセット・重なりが少ない(AMI ベンチ) | 約 11% |
| 重なり率 10〜20%(ふつうの会議) | 20〜35% |
| **日本語・14 話者の検証(WeSpeaker/ECAPA)** | **64.91〜82.80%** |

日本語会議音声の公開 DER はほとんど存在せず、数少ない検証がこの値です。
卓上マイク 1 本で録った日本語の会議で、AI が実名を当てられる根拠はありません。

しかも**話者の取り違えは、読んだだけでは気づけない誤り**です。誤字なら読めば
分かりますが、「誰が言ったか」が入れ替わっていても文章としては自然に読めます。
気づくには音声に戻るしかなく、それは結局、人が聴き直す作業です。

**このアプリは、その工程を隠しません。** AI には声質で A / B / C に分けるところ
までをやらせ、実名は人が区間の音声を聴いて確定します。

### それでも、全部を聴くわけではありません

同じ声のまとまりごとに 1 つ聴いて確定すれば、そのまとまり全体に広がります。

**既定のローカル経路では、話者分離が音声全体をとおして声をまとめます。**
まとまりの数は**会議に出ていた人数に近づく**ので、割当の操作もその回数で済みます。
6 名・67 分の実会議(卓上マイク 1 本)で測ったところ、**割当の操作は 6 回**でした。

数が動いても原理は変わりません — **操作の回数は、おおむね参加者の人数です。**

候補リストは確定するたびに学習します。同じ声のまとまり、会話の流れ(誰の次に誰が
話すか)、発言頻度から、可能性の高い人を上に並べ替えます。同じ実測で、
**候補リストの一番上に正解が出ていた割合は 93.2%** でした。
数字キーひとつで確定 → 次の未確定区間へ移動 → 自動再生、と流し続けられます。

> **実測は 1 本(67 分・6 名・2026-08)です。** 声の似た参加者が多い、発言の
> 重なりが多いといった条件では、まとまりが増えて操作も増えます。

クラウド経路(Gemini)は**チャンクごとに独立して声を聞き分ける**ため、
まとまりの数は「チャンク数 × 人数」に近づきます。同じ会議なら 30〜40 回程度です。
**ローカルが全長でまとめるのに対し、クラウドはチャンクの中で閉じる** — これが
両者で割当回数の変わる理由です。

## 2 · `✓` と `△` ── 「確認した」と「埋めただけ」を分けます

区間ごとに、話者の欄へ次のどちらかの印が付きます。

| 印 | 意味 |
| --- | --- |
| `✓` | **その区間の音声を、人が聴いて確定した** |
| `△` | 同じ声のまとまりへ一括で適用しただけ。**まだ誰も聴いていない** |

この 2 つは、成果物としてまったく違うものです。

`△` は、機械が「同じ声だ」と判断したまとまりに、人がラベルを 1 つ与えた結果です。
たいてい合っていますが、**外れているとしたら、それを誰も見ていません。**
`✓` は、その区間について人が耳で確かめたという記録です。

Word に出力すると、冒頭にこの内訳が入ります。

```
全 412 区間中 — 聴いて確定 156 / まとめて適用 240 / 未確定 16
```

**読む人が「どこまで人手で確かめたものか」を判断できます。**
「AI が作った議事録」と「人が全部聴いた反訳」の間には広い幅があり、
その幅のどこにいるかを書き残すのがこのアプリの役目です。

自動処理が `✓` を立てることは決してありません。一括適用も、再転写も、
どれだけ確からしくても `△` までです。**`✓` は人が聴いたときにしか付きません。**

> これは「証拠になる」という意味ではありません。
> **検証済みであることを記録する**、というところまでです。
> その記録をどう使うかは、使う人の領域です。

## 3 · 録音がこの PC から出ません

既定の設定では、音声も本文も端末の外へ出ません。文字起こしも話者の分離も
この PC の中で動きます。**API キーも要らず、通信を遮断したままでも動きます**
(モデルはインストーラに同梱しています)。

これが効くのは、外に出せないから困っていた人たちです。

- **質的研究** — 倫理審査で「音声データを外部サービスへ送らない」と約束した調査
- **士業** — 依頼者との面談、守秘義務のかかる打ち合わせ
- **社内調査・ハラスメント相談** — 対象者の音声をベンダーに預けられない案件
- **議会・監査** — 公開前の審議

### 声紋を保存しません

このアプリは**声の特徴量を永続保存しません。** 声のまとまりはその音声の中だけの
一時的なもので、実名との対応は人が付けたラベルとして残るだけです。
ファイルをまたいで「この声は佐藤さん」と記憶する仕組みはありません。

声紋登録型のツールは、その機能ゆえに法務リスクを負っています。Microsoft Teams の
話者分離はイリノイ州 BIPA(生体情報プライバシー法)違反で提訴されており
(争点は、抽出した声のベクトルを氏名に紐づける行為が声紋収集にあたるか)、
Microsoft は同州で voice enrollment を停止しています。

**この設計は、精度ではなく制度の上での違いです。** 便利さと引き換えに、
ファイルをまたいだ話者の同定はできません。

### クラウドを選んだときだけ

処理経路で「クラウド」を明示的に選んだときに限り、音声が Google(Gemini API)へ
送られます。既定ではありません。逐語モードを使いたい場合の選択肢です。

| 経路 | 中身 | 向き・不向き |
| --- | --- | --- |
| **ローカル(既定)** | この PC の faster-whisper と話者分離で処理。録音も本文も外へ出ません。API キー不要 | 録音を外部へ出せない案件向け。声のまとまりは**全長**で作ります。GPU があれば large-v3 が既定 |
| クラウド | 音声を Gemini API へ送って処理 | 逐語モードが使えます。録音が外部サービスへ出ます。声のまとまりは**チャンクごと** |

## 4 · できること・できないこと

自前の日本語会議音声に**逐語(一言一句)の正解を人手で作り**、6 系統を同じ物差しで
測りました。**指標によって順位が入れ替わりました。**

| エンジン | CER | フィラー保持 | 相づち保持 | 短発話再現 | 脱落の再現 |
|---|---:|---:|---:|---:|---:|
| **ローカル small(既定・無料)** | **27.3%** | 9.0% | 16.7% | **57.3%** | 1/33 |
| AmiVoice API(有償) | 28.3% | **152.2%** | 70.0% | 47.3% | 5/33 |
| gemini-2.5-flash(クラウド経路) | 29.5% | 106.0% | **130.0%** | 41.8% | **13/33** |
| large-v3-turbo | 30.7% | 17.9% | 33.3% | 45.5% | 3/33 |
| aTrain(turbo・GPU) | 34.1% | 23.9% | 36.7% | 40.9% | 2/33 |
| Notta(Privacy Mode・有償) | 34.5% | 95.5% | 73.3% | 38.2% | 3/33 |

**文字の誤り(CER)では既定のローカルが最も良く、フィラーの保持では最下位です。**
逐語に近い記録が欲しいなら、結果は混ざります。**「うちが一番」とは書けません。**

なお、**この 6 系統に要約や整文をするツールは含まれていません。** Notta も既定設定の
まま測っており(フィラーの設定は見当たらず)、95.5% を保持しています。
**整文するツールが 6 系統に無い以上、フィラーが少ないことに読みやすさの見返りは
ありません。** 表が示すのは値であって、なぜその値になったかではありません。
**読み物として整った文章が欲しい場合に何が良いかは、この測定からは分かりません。**

読み方:

- **CER** — 文字の誤り率。低いほど良い。**逐語の正解に対する値**で、挿入・削除・
  置換をすべて数えます([src/evaluate.py](src/evaluate.py) の `cer()`)。
  **フィラーを落としたぶんも誤りとして数えています**(既定のローカルはフィラー
  保持 9.0%)。読み物として使う分には、この数字ほど悪くありません
- **フィラー保持 / 相づち保持** — 正解と同数なら 100%。**100% を超えるのは
  「正解より多く出している」**という意味で、単純に良いわけではありません
- **短発話再現** — 短い発話をどれだけ拾えたか。高いほど良い
- **脱落の再現** — 人が聴いて拾えた 33 件の発話のうち、機械が拾えた数

> **実測は音源 1 本(67 分・6 名・卓上マイク 1 本・2026-08)です。**
> 別の会議では順位が変わりえます。数字を出している競合がほとんど無いので
> 比較先は限られますが、**この 1 本で測った結果である**ことは明記しておきます。

> **表の「CER」と、アプリの画面に出る「誤字」は別の指標です。**
>
> 表の CER は上のとおり、逐語の正解に対して挿入・削除・置換をすべて数えます。
> 画面の案内に出る「誤字」は**別の測定**によるもので、その測定では
> **脱落(取りこぼし)が誤字とは別の欄で数えられています**(設計書 §9.5.1)。
> つまり **CER が誤りとして数える取りこぼしは、誤字には入っていません。**
> 2 つは別の尺度なので、値を並べて引き算しても意味がありません。
>
> **どちらを見るかは用途で決まります。** 逐語に近い記録が要るなら、フィラーの
> 取りこぼしまで数える CER を見てください。読める文章が欲しいなら、CER は
> その用途には厳しすぎる物差しです。
>
> **ただし、その用途に合う数字を私たちは持っていません。** 画面に出る「誤字」は
> 再現できる定義が残っておらず、README には載せていません。**「読み物として
> どれくらい使えるか」を示す数字は、いまのところ無い**とお考えください。

> **`large-v3-turbo` は比較のために測ったモデルで、製品では使いません。**
> 表に載っているのは、**GPU 向けの候補として測った結果、退けたから**です。
> 6.0 分と速いものの、蒸留した復号器が固有名詞に弱く、「目立つ語」が
> 落ちました(設計書 §9.5.3)。
>
> **GPU を積んだ機械にこのアプリが勧めるのは、turbo ではない `large-v3` です**
> (`align.py` の `GPU_DEFAULT_MODEL`)。別のモデルなので、この表の turbo の値から
> large-v3 の性能は読めません。
>
> **そして `large-v3` は、この物差しでは測っていません。** 上の表に行がないのは
> そのためです。GPU 経路について、この表と同じ条件の数字は**まだありません。**

### なぜフィラーを落とすほうを既定にしているのか

**音声が外に出ないことを優先したからです。**

フィラーの保持だけを見れば、AmiVoice(152.2%)やクラウド経路(106.0%)が上です。
ローカル small は 9.0% で 6 系統中の最下位です。**この数字を知ったうえで、
それでも端末内で完結する経路を既定にしています。**

このアプリを必要としている人は、倫理審査で外部送信をしないと約束していたり、
守秘義務のかかる音声を扱っていたりします。**その人たちにとって「精度は高いが
音声を Google へ送る」は選択肢ではありません。** 送れないから困っている、
が出発点です。

逐語の再現が要る場合は、次のどちらかを選べます。

- **クラウド経路(逐語モード)を選ぶ** — 音声が Google へ送られます
- **ローカルのまま、聞こえた発話を人が足す** — 割当画面の
  「本文に無い声が聞こえた」から、聴こえたとおりに書き足せます

なお CER では、ローカル small は 6 系統中**最良**(27.3%)でした。日本語特化の
商用エンジンにも負けていません。弱いのはフィラーと短い発話の再現であって、
本文の書き取り全般ではありません。

### できないこと

- **逐語録としてそのまま使えません。** ローカル経路はフィラー(「えー」「あの」)を
  9.0% しか残しません。言い淀みまで要る反訳では、上のどちらかが要ります
- **聞き取れなかった発言があります。** 人が聴いて拾えた 33 件のうち、ローカル経路が
  拾えたのは 1 件でした。**6 系統すべてを足し合わせても、14 件(42%)はどれも
  拾えません。** 短い応答や重なった発言は、エンジンを選んでも解決しません。
  だから「本文に無い声が聞こえた」を人が足す機能があります
- **固有名詞・専門用語は誤ります。** 人名・団体名は特に弱いです
- **要約・議事録の自動生成はしません。** 逐語に近い記録を作るための道具です
- **ファイルをまたいだ話者の同定はしません。**(声紋を保存しないため)
- **日本語向けに調整してあります。** 照合の閾値も話速も日本語で測った値です

### 向いている使い方

音声を最初から最後まで聴いて反訳するつもりだった作業を、**下書きから始められる**
ようにするものです。ゼロから作るより速く、AI 任せより確かめられます。

## クイックスタート

1. [Releases](../../releases) から最新の `WhosaidEditorSetup-x.y.z.exe` をダウンロード
2. インストーラを実行
3. スタートメニューから「Whosaid 反訳エディタ」を起動
4. 音声ファイル選択 → 出席者を入力 → 「文字起こし → 割当画面へ」
   (既定のローカル処理なら API キーは要りません。クラウドを選ぶ場合だけ貼付)

### ダウンロード約 630MB / インストール後 約 1.1GB

文字起こしと話者分離のモデル(合計 510MB)を**インストーラに同梱**しているためです。
インストーラは圧縮されているので、**ダウンロードは約 630MB**(v2.1.0 の実測)、
**展開後に約 1.1GB** を使います。

**初回起動時のダウンロードはありません。** インストールした直後から、通信を
遮断した状態で使えます。

### 「WindowsによってPCが保護されました」と出ます

青い画面が出て起動できないことがあります。［詳細情報］→［実行］で進めます。

**コード署名をしていないためです。** 署名証明書は年数万円かかり、このアプリは
無料で配っているので取得していません。SmartScreen が警告しているのは
「署名が無いので発行元を確認できない」ということであって、**中身を検査した結果では
ありません。**

気になる場合は、ソースコードがこのリポジトリに全部あります。Releases の `.exe` は
[GitHub Actions](.github/workflows/build.yml) がこのリポジトリから自動ビルドした
もので、手元でも同じ手順で作れます(下の「ビルド手順」)。

### GPU があると、固有名詞の誤りが減ります

NVIDIA の GPU を積んだ PC では、より大きなモデル(**`large-v3`**)を取得するかどうかを
**一度だけ**尋ねます。turbo 版ではありません(§4 の注記)。

- `large-v3` … 約 3,090MB
- GPU で動かすための部品(cuBLAS) … 約 553MB

利用者が誤りとして挙げた固有名詞は、次の 5 語です。

> 同窓会 / 文科省 / 耐震 / 新潟 / 建て替え

`small` はこの 5 語を **1 つも正しく書けませんでした(0/5)**。`large-v3` では
**5 語とも正しくなりました(5/5)**。処理時間も **24 分 → 15.5 分**に短くなりました。
**速くなって、かつ固有名詞に強くなります。**

> **測定条件**: 音源 1 本(67 分の会議)・GPU は GTX 1660 SUPER(**VRAM 6GB**)・
> `int8_float16`・**2026-08-20 の 1 回**。出典は設計書 §9.5.1。
> **機械が違えば時間は変わります。** 5 語がどれも直るかも、この 1 本での結果です。
>
> **VRAM について。** 動作を確かめたのは **6GB の機械 1 台だけ**です。
> **これより少ない VRAM で `large-v3` が動くかは測っていません**(最小要件は
> 不明です)。読み込めなかった場合はエラーにはならず、**同梱の `small` に
> 自動で切り替わり、その旨と代償が画面のログに出ます**
> ([local_asr.py](src/local_asr.py))。ただし**取得した約 3.6GB は使われません。**
> VRAM が 6GB 未満の機械では、取得する前にこの点をご承知おきください。
>
> なお **この 5 語の判定を行うスクリプトはリポジトリにありません**
> (同じ表にある「誤字」と同じ測定です。§4 の注記を参照)。5 語を書き出して
> あるのは、**読者が自分の音声で同じことを確かめられるようにするため**です。

効くのは固有名詞と速度です。**フィラーの取りこぼしは大きなモデルでも残ります。**

> **取得を断っても、同梱の `small` でそのまま使えます。**
> `large-v3` は速度と固有名詞のための追加であって、**必須ではありません。**
> あとから設定画面で選ぶこともできます。
>
> 取得するときの通信先は Hugging Face と PyPI で、**録音も本文も送りません**
> (取得するだけです)。詳しくは [PRIVACY.md](PRIVACY.md)。

### 必要な画面の大きさ

**1024x768・拡大率 125% まで**で、割当画面のボタンがすべて見えることを
実測してあります(下限)。1280x720 以上なら 150% でも収まります。
内訳は下の「[画面の大きさ — 実測](#画面の大きさ--実測)」を参照してください。

## v2.0.6 からの変更点

### 1 · ローカルで完結するようになりました（最大の変更）

**v2.0.6 は Gemini API キーが必須**でした（音声は必ず Google へ送られました）。
v2.1.0 の既定はこの PC での処理で、**API キーは要らず、通信を遮断したままでも
動きます。** クラウド経路は残っていますが、明示的に選んだときだけ使われます。

### 2 · 話者分離が入りました

v2.0.6 では、声のまとまりを作るのは Gemini でした。v2.1.0 は端末内で分離します
（sherpa-onnx）。**まとまりを音声の全長で作る**ようになったので、割当の操作が
「区間ごと」から**実質「話者ごと」**に変わりました（6 名・67 分の実測で 6 回）。

### 3 · 測って、できないことも書きました

6 系統を同じ物差しで比較し、結果を上の「**4 · できること・できないこと**」に

## 使い方

### 1. 文字起こし(メイン画面)

1. **音声ファイル**を「参照...」で選択。
2. **出力フォルダ**は既定で *音声と同じフォルダ*。
3. **処理経路**を選ぶ。既定は「この PC で処理する(ローカル)」。
   クラウドを選んだときだけ **API キー**を貼り付けて「保存」(初回のみ)。
4. **話者の決め方**で「区間ごとに聴いて割り当てる(推奨)」を選ぶ。
   (「AI にすべて任せる(従来方式)」はクラウド専用です)
5. **出席者**を 1 行 1 人で入力(例: `佐藤(理事長)`)。
   よく発言する人を上に置くと、最初の候補順が良くなります。
   ここで入れなくても、割当画面から追加できます。
6. 「**文字起こし → 割当画面へ**」を押す。

完了すると `<音声名>.speakers.json`(作業ファイル)ができ、割当画面が自動で開きます。

### 2. 話者の割当(割当画面)

| | |
| --- | --- |
| 上部の帯 | 音声全体のタイムライン。色は話者、灰色は未確定。クリックでジャンプ |
| 左 | 区間の一覧。時刻 / 声のまとまり / 話者 / 発言。絞り込みは上部のラジオボタン |
| 右上 | 選択中の区間の全文(その場で修正できます) |
| 右中 | 再生。区間の前後に少し余白を付けて鳴らします |
| 右下 | 話者候補。**可能性の高い順**に並び、右側に理由が出ます |

一覧の話者欄に付く印:

| 印 | 意味 |
| --- | --- |
| (なし・黄色の行) | 未確定 |
| `△` | まとめて適用しただけ(**自分の耳では聴いていない**) |
| `✓` | その区間を聴いて確定した |

**キーボード操作**(これだけで一周できます)

| キー | 動作 |
| --- | --- |
| `Space` | 再生 / 停止 |
| `1`〜`9` | その番号の候補で確定 → 次へ |
| `Enter` | 一番上の候補で確定 |
| `↑` `↓` / `k` `j` | 区間を移動 |
| `Tab` / `Shift+Tab` | 次 / 前の「まだ手を付けていない区間」へ |
| `A` | 「同じ声のまとまり全体に適用」の ON/OFF(既定 ON) |
| `U` | 発言者不明にする |
| `D` | 未確定に戻す |
| `Ctrl+Z` | 取り消し |
| `Ctrl+S` | 保存 |

**おすすめの進め方(2 パス)**

1. **1 パス目 — まとまり単位でざっと埋める。**
   `A`(同じ声のまとまり全体に適用)は既定で ON です。各まとまりの代表を 1 つ聴いて確定すると、
   そのまとまりの未確定区間がすべて同じ話者になります。
   **必要な操作の回数は、まとまりがいくつできるかで決まります**(下の注記)。
   まとめて適用したぶんは `△`(未確認)として記録されます。
2. **2 パス目 — `△` を聴いて確かめる。**
   一覧上部を「**未確認のみ**」に切り替えると `△` の区間だけが並びます。`Tab` でたどり、
   聴いて正しければ同じ候補をもう一度選べば `✓` になります。違っていればその場で直します。
   ここを飛ばすと「速いが検証していない議事録」になるので、重要な会議では必ず通してください。
3. 間違えて一括適用したときは `Ctrl+Z`、あるいは下部の「このまとまりを未確定に戻す」。
4. 「**Word で出力...**」。

> **まとまりの作られ方は経路で違います。**
>
> **ローカル(既定)** は話者分離が**音声全体をとおして**声をまとめるので、
> まとまりは `声A` `声B` … のように 1 会議で 1 組です。数は参加者の人数に近づき、
> **操作の回数もおおむね人数ぶん**になります(6 名・67 分の実測で 6 回)。
>
> **クラウド(Gemini)** は**チャンクごとに独立して**声を聞き分けるので、
> 「C1-A」と「C2-A」は別のまとまりです。数は「チャンク数 × 人数」に近づきます
> (15 分 × 6 チャンク・6 名なら 30〜40 回程度)。
> ただし候補の学習は会議全体で共有され、
> **チャンク境界の連続性**(切れ目は発言の途中に落ちるので、前チャンク末尾と次チャンク先頭は
> 同じ人であることが多い)と**同じ記号の引き継ぎ**(前のチャンクの A が誰だったか)を
> 手がかりにするため、2 つ目以降のチャンクは最初の 1 手から候補が当たりやすくなります。
> チャンク長を長くする(既定 15 分 → 20 分など)と、まとまりの数自体が減って手数も減ります。

> **【?】【*】のまとまりには一括適用できません。**
> それぞれ「判別できなかった」「複数人が重なった」区間の寄せ集めで、同じ声ではないためです。
> 1 区間ずつ聴いて判断してください。

### 3. 出力

「**Word で出力...**」を押すと、出力の設定を選べます。

- **表題**(既定は音声ファイル名)
- 段落の先頭に時刻を入れるか(配布用の議事録なら外す / 反訳なら入れる)
- 同じ話者の連続発言を 1 段落にまとめるか
- 冒頭に出席者一覧を入れるか
- 「発言なし・雑音」と印を付けた区間を省くか
- 同じ内容の `.txt` も出すか(自分のテンプレートに貼り込む場合に便利)

冒頭には「全 N 区間中、聴いて確定 X 区間 / まとめて適用 Y 区間 / 未確定 Z 区間」という
但し書きが入ります。どこまで人手で確認したものかが、あとから読む人にも分かるようにするためです。
未確定の区間は【発言者不明】(赤字)、ユーザーが意図的に不明と判断した区間はグレーで出力されます。

### 中断・再開

- 割当作業は 4 秒ごとに自動保存されます。ウィンドウを閉じても失われません。
- 再開はメイン画面の「**保存済みの割当作業を開く...**」から `<音声名>.speakers.json` を選択。
- 文字起こし自体もチャンク単位でキャッシュされます(`.work_<音声名>\transcripts\`)。
  同じ音声で再実行すると未処理分だけが走り、**既存の割当結果も引き継がれます**。

## 詳細設定

- **処理経路**: `ローカル`(既定 / この PC で完結) / `クラウド`(Gemini へ送る)。
  ローカルでは API キー・逐語モード・従来方式は使えません(いずれも仕組みが無いため、
  画面上でも選べないようにしてあります)。
- **モデル**: 経路によって候補が変わります。
  - ローカル: `small`(既定) / `base`(速いが精度は落ちる) / `medium`(CPU では重い)
  - クラウド: `gemini-2.5-flash`(既定 / 速くて安価) / `gemini-2.5-pro`(高精度・高コスト)
- **チャンク長**: 既定 15 分。長いほど声の聞き分けが安定し、まとまりの数も減って
  割当が楽になりますが、アップロード/転写失敗のリスクは上がります。
  変更すると転写はやり直しになります(長さの違う転写を混ぜるとテキストと音声がずれるため)。
- **逐語モード**: フィラー・言い直しを残し、整文しません(反訳・記録用)。
- **AI にすべて任せる(従来方式)**: v1.3 の動作。名簿を AI に渡して実名まで推定させます。
  精度は落ちますが、割当作業をしたくない場合の選択肢として残しています。

### 作業ファイル(`<音声名>.speakers.json`)の中身

```jsonc
{
  "schema": 5,
  "audio_path": "C:\\...\\meeting.m4a",
  "duration": 3600.0,
  "source_sha256": "",     // 元音声の SHA-256。第三者が検算するための値
  // 処理経路の記録。Word の検証要約に「クラウド/ローカル」として出る
  "engine": { "mode": "local", "model": "small", "compute_type": "int8",
              "app_version": "2.1.0", "at": "2026-08-14T…Z" },
  "doc_revision": 0,       // Word を出力するたびに +1(書面に「版」として併記)
  "edit_log": [],          // 追記型の編集履歴(編集履歴の実装で記録される)
  "speakers": [ { "id": "sp01", "name": "佐藤", "note": "理事長", "order": 0 } ],
  "segments": [
    {
      "index": 0, "start": 0.0, "end": 25.0,
      "text": "本日はお忙しい中...",
      "cluster": "0:A",        // チャンク0の「声A」
      "chunk": 0,
      "speaker_id": "sp01",    // null なら未確定
      "reviewed": true,        // false = まとめて適用しただけ(未確認)
      "text_edited": false,    // true なら再実行時も本文を上書きしない
      "time_edited": false,    // true なら以後この区間にずれ補正を足さない
      "time_reviewed": false,  // true = 時刻を自分の耳で確かめた
      "orig_start": 0.0,       // AI が出した元の時刻。人が直しても動かさない
      "orig_end": 25.0
    }
  ]
}
```

`speaker_id` は名前ではなく ID を指しています。出席者の並び順を変えたり名簿を編集しても
ID は保たれるので、確定済みの区間が別人に化けることはありません。

## 画面の大きさ — 実測

<details>
<summary>どの画面サイズ・拡大率で全部が見えるか（実測表と、収まらない組み合わせの詳細）</summary>

割当画面はボタンが多いので、**どこまで小さい画面で全部が見えるかを実測して**
あります。○ の範囲では、ボタンが窓の外へ出たり下が切れたりしません。

| 画面 | 拡大率 100% | 125% | 150% |
| --- | --- | --- | --- |
| 1024x768 | ○ | ○ | ✗ |
| 1280x720 | ○ | ○ | ○ |
| 1366x768 以上 | ○ | ○ | ○ |

**下限は 1024x768・拡大率 125% まで**です。

✗ は 1024x768 の 150% だけです。この組み合わせでは、窓のいちばん下にある
編集系のボタン列（［出席者を編集...］から［一括適用を取り消す］までの 7 個）
が幅 984px に収まらず（1125px 必要）、右端の［一括適用を取り消す］が
押し出されて見えなくなります。**［保存］は別の行にあるので消えません。**

なお、`Ctrl+S` でも保存できます（[assign_gui.py](src/assign_gui.py) の
`<Control-s>`）。窓を閉じるときにも未保存の変更は自動で保存されます
（`_on_close`。確認は出ません）。

拡大率は Windows の［設定］→［システム］→［ディスプレイ］→［拡大縮小］です。

<details>
<summary>これ以上小さい画面に広げるには（未着手）</summary>

1024x768 の 150% に届かせるには、編集系のボタン列をさらに分ける必要が
あります。ただし**高さの余裕が 1 行しかない**ため（実測）、行を足すと
今度は上の「縮まない行」（時刻・確定など）が下から切れます。

つまり幅と高さのどちらかを別の方法で減らす必要があり、手としては
**窓全体の高さを減らす**（再生欄やずれ補正欄の圧縮、ボタンのメニュー化など）
が残っています。今回はそこまで行っていません。

</details>

## トラブルシューティング

| 症状 | 対処 |
| --- | --- |
| 起動時に「ffmpeg が見つかりません」 | `ffmpeg\ffmpeg.exe` を配置して再ビルド |
| 割当画面で音が出ない | `ffmpeg\ffplay.exe` を同梱して再ビルド。画面下部に現在の再生方式が出ます |
| 「音声ファイルが見つかりません」 | 音声を移動した場合。再生ボタンから場所を指定し直せます |
| 同じ人が別のまとまりに分かれる | クラウド経路では、声のまとまりはチャンクごとに独立です。チャンク長を延ばすと減ります。ローカル経路(既定)は全長でまとめるので、これは起きにくくなります |
| 再生した音声とテキストがずれる | Gemini の時刻推定のずれです。「◀ 5秒前から」「この先30秒▶」で前後を確認してください |
| 一括適用を間違えた | `Ctrl+Z`、または「このまとまりを未確定に戻す」 |
| API キーエラー | https://aistudio.google.com/apikey で発行し、画面で「保存」 |
| 大きなファイルでアップロード失敗 | 詳細設定の「チャンク長」を短く(例: 5 分) |
| インストーラを Defender がブロック | コード署名を行うか、自己責任で除外。配布前に署名を推奨 |
